## 一、核心概念

### 1.1 什么是工作区？

**工作区（Workspace）** 是 AgentScope 中为 Agent 提供**安全执行环境和资源管理**的模块。

它是 Agent 的"个人工作空间"，负责提供三类核心资源：
1. **工具（Tools）**：内置工具（Bash、Read、Write、Edit、Grep、Glob）+ MCP 工具
2. **技能（Skills）**：可动态加载的技能模块
3. **上下文卸载（Offload）**：将压缩的上下文或超大工具结果持久化到文件

**关键理解** 🔴：
- **七种后端**：LocalWorkspace（本地）、DockerWorkspace（容器）、E2BWorkspace（云沙箱）、**K8sWorkspace**（Kubernetes Pod）、**OpenSandboxWorkspace**（OpenSandbox 沙箱）、**DaytonaWorkspace**（Daytona 沙箱）、**BubblewrapWorkspace**（Linux bwrap 沙箱）
- **v2.0.4 新增**：`SandboxedWorkspaceBase` 抽象基类，所有沙箱类后端（Docker/E2B/K8s/OpenSandbox/Daytona/Bubblewrap）共享的基类，提供统一的 `_provision_backend()` / `_teardown_backend()` 模板、Bootstrap 探测 + 安装循环、MCP Gateway 统一管理
- **统一接口**：`WorkspaceBase` 确保同一份 Agent 代码可在任意后端无差别运行
- **MCP Gateway**：解决容器/沙箱内 MCP server 无法直接在宿主侧注册的问题
- **Offloader 协议**：Workspace 同时实现 `Offloader` 协议，为 Agent 提供上下文卸载能力
- **多租户管理**：Workspace Manager 负责分配和追踪 workspace，支持按 user/agent/session 隔离

### 1.2 为什么需要工作区？

| 需求 | 没有工作区 | 有工作区 |
|------|-----------|---------|
| 文件操作 | Agent 直接操作宿主文件系统 | 限定在 workdir 内，安全隔离 |
| 代码执行 | 直接在宿主运行，风险高 | Docker/E2B 沙箱内执行 |
| MCP 工具 | 只能在宿主侧运行 | 容器内 Gateway 转发 |
| 上下文管理 | 全部留在内存 | 可卸载到文件，按需检索 |
| 多租户 | 数据混在一起 | 按 user/agent/session 隔离 |
| 技能管理 | 硬编码 | 动态加载/卸载 |

**核心矛盾**：
- Agent 需要强大的工具能力（文件操作、代码执行）
- 但直接暴露宿主环境有安全风险

**AgentScope 的解法**：分层后端（Local/Docker/E2B）+ MCP Gateway + Offloader 协议

## 二、核心接口 / 类型定义

### 2.1 WorkspaceBase（抽象基类）

```python
class WorkspaceBase:
    workspace_id: str    # 唯一标识符
    workdir: str         # Agent 可见的根目录
    is_alive: bool       # 生命周期标志

    # === 生命周期（Developer）===
    async def initialize(self) -> None    # 分配资源、连接 MCP、复制技能
    async def close(self) -> None         # 释放所有资源
    async def reset(self) -> None         # 清空 per-session 状态

    # === 资源发现（Agent）===
    async def get_instructions(self) -> str       # workspace 专属 system prompt
    async def list_tools(self) -> list[ToolBase]  # 内置工具
    async def list_mcps(self) -> list[MCPClient]  # 活跃的 MCP 客户端
    async def list_skills(self) -> list[Skill]    # 可用技能

    # === 上下文卸载（Agent）===
    async def offload_context(self, session_id: str, msgs: list[Msg]) -> str
    async def offload_tool_result(self, session_id: str, tool_result: ToolResultBlock) -> str

    # === 动态管理（User）===
    async def add_mcp(self, mcp_client: MCPClient) -> None
    async def remove_mcp(self, name: str) -> None
    async def add_skill(self, skill_path: str) -> None
    async def remove_skill(self, name: str) -> None
```

### 2.3 六种后端对比

| 特性 | LocalWorkspace | DockerWorkspace | E2BWorkspace | **K8sWorkspace** ⚠️ | **OpenSandboxWorkspace** ⚠️ | **DaytonaWorkspace** ⚠️ |
|------|---------------|-----------------|--------------|---------------------|---------------------------|------------------------|
| **执行环境** | 宿主文件系统 | Docker 容器 | E2B 云沙箱 | Kubernetes Pod | OpenSandbox 沙箱 | Daytona 沙箱 |
| **隔离级别** | 无 | 进程级 | 完全隔离 | Pod 级 | 完全隔离 | 完全隔离 |
| **持久化** | 本地目录 | 挂载卷 / 可写层 | 沙箱文件系统 | PVC（跨 Pod 重启） | 沙箱文件系统（pause） | 沙箱文件系统（stop） |
| **MCP 访问** | 直接 stdio | Gateway HTTP | Gateway HTTP | Gateway HTTP | Gateway HTTP | Gateway HTTP |
| **适用场景** | 开发调试 | 生产部署 | 托管服务 | K8s 集群 | OpenSandbox 平台 | Daytona 平台 |
| **依赖** | 无 | aiodocker | e2b SDK | kubernetes_asyncio | opensandbox SDK | daytona SDK |
| **workdir** | 本地路径 | 挂载到容器 `/workspace` | 沙箱内 | PVC 挂载 `/workspace` | 沙箱内 | 沙箱内 |
| **关闭行为** | 无操作 | 删除容器 | 删除沙箱 | 删除 Pod（保留 PVC） | pause（保留文件系统） | stop（保留文件系统） |

**v2.0.4 新增后端详解**：

**K8sWorkspace** (`src/agentscope/workspace/_k8s/`)：
- 基于 Kubernetes Pod + PVC 持久化
- Pod 生命周期：查找→复用 Running / 删除重建 Failed / 新建
- PVC：`as-ws-{workspace_id}`，挂载到 `/workspace`，默认关闭时保留
- 文件传输：tar-stream（类似 `kubectl cp`）
- 构造参数：`kubeconfig`、`namespace="agentscope"`、`storage_size="1Gi"`、`delete_pvc_on_close=False`

**OpenSandboxWorkspace** (`src/agentscope/workspace/_opensandbox/`)：
- 基于 OpenSandbox SDK
- 关闭时 `sandbox.pause()`（非 kill），保留文件系统
- 健康检查：30s 轮询 `_wait_until_running()`

**DaytonaWorkspace** (`src/agentscope/workspace/_daytona/`)：
- 基于 Daytona SDK
- 沙箱解析：按 label 查找→复用/恢复/新建
- 状态归一化：error→recover、stopped/paused→start
- SDK 路径从 SDK API 获取，不硬编码 `/home/daytona`
- 关闭时 `sandbox.stop(force=False)` 保留文件系统

from agentscope.workspace import BubblewrapWorkspace

workspace = BubblewrapWorkspace(
    host_workdir="/path/to/workdir",   # 挂载到沙箱内 /workspace（RW）；省略则临时目录，关闭时清理
    share_net=True,                    # 必须 True：TCP MCP gateway 跨多次 bwrap 执行需经宿主回环可达
    extra_pip=["numpy"],               # 引导阶段装入网关 venv 的依赖
)
await workspace.initialize()

**设计要点** 🔴：
- **轻量 Linux 沙箱**：基于 `bwrap`（Bubblewrap）做 namespace + 挂载隔离，**不隔离网络命名空间**——当前 TCP MCP gateway 要求 `share_net=True`，沙箱内与宿主共享网络命名空间，可访问宿主回环服务与云元数据（`169.254.169.254`）。网关 bearer token 只保护 gateway 本身，不保护宿主其余网络
- `host_workdir` 以 RW 挂载到 `/workspace`；省略则创建临时目录并在关闭时清理。Bootstrap 缓存默认放在 `host_workdir` 之外
- 配套 `BubblewrapWorkspaceManager`（`app/workspace_manager/_bubblewrap_workspace_manager.py`）继承 `WorkspaceManagerBase`，支持多租户隔离

**面试考点**：Bubblewrap vs Docker/K8s 隔离粒度差异？答：bwrap 仅做用户态 namespace + mount 隔离，无 daemon、无镜像，启动极快、开销低，但**不是网络沙箱**；Docker/K8s 提供更强（也更重）的隔离。适合"需要隔离文件系统但不想承担容器运行时成本"的场景。

### 3.2 关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 三种后端统一接口 | `WorkspaceBase` 抽象 | 同一份 Agent 代码可在任意后端运行 |
| MCP Gateway | 容器内 FastAPI + HTTP | 解决 stdio 会话无法跨越容器边界的问题 |
| Bearer 鉴权 | per-workspace token | 每次 `initialize()` 重新生成，防止未授权访问 |
| 技能索引 | `.skills` JSON 文件 + SHA-256 哈希 | 避免重复复制相同内容的技能 |
| MCP 持久化 | `.mcp` JSON 文件 | 重启后恢复 MCP 配置 |
| Offloader 协议 | Protocol 类 | 结构化类型，Workspace 自然实现 |
| 隔离策略 | Manager 层控制 | LocalManager 按 agent_id，DockerManager 按 (user_id, agent_id) |
| 路径穿越防护 | `realpath` 检查 | 防止技能路径逃逸出 skills_dir |

### 4.2 核心实现

#### 4.2.1 LocalWorkspace 初始化

```python
class LocalWorkspace(WorkspaceBase):
    async def initialize(self):
        os.makedirs(self.workdir, exist_ok=True)

        # 1. 恢复或种子 MCP 配置
        mcp_file = os.path.join(self.workdir, ".mcp")
        if await self._backend.file_exists(mcp_file):
            # 从 .mcp 文件恢复
            raw = await self._backend.read_file(mcp_file)
            for m in json.loads(raw):
                self._mcps.append(MCPClient.model_validate(m))
        else:
            # 首次使用，种子 default_mcps
            self._mcps = list(self.default_mcps)
            await self._save_mcp_file()

        # 2. 连接有状态的 MCP
        for mcp in self._mcps:
            if mcp.is_stateful and not mcp.is_connected:
                await mcp.connect()

        # 3. 种子技能（按内容哈希去重）
        for skill_path in self.skill_paths:
            result = await self._validate_and_hash_skill(skill_path)
            _, raw_name, skill_hash = result
            if skill_hash in existing_hashes:
                continue  # 已存在，跳过
            # 复制到 skills/{sanitized_name}/
            await asyncio.to_thread(shutil.copytree, skill_path, dest_path)
```

#### 4.2.3 Gateway 宿主侧适配器

```python
class GatewayMCPClient(MCPClient):
    """MCPClient 子类，用 HTTP 替代 stdio/HTTP 会话"""
    # connect → POST /mcps
    # close → DELETE /mcps/{name}
    # list_tools → GET /mcps/{name}/tools

class GatewayMCPTool(ToolBase):
    """ToolBase 子类，__call__ 是 HTTP POST"""
    async def __call__(self, **kwargs) -> ToolChunk:
        response = await self._http.post(
            f"{self._gateway_url}/mcps/{self.mcp_name}/tools/{self._tool.name}",
            json={"arguments": kwargs},
            headers={"Authorization": f"Bearer {self._token}"},
        )
```

### 4.6 v2.0.6 大改：工作区共享 + Skill 按 Agent 隔离（#1951 + #2283）

v2.0.6 对工作区做了架构级重构，核心变化是**归属维度从"单 key"扩展为 `(agent_id, session_id)` 双 key**，并新增**跨 Agent 共享**与 **Skill 按 Agent 分区**能力。

#### 4.6.1 跨 Agent 共享：IsolationPolicy.PER_USER（#1951）

**归属粒度由 `WorkspaceManager` 的 `IsolationPolicy` 决定**（`app/workspace_manager/_base.py`）：

| 策略 | workspace_id 推导 | 效果 |
|------|------------------|------|
| `PER_AGENT`（默认） | `BLAKE2b("user_id::agent_id")` | 每 (user, agent) 一个 workspace |
| **`PER_USER`**（#1951 新增） | `BLAKE2b("user::user_id")` | **同一 user 的所有 agent 共享同一 workspace_id → 同一实例** |
| `PER_SESSION` | fresh UUID | 每会话独立 |

```python
# app/workspace_manager/_base.py
class IsolationPolicy(StrEnum):
    PER_AGENT = "per_agent"
    PER_USER = "per_user"    # ← v2.0.6 新增：跨 agent 共享
    PER_SESSION = "per_session"

    def assign_workspace_id(self, user_id, agent_id, session_id) -> str:
        ...
```

**显式共享通道**：`CreateSessionRequest.workspace_id`（可选字段）——请求带 `workspace_id` 时**始终优先**（team invite/borrow 强制共享），否则才走 isolation policy。

**关键细节** 🔴：
- 即使 `PER_USER` 共享了 `workspace_id`，workdir 仍由 `agent_id` 推导（Local：`basedir/<agent_id>`）——物理目录是**第一个触达它的 agent** 的 workdir
- `SessionConfig.workspace_id` 成为权威绑定，也是 manager 缓存键（`storage/_model/_session.py`）
- 共享工作区内 agent 之间靠 **Skill 分区（见 4.6.2）** 隔离，MCP 靠 `(agent, session)` 键控隔离

#### 4.6.2 Skill 按 Agent 分区隔离 + 按 Session 选择（#2283）

**目录布局大改**：

```
{workdir}/skills/
├── .seed/               # 模板：skill_paths 首次注入处，不是分区、不被直接读
├── default/             # 无 agent 的 SDK 调用者专用分区（DEFAULT_SKILL_PARTITION）
└── <agent_id>/          # 每 agent 一个分区（可原地编辑，分区即所有权边界）
    ├── .index           # LocalWorkspace 才有：{dir_name: {hash, skill_name}} 哈希索引
    └── <skill_dir>/SKILL.md
```

**核心机制**：
- `list_skills(*, agent_id=None)`——keyword-only `agent_id`，无 `session_id`；"按 session 选择"的实际语义是**会话继承其 agent 的分区**（同一 agent 的所有 session 共享该分区）
- `_equip_partition(agent_id)`：首次 skill 调用把 `.seed` 原子 rename 复制成分区（并发安全，输者丢弃）
- **`_migrate_skill_layout`（#2283 幂等迁移）**：旧版平铺 `skills/<skill>/` + `.skills` 索引整体搬进 `skills/.seed/`，已存在内容的共享工作区升级后每个新 agent 都能从种子装备
- 分区删除：`purge_agent(agent_id)` 删 `skills/<agent_id>/`；agent 自己删掉的 skill **不会从种子复活**（与 `default_mcps` 不复活同规则）
- 路径安全：`_skill_partition()` 拒绝以 `.` 开头或含 `/`、`\` 的 agent_id（防 `..`/`.seed` 逃逸）

#### 4.6.3 MCP 持久化 v2 格式 + 双 key 隔离（#1951）

- `.mcp` 落盘从 v1（平铺 list）升级为 **v2 嵌套格式**：`{version: 2, mcps: {agent_id: {session_id: [...]}}}`；v1 读回走 legacy 空 id
- MCP 实例与声明按 `(agent_id, session_id)` 隔离（`_mcp_specs` / `_mcp_instances` / `_mcp_last_used` 全部双 key 键控）——**stateful MCP 状态互不泄漏**
- Gateway 内部同构：`_mcp_gateway_app._State.clients: dict[tuple[str,str], dict[str, MCPClient]]`；proxy 在 query 带 `?agent_id=&session_id=`
- `purge_session(agent_id, session_id)`：删除某 agent/session 的 MCP 实例、声明与 `sessions/<sid>/` offload 目录
- LRU 驱逐（`_enforce_mcp_capacity`）跨 `(agent, session)`，永不驱逐请求方自身

#### 4.6.4 REST 契约变化

**通用变化**：所有 `/workspace/*` 端点新增必填 `agent_id` 查询参数（与 `session_id` 并存）；workspace 解析链变为 `(user, agent, session) → SessionConfig.workspace_id → manager 缓存`。

| 端点 | 变化 |
|------|------|
| `GET /workspace/mcp` | 加 `agent_id`；返回 `list[MCPClientStatus]`（含 is_healthy/tools/error），读 agent+session 的 MCP |
| `POST /workspace/mcp` / `from-library` / `DELETE /workspace/mcp/{name}` | 全部加 `agent_id`，按 (agent, session) 注册/移除 |
| `GET /workspace/skill` | **核心变化**：返回**该 agent 分区**的技能（`list_skills(agent_id=)`） |
| `POST /workspace/skill/upload` | multipart `manifest` + `files`，安装进 agent 分区 |
| `DELETE /workspace/skill/{skill_name}` | **按 agent 分区删除**；`agent_id=None` 时基类搜全部分区 |
| `GET /workspace/status` | 返回 `WorkspaceStatus{workdir, cwd, git}`（#2257 新增 cwd + git 状态） |
| `GET /workspace/files` | #2187 新增（支持 `token` 或 `X-User-ID` 鉴权，list_dir/read_file） |
| `POST /sessions/` | `CreateSessionRequest` 新增可选 `workspace_id`；显式值优先 |

#### 4.6.5 沙箱基类对齐新架构（#1951 + #2283）

> 沙箱没有新增后端类型，而是把 `SandboxedWorkspaceBase`（`_sandboxed_base.py`，+228 行）整体对齐到新架构。所有具体后端（Docker/E2B/K8s/Daytona/Bubblewrap）**零改动、免费继承**。

**① MCP 从"启动即全量加载"改为"声明恢复 + 按需实例化"**

```python
# 改动前：单份共享列表

_mcp_instances: dict[tuple[str,str], dict[str, MCPClient]]    # live handles
_mcp_last_used: dict[tuple[str,str], float]                   # LRU 时间戳
```

```python
# 改动前
```

- 新增 `max_live_stateful_mcps` 参数（默认 **40**）透传沙箱——LRU 驱逐最久未用的实例，永不驱逐请求方自身
- 关闭时不再逐个 close proxy（gateway 进程随沙箱消亡），只清 `_mcp_instances`/`_mcp_last_used`

`.mcp` 删除后每个 agent/session 回到"从未配置"状态 → 下次 `list_mcps` 重新继承 `default_mcps`。

**③ Bubblewrap 精简（-3 行）**

- 启动 gateway 的 `launch_cmd` **移除 `--config {self._mcp_file}`**——gateway 空启动，不再推送 MCP 配置
- **删除**启动后 `self._mcps = list(await self._gateway.list_mcps())` 的全量拉取

**④ Skill 分区免费继承**

```python
await self._migrate_skill_layout()   # 旧布局 → .seed 幂等迁移
await self._setup_skills()           # 装备分区
```

`_equipped_partitions` 参与 reset 清理（清空后重新装备）。Skill 分区能力全部由基类提供，各沙箱后端无需感知。

**⑤ 新增端到端测试（质量保障）**

| 文件 | 验证点 |
|------|--------|
| `test_e2e_docker_mcp.py`（+251） | Docker 沙箱 + MCP `(agent, session)` 双 key 隔离 |
| `test_e2e_e2b_mcp.py`（+176） | E2B 沙箱 + MCP 双 key 隔离 |

### 7.2 工程实现题（字节高频）

#### Q4: 技能去重是如何实现的？（阿里高频）

**参考答案**：
> **技能去重机制**：
> 1. 每个技能目录包含 `SKILL.md`，其中有 YAML front matter（name, description）
> 2. 初始化时计算 `SKILL.md` 内容的 SHA-256 哈希
> 3. `.skills` 索引文件记录 `{dir_name: {hash, skill_name}}`
> 4. 新技能若哈希已存在则跳过，避免重复复制
>
> **技能去重代码示例**：
> ```python
> def _validate_and_hash_skill(skill_path: str) -> tuple[str, str, str]:
>     skill_md_path = os.path.join(skill_path, "SKILL.md")
>     with open(skill_md_path, "r") as f:
>         content = f.read()
>     
>     # 解析 YAML front matter
>     post = frontmatter.loads(content)
>     skill_name = post.get("name")
>     
>     # 计算 SHA-256 哈希
>     skill_hash = hashlib.sha256(content.encode()).hexdigest()
>     
>     return skill_path, skill_name, skill_hash
> 
> # 初始化时检查哈希
> if skill_hash in existing_hashes:
>     logger.info("Skill '%s' already exists, skipping", skill_name)
>     continue
> ```
>
> **2026 年趋势**：技能去重成为技能管理的标准机制

- 为什么使用 SHA-256 而不是 MD5？→ SHA-256 更安全，抗碰撞
- 技能去重的性能开销如何？→ 较小，主要是哈希计算开销
- 如何处理技能冲突？→ 使用哈希去重，避免重复复制

#### Q5: Gateway 鉴权是如何工作的？（腾讯高频）

>     if not state.token:

#### Q7: 如何实现自定义的 Workspace 后端？（腾讯高频）

**参考答案**：
> **实现自定义 Workspace 后端的步骤**：
> 1. 继承 `WorkspaceBase`
> 2. 实现所有抽象方法：`initialize`, `close`, `list_tools`, `list_mcps`, `list_skills`, `offload_context`, `offload_tool_result`, `add_mcp`, `remove_mcp`, `add_skill`, `remove_skill`, `get_instructions`
> 3. 实现 `__aenter__` / `__aexit__`（基类已提供默认实现）
> 4. 如需 MCP Gateway，在 workspace 内部部署 FastAPI 进程，宿主侧使用 `GatewayMCPClient`
>
> **自定义 Workspace 后端代码示例**：
> ```python
> class CustomWorkspace(WorkspaceBase):
>     async def initialize(self):
>         # 初始化资源
>         self._resources = {}
>     
>     async def close(self):
>         # 释放资源
>         self._resources.clear()
>     
>     async def list_tools(self) -> list[ToolBase]:
>         # 返回工具列表
>         return [Bash(), Read(), Write()]
>     
>     async def list_mcps(self) -> list[MCPClient]:
>         # 返回 MCP 客户端列表
>         return []
>     
>     async def list_skills(self) -> list[Skill]:
>         # 返回技能列表
>         return []
>     
>     async def offload_context(self, session_id: str, msgs: list[Msg]) -> str:
>         # 卸载上下文
>         path = f"/tmp/{session_id}/context.json"
>         with open(path, "w") as f:
>             json.dump([msg.dict() for msg in msgs], f)
>         return path
>     
>     async def offload_tool_result(self, session_id: str, tool_result: ToolResultBlock) -> str:
>         # 卸载工具结果
>         path = f"/tmp/{session_id}/tool_result.json"
>         with open(path, "w") as f:
>             json.dump(tool_result.dict(), f)

#### Q8: 多租户场景下，如何防止 workspace 之间的数据泄露？（阿里高频）

**参考答案**：
> **多租户数据泄露防护**：
> 1. **Manager 层隔离**：不同 user/agent 分配不同的 workspace 实例
> 2. **容器隔离**：Docker/E2B 提供进程级/完全隔离
> 3. **路径检查**：`realpath` 防止路径穿越
> 4. **Gateway 鉴权**：per-workspace token 防止未授权访问
> 5. **workdir 隔离**：每个 workspace 独立的 workdir，不共享
>
> **多租户数据泄露防护代码示例**：
> ```python
> # Manager 层隔离
> class DockerWorkspaceManager:
>     def get_workspace(self, user_id: str, agent_id: str) -> DockerWorkspace:
>         key = (user_id, agent_id)
>         if key not in self._workspaces:
>             self._workspaces[key] = DockerWorkspace(
>                 workdir=f"/workspaces/{user_id}/{agent_id}"
>             )
>         return self._workspaces[key]
> 
> # 路径检查
> def _is_safe_path(base_path: str, target_path: str) -> bool:
>     base_real = os.path.realpath(base_path)
>     target_real = os.path.realpath(target_path)
>     return target_real.startswith(base_real)
> 
> # Gateway 鉴权
> async def _auth(request: Request):
>     if not state.token:
>         return
>     header = request.headers.get("authorization", "")
>     if header != f"Bearer {state.token}":
>         raise HTTPException(status_code=401, detail="unauthorized")
> ```
>
> **2026 年趋势**：多层防护成为多租户安全的标准

- 如何检测数据泄露？→ 使用审计日志，监控异常访问
- 如何优化多租户性能？→ 使用连接池，减少连接开销

### 8.1 开发建议

| 建议 | 说明 |
|------|------|
| 开发阶段用 LocalWorkspace | 快速迭代，无需容器开销 |
| 生产环境用 Docker/E2B | 安全隔离，防止代码执行风险 |
| 合理设置 Manager TTL | 避免空闲 workspace 占用资源 |
| 使用 ToolGroup | 工具过多时按需激活，减少 token 消耗 |

### 8.2 性能优化

| 优化点 | 方法 |
|--------|------|
| 技能去重 | SHA-256 哈希避免重复复制 |
| MCP 连接复用 | Gateway 共享 HTTP 连接池 |
| 延迟初始化 | workspace 按需创建，不预分配 |
| TTL 淘汰 | 空闲 workspace 自动回收 |

### 8.3 安全建议

| 建议 | 说明 |
|------|------|
| 生产环境必须用 Docker/E2B | Local 无隔离，代码执行风险高 |
| 定期轮换 Gateway token | 防止 token 泄露 |
| 审查技能来源 | 技能可执行任意代码 |
| 限制 workdir 权限 | 防止 Agent 操作敏感文件 |

## 九、总结

> **一句话总结**：AgentScope 工作区是 Agent 的安全执行环境，通过三种后端（Local/Docker/E2B）提供不同级别的隔离，通过 MCP Gateway 解决容器内 MCP 的跨边界访问，通过 Offloader 协议支持上下文卸载，通过 Manager 层实现多租户隔离，确保同一份 Agent 代码可在任意后端无差别运行。
