## 一、核心概念

### 1.1 什么是 RAG？

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是 AgentScope 中用于**将外部知识库的检索能力接入 Agent 推理循环**的模块。

它由 5 个可独立替换的子系统组成：

```
┌─────────────────────────────────────────────────────────────────────┐
│                       RAG 模块全景                                   │
│                                                                     │
│  ┌──────────┐   ┌──────────┐   ┌──────────────┐   ┌────────────┐  │
│  │  Parser   │──▶│  Chunker │──▶│EmbeddingModel│──▶│ VectorStore│  │
│  │  (解析器) │   │ (切块器) │   │  (嵌入模型)  │   │  (向量库)  │  │
│  └──────────┘   └──────────┘   └──────────────┘   └────────────┘  │
│       │               │                │                  │         │
│    Section[]       Chunk[]         list[float]        VectorRecord  │
│                                                                     │
│              ┌──────────────────────────────────┐                   │
│              │         KnowledgeBase             │                   │
│              │  (绑定 embedding + store + coll)  │                   │
│              └──────────────────────────────────┘                   │
│                          │                                          │
│              ┌───────────▼───────────┐                              │
│              │    RAGMiddleware       │                              │
│              │ (static / agentic)    │                              │
│              └───────────────────────┘                              │
└─────────────────────────────────────────────────────────────────────┘
```

**关键理解** 🔴：
- **Parser**：将原始文件拆分为 `Section[]`（自然边界：PDF 页、PPT 幻灯片、整张图片等）
- **Chunker**：将 `Section[]` 切分为 `Chunk[]`（最终入库单元），**严格不跨 Section 合并**
- **EmbeddingModel**：将 Chunk 内容转化为向量
- **VectorStore**：存储向量 + 元数据，支持相似度检索
- **KnowledgeBase**：运行时句柄，绑定 (embedding, store, collection)，对外暴露一站式 API
- **RAGMiddleware**：将检索接入 Agent 的 ReAct 循环，支持 static / agentic 两种模式

---

### 1.2 为什么需要 RAG？

| 需求 | 没有 RAG | 有 RAG |
|------|---------|--------|
| 企业知识库问答 | 模型不知道内部文档 | 检索相关片段注入上下文 |
| 多模态文档 | 只能处理文本 | 原生支持图片/表格等多模态 |
| 多租户隔离 | 数据混在一起 | `metadata_filter` 深度防御 |
| 分布式部署 | 单机运行 | 独立 IndexWorker + 消息总线 |
| Agent 自主检索 | 每次强制检索 | agentic 模式让模型决定何时检索 |

**核心矛盾**：
- LLM 参数知识有截止日期，无法覆盖私有/最新数据
- 直接拼接全文会超出上下文窗口

**AgentScope 的解法**：模块化流水线（Parser → Chunker → Embedding → VectorStore）+ 中间件集成

## 二、核心接口 / 类型定义

### 2.1 数据结构

```python
# === 索引流水线的两个中间产物 ===

class Section(BaseModel):
    """Parser 产出 —— 一个自然边界"""
    content: TextBlock | DataBlock    # 文本用 TextBlock，多模态用 DataBlock
    source: str                        # 源文件名（如 "report.pdf"）
    metadata: dict[str, Any]           # 格式特定元数据（如 {"page": 3}）

class Chunk(BaseModel):
    """Chunker 产出 —— 最终入库单元"""
    content: TextBlock | DataBlock     # 从 Section 切片而来
    source: str                        # 继承自 Section
    chunk_index: int                   # 文档内 0-based 序号（用于上下文扩展）
    total_chunks: int                  # 文档总 chunk 数（界定扩展范围）
    metadata: dict[str, Any]           # 继承自 Section

# === 向量库层的包装类型 ===

class VectorRecord(BaseModel):
    """即将入库的记录 = Chunk + 向量 + 文档ID"""
    vector: list[float]
    document_id: str
    chunk: Chunk

class VectorSearchResult(BaseModel):
    """检索命中 = Chunk + 相似度分数 + 文档ID"""
    score: float
    document_id: str
    chunk: Chunk

class DocumentSummary(BaseModel):
    """文档摘要（list_documents 返回）"""
    document_id: str
    source: str
    chunk_count: int
    metadata: dict[str, Any]
```

### 2.2 公开 API

#### KnowledgeBase（核心运行时句柄）

| 方法 | 签名 | 说明 |
|------|------|------|
| `ensure_collection` | `async () -> None` | 幂等创建 backing collection，首次操作自动调用 |
| `search` | `async (queries, top_k=5, score_threshold=None) -> list[VectorSearchResult]` | 批量嵌入 + 并发检索 + 去重排序 |
| `insert_document` | `async (chunks, document_id=None, document_metadata=None) -> str` | 批量嵌入 + 插入，返回 document_id |
| `delete_document` | `async (document_id) -> None` | 按 document_id 删除所有记录 |
| `list_documents` | `async () -> list[DocumentSummary]` | 列出所有已索引文档 |

#### ParserBase（解析器基类）

| 方法 | 签名 | 说明 |
|------|------|------|
| `supported_media_types` | `list[str]` (类属性) | IANA 媒体类型列表 |
| `supported_extensions` | `classmethod () -> list[str]` | 支持的文件扩展名 |
| `parse` | `async (file: bytes \| str, filename: str) -> list[Section]` | 解析文件为 Section 列表 |

#### ChunkerBase（切块器基类）

> **v2.0.6+（#2083）**：Chunker 配置显式化 + schema 驱动重构。`ChunkerBase` 新增两个类属性，使每个 chunker 自带可序列化的配置 schema，支持按 KB 持久化与重建。

| 成员 | 类型 | 说明 |
|------|------|------|
| `chunk` | `async (sections: list[Section]) -> list[Chunk]` | 将 Section 列表切分为 Chunk 列表 |
| `chunker_type` | `ClassVar[str]` | 类属性，chunker 的唯一类型标识（如 `"approx_token"`），用于配置持久化与反序列化 |
| `Parameters` | `ClassVar[type[BaseModel]]` | 类属性，内嵌的 pydantic schema，声明该 chunker 的构造参数（字段名 + 类型 + 默认值），驱动配置校验与重建 |

**schema 驱动机制**：每个 chunker 通过 `Parameters` 声明自己的可配置参数，`ChunkerConfig`（`type` + `parameters`）可被序列化存入 KB 元数据。索引时按记录的 `ChunkerConfig` 重建对应 chunker，实现"配置随文档走"——不同文档可用不同 chunker/参数，且跨进程可复现。

#### VectorStoreBase（向量库基类）

| 方法 | 签名 | 说明 |
|------|------|------|
| `create_collection` | `async (name, dimensions) -> None` | 创建集合 |
| `delete_collection` | `async (name) -> None` | 删除集合 |
| `has_collection` | `async (name) -> bool` | 检查集合是否存在 |
| `insert` | `async (collection, records) -> None` | 插入记录 |
| `delete` | `async (collection, document_id) -> None` | 按文档ID删除 |
| `search` | `async (collection, query_vector, top_k, metadata_filter) -> list[VectorSearchResult]` | 相似度搜索 |
| `list_documents` | `async (collection, metadata_filter) -> list[DocumentSummary]` | 列出文档 |

### 2.3 使用示例

```python
from agentscope.rag import (
    TextParser, ApproxTokenChunker, KnowledgeBase, QdrantStore,
)
from agentscope.embedding import DashScopeEmbeddingModel
from agentscope.credential import DashScopeCredential

# 1. 组装组件
parser = TextParser()
chunker = ApproxTokenChunker(chunk_size=256, overlap=32)
embedding = DashScopeEmbeddingModel(
    credential=DashScopeCredential(api_key="sk-..."),
    model="text-embedding-v4", dimensions=1024,
)
store = QdrantStore(location=":memory:")

# 2. 创建知识库句柄
async with store:
    kb = KnowledgeBase(
        name="my-kb",
        description="公司手册和文档",
        embedding_model=embedding,
        vector_store=store,
        collection="my-collection",
    )

    # 3. 索引文档
    sections = await parser.parse(file=b"# Hello\nWorld", filename="test.md")
    chunks = await chunker.chunk(sections)
    doc_id = await kb.insert_document(chunks, document_metadata={"filename": "test.md"})

    # 4. 检索
    results = await kb.search(queries=["Hello"], top_k=3)
```

## 三、设计原理

### 3.1 架构设计

AgentScope RAG 采用**分层解耦 + 策略模式**的架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                     服务层 (Service Layer)                       │
│                                                                 │
│  ┌─────────────────┐  ┌──────────────┐  ┌──────────────────┐   │
│  │ KnowledgeBase   │  │ IndexWorker  │  │ BlobStore        │   │
│  │ ManagerBase     │  │ (消息总线驱动)│  │ (Local / S3)     │   │
│  │                 │  │              │  │                  │   │
│  │ · CRUD 知识库   │  │ · 消费索引任务│  │ · 存储原始文件   │   │
│  │ · 解析 embedding│  │ · 并发索引   │  │ · 支持本地/S3    │   │
│  │ · 隔离策略      │  │ · 分布式部署 │  │                  │   │
│  └─────────────────┘  └──────────────┘  └──────────────────┘   │
├─────────────────────────────────────────────────────────────────┤
│                     核心层 (Core Layer)                          │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │

│  └──────────────────────────────────────────────────────────┘   │
├─────────────────────────────────────────────────────────────────┤
│                     流水线层 (Pipeline Layer)                     │
│                                                                 │
│  ┌──────────┐   ┌──────────────┐   ┌────────────────────┐      │
│  │ Parser   │──▶│   Chunker    │──▶│  EmbeddingModel    │      │
│  │          │   │              │   │                    │      │
│  │ Text     │   │ ApproxToken  │   │ DashScopeEmbedding │      │
│  │ PDF      │   │ Chunker      │   │ (可扩展)           │      │
│  │ PPT      │   │ (可扩展)     │   │                    │      │

│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │              VectorStore (向量库抽象)                      │   │
│  │  QdrantStore (内存/本地/远程)  ← 可扩展 Chroma/Milvus等  │   │
│  └──────────────────────────────────────────────────────────┘   │
├─────────────────────────────────────────────────────────────────┤
│                     集成层 (Integration Layer)                    │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │              RAGMiddleware (中间件集成)                    │   │
│  │  static 模式: on_reply 缓存输入 → on_reasoning 自动注入  │   │
│  │  agentic 模式: list_tools 暴露 search_knowledge 工具     │   │
│  └──────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| Section 与 Chunk 分离 | 两个独立数据类 | Section 是自然边界（不可跨），Chunk 是策略边界（可配置大小） |
| Chunk 不携带 embedding | VectorRecord 包装 | 保持 Chunk 语义稳定，embedding 是入库时的临时产物 |
| Chunk 不携带 score | VectorSearchResult 包装 | 同上，检索分数是查询时的临时产物 |
| metadata_filter 强制覆盖 | insert 时覆盖同名 key | 深度防御：防止恶意/buggy parser 让记录逃逸到其他租户 |
| collection 懒创建 | ensure_collection 幂等 | 新部署无需显式 setup，首次操作自动创建 |
| 近似 token 计数 | `len(text.encode("utf-8")) // 4` | 避免 tokenizer 依赖，数量级正确 |

## 四、实现原理与流程

### 4.1 整体架构（索引 + 检索流程）

```
=== 索引流程 ===

  文件 bytes ──▶ Parser.parse() ──▶ Section[]
                                      │
                                      ▼
                               Chunker.chunk()
                                      │
                                      ▼
                                   Chunk[]
                                      │
                    ┌─────────────────┤
                    │                 │
                    ▼                 ▼
         EmbeddingModel(chunks)   metadata 合并
                    │            (document_metadata
                    ▼             + chunk.metadata
             response.embeddings   + metadata_filter)
                    │
                    ▼
              VectorRecord[] ──▶ VectorStore.insert()


=== 检索流程 ===

  query string ──▶ EmbeddingModel([query]) ──▶ query_vector
                                                   │
                                                   ▼
                                          VectorStore.search()
                                                   │
                                                   ▼
                                         VectorSearchResult[]
                                                   │
                                          ┌────────┤
                                          │        │
                                          ▼        ▼
                                     去重       排序截断
                                  (doc_id,     (score desc,
                                   chunk_index)  top_k)
                                          │
                                          ▼
                                    最终结果列表
```

### 4.2 核心类实现

#### 4.2.1 Parser 实现

**TextParser** (`src/agentscope/rag/_parser/_text.py`)

```python
class TextParser(ParserBase):
    supported_media_types = [
        "text/plain", "text/markdown", "text/csv", "text/html",
        "text/x-rst", "application/json", "application/xml",
        "application/x-yaml",
    ]

    async def parse(self, file: bytes | str, filename: str) -> list[Section]:
        # 三种输入形式：
        # - bytes: 直接 decode
        # - str 且是文件路径: 读取文件后 decode
        # - str 且不是文件路径: 当作已解码文本直接使用
        if isinstance(file, str):
            if os.path.isfile(file):
                with open(file, "rb") as fp:
                    raw = fp.read()
                text = raw.decode(self.encoding)
            else:
                text = file
        else:
            text = file.decode(self.encoding)

        return [Section(content=TextBlock(text=text), source=filename, metadata={})]
```

**关键特点**：
- 整文件作为一个 Section，不做内部切分
- 支持 bytes / 文件路径 / 预解码文本三种输入
- 重写 `supported_extensions()` 避免 `text/plain` 解析出 `.bat`/`.c` 等无关扩展名

**PDFParser** (`src/agentscope/rag/_parser/_pdf.py`)

```python
class PDFParser(ParserBase):
    supported_media_types = ["application/pdf"]

    async def parse(self, file: bytes | str, filename: str) -> list[Section]:
        # 每页一个 Section，metadata 携带 page 页码（从 1 开始）
        reader = PdfReader(io.BytesIO(file))
        sections = []
        for page_idx, page in enumerate(reader.pages, start=1):
            text = page.extract_text() or ""
            sections.append(Section(
                content=TextBlock(text=text),
                source=filename,
                metadata={"page": page_idx},
            ))
        return sections
```

class ImageParser(ParserBase):

    async def parse(self, file: bytes | str, filename: str) -> list[Section]:

#### 4.2.2 Chunker 实现

**ApproxTokenChunker** (`src/agentscope/rag/_chunker/_approx_token_chunker.py`)

#### 4.2.3 KnowledgeBase 实现

```python
class KnowledgeBase:
    """运行时句柄 —— 绑定 embedding + store + collection"""

    async def search(self, queries, top_k=5, score_threshold=None):
        # 1. 过滤不可用查询（非多模态模型丢弃 DataBlock）
        if not self._embedding_model.supports_multimodal:
            queries = [q for q in queries if not isinstance(q, DataBlock)]

        # 2. 批量嵌入（一次 API 调用）
        await self.ensure_collection()
        response = await self._embedding_model(queries)

        # 3. 并发检索（每个 query vector 独立搜索）
        results_per_query = await asyncio.gather(*(
            self._vector_store.search(collection=self._collection, query_vector=v, ...)
            for v in response.embeddings
        ))

        # 4. 去重（按 document_id + chunk_index）+ 排序 + 截断
        best = {}
        for results in results_per_query:
            for result in results:
                key = (result.document_id, result.chunk.chunk_index)
                if key not in best or result.score > best[key].score:
                    best[key] = result
        return sorted(best.values(), key=lambda r: r.score, reverse=True)[:top_k]

    async def insert_document(self, chunks, document_id=None, document_metadata=None):
        # metadata 合并优先级（高→低）：
        # 1. metadata_filter（安全边界，强制覆盖）
        # 2. chunk.metadata（parser 提供）
        # 3. document_metadata（文档级字段）
        for chunk in chunks:
            chunk.metadata = {
                **(document_metadata or {}),
                **chunk.metadata,
                **(self._metadata_filter or {}),
            }
        # 批量嵌入 + 构建 VectorRecord + 插入
        response = await self._embedding_model([c.content for c in chunks])
        records = [VectorRecord(vector=v, document_id=document_id, chunk=c)
                   for v, c in zip(response.embeddings, chunks)]
        await self._vector_store.insert(self._collection, records)
```

**设计要点**：
- **同步包装**：MilvusClient 是同步 API，所有操作通过 `asyncio.to_thread()` 转为异步
- **本地检测**：`_is_local_db_uri()` 检测 `.db` 扩展名判断是否使用 Milvus Lite
- **资源释放**：`_release_lite_server()` 在 close 时释放嵌入式服务器

> **v2.0.4.post1 增强（#2089）：COSINE 距离语义适配**。
> `MilvusLiteStore._extract_score()` 负责把 Milvus 返回的 `distance` 转成 `VectorSearchResult.score`。milvus-lite **3.1.0 起改变了 COSINE 的语义**：`distance` 字段此时**直接就是余弦相似度**（1.0 = 完全相同向量），旧实现里 `score = 1.0 - distance` 的转换不再需要、且会算错。
> 修复后 `_extract_score` 直接 `return float(hit["distance"])`（优先 `distance`，回退 `score`），不再做任何 1.0 减运算。
>
> **设计动机**：向量库的"距离"在不同 metric / 版本下语义不统一——L2 是越小越相似，COSINE / IP 是越大越相似（1.0 最相似）。milvus-lite 在 3.1.0 把 COSINE 的 `distance` 从"距离"改"相似度"，属于**底层库版本语义漂移**，上层必须跟随修正，否则检索排序（按 `score` 降序）会完全反掉。
>
> **替代方案 / trade-off**：*替代* 在应用层统一归一化（无论底层如何都做 `1.0 - distance`）。代价是必须精确感知每个版本行为，易错。AgentScope 选**跟随官方 3.1.0 语义、直接读 distance**，并在 `_extract_score` 注释固化该约定，降低后续维护者的认知负担。
>
> **⚠️ 面试考点**：COSINE 与 L2 的"相似度方向"有何不同？答：COSINE / IP 越大越相似（1.0 最相似），L2 越小越相似；向量库升级时这类语义变更极易引发静默的检索质量回退，必须回归测试。

### 5.1 基础使用：库模式索引与检索

```python
# examples/rag/index_and_search.py
import asyncio
from agentscope.rag import TextParser, ApproxTokenChunker, KnowledgeBase, QdrantStore
from agentscope.embedding import DashScopeEmbeddingModel
from agentscope.credential import DashScopeCredential

async def main():
    embedding = DashScopeEmbeddingModel(
        credential=DashScopeCredential(api_key="sk-..."),
        model="text-embedding-v4", dimensions=1024,
    )
    parser = TextParser()
    chunker = ApproxTokenChunker(chunk_size=256, overlap=32)
    store = QdrantStore(location=":memory:")

    async with store:
        kb = KnowledgeBase(
            name="demo-kb",
            description="A toy corpus.",
            embedding_model=embedding,
            vector_store=store,
            collection="demo-kb",
        )
        # 索引
        sections = await parser.parse(file=b"# Cats\nCats are cute.", filename="cats.md")
        chunks = await chunker.chunk(sections)
        doc_id = await kb.insert_document(chunks, document_metadata={"filename": "cats.md"})

        # 检索
        results = await kb.search(queries=["When do cats sleep?"], top_k=3)
        for r in results:
            print(r.score, r.chunk.content.text[:80])

asyncio.run(main())
```

#### Q2: RAG 的完整流程是什么？索引阶段和检索生成阶段分别做什么？（腾讯高频）

**参考答案**：
> **RAG 完整流程**：
> ```
> 1. 索引阶段（离线）
>    文档加载 → 解析（如 PDF 用 OCR）→ 分块 → Embedding 向量化 → 存入向量数据库
>
> 2. 检索生成阶段（在线）
>    用户 Query → 预处理（如改写）→ 向量检索 + BM25 关键词检索 → RRF 融合排序 
>    → Re-rank 精排 → 拼接上下文 → 喂给 LLM 生成答案
> ```
>
> **索引阶段详解**：
> 1. **文档加载**：从各种来源加载文档（PDF、Word、网页等）
> 2. **解析**：将文档转为纯文本（PDF 用 OCR，Word 用解析器）
> 3. **分块**：将长文本切分为小块（chunk_size=500-1000，overlap=100-200）
> 4. **Embedding**：使用 Embedding 模型将文本块转为向量
> 5. **存储**：将向量和原文存入向量数据库（Milvus、Chroma、Qdrant）
>
> **检索生成阶段详解**：
> 1. **Query 预处理**：Query 改写、扩展、多路查询
> 2. **向量检索**：使用 Embedding 模型将 Query 转为向量，进行相似度检索
> 3. **关键词检索**：使用 BM25 进行关键词匹配
> 4. **融合排序**：使用 RRF（Reciprocal Rank Fusion）融合两路结果
> 5. **Re-rank**：使用 Cross-Encoder 精排（Top-40 → Top-3）
> 6. **生成**：将检索结果拼接为上下文，喂给 LLM 生成答案
>
> **2026 年趋势**：生产级 RAG 召回率可达 89% 左右

**追问**：
- 为什么需要两路检索（向量 + BM25）？→ 向量擅长语义匹配，BM25 擅长精确匹配
- 为什么需要 Re-rank？→ 向量检索（Bi-Encoder）无法捕捉细粒度交互
- 如何评估 RAG 效果？→ Recall@K、Precision@K、F1

#### Q3: BM25 是什么？和 TF-IDF 有什么区别？（阿里高频）

**参考答案**：
> **BM25（Best Matching 25）**：ElasticSearch 7.0 后的默认算法，工业级关键词检索基石
>
> **BM25 vs TF-IDF 对比**：
>
> | 维度 | TF-IDF | BM25 |
> |------|--------|------|
> | **核心思想** | 词频 × 逆文档频率 | 概率模型，考虑文档长度 |
> | **词频处理** | 线性增长 | 饱和函数（对数） |
> | **文档长度** | 未考虑 | 考虑（长度归一化） |
> | **参数** | 无 | k1（词频饱和）、b（长度归一化） |
> | **效果** | 一般 | 更好 |
>
> **BM25 核心公式**：
> ```
> score(D, Q) = Σ IDF(qi) × (f(qi, D) × (k1 + 1)) / (f(qi, D) + k1 × (1 - b + b × |D| / avgdl))
>
> 其中：
> - f(qi, D)：词 qi 在文档 D 中的词频
> - |D|：文档 D 的长度
> - avgdl：平均文档长度
> - k1：词频饱和参数（通常 1.2-2.0）
> - b：长度归一化参数（通常 0.75）
> ```
>
> **BM25 解决了 TF-IDF 的什么问题？**
> 1. **词频线性增长**：TF-IDF 中词频线性增长，BM25 使用饱和函数
> 2. **文档长度偏差**：TF-IDF 未考虑文档长度，BM25 进行长度归一化
>
> **2026 年趋势**：BM25 仍是工业级关键词检索的核心组件

**追问**：
- BM25 的参数如何调优？→ k1=1.2-2.0，b=0.75
- BM25 和向量检索如何融合？→ RRF（Reciprocal Rank Fusion）
- BM25 的缺点是什么？→ 不理解语义，只能字面匹配

**面试加分点**：
- 提到 BM25 vs TF-IDF 的对比
- 提到 BM25 核心公式
- 提到 BM25 解决的问题（词频饱和、长度归一化）

> |------|------|------|------|---------|
> | **固定大小** | 按字符数切分（如 500 字符） | 简单 | 可能切断语义 | 快速原型 |
> | **递归切分** | 按段落 → 句子 → 字符递归切分 | 保留语义 | 复杂 | 通用场景 |
> | **语义切分** | 按语义相似度切分 | 语义完整 | 需要 Embedding | 高质量场景 |
> | **结构化切分** | 按文档结构（标题、章节）切分 | 结构完整 | 需要解析 | 结构化文档 |
>
> **chunk_size 和 overlap 如何选择？**
>
> | 参数 | 推荐值 | 说明 |
> |------|--------|------|
> | **chunk_size** | 500-1000 字符 | 太小丢失上下文，太大降低精度 |
> | **overlap** | 100-200 字符（10%-20%） | 保证切片间上下文连贯 |
>
> **调优方法**：
> 1. **建立离线评测集**：准备 100-1000 个 QA 对
> 2. **调整参数**：chunk_size ∈ {300, 500, 700, 1000}，overlap ∈ {50, 100, 150, 200}
> 3. **监控指标**：Recall@K、Precision@K、F1
> 4. **选择最优**：F1 最高的参数组合
>
> **2026 年趋势**：递归切分 + 语义切分成为主流

**追问**：

- chunk_size 太大怎么办？→ 降低 chunk_size，增加 overlap
- chunk_size 太小怎么办？→ 增加 chunk_size，减少 overlap

#### Q6: 混合检索（Hybrid Search）是什么？如何融合向量和关键词检索结果？（腾讯高频）

**参考答案**：
> **混合检索（Hybrid Search）**：同时使用向量检索和关键词检索，融合两路结果
>
> **为什么需要混合检索？**
>
> | 检索方式 | 擅长 | 不擅长 |
> |---------|------|--------|
> | **向量检索** | 语义匹配（"退订" → "取消订阅"） | 精确匹配（"Error 503"） |
> | **关键词检索（BM25）** | 精确匹配（"Error 503"） | 语义匹配（"退订" → "取消订阅"） |
>
> **融合方法**：
>
> | 方法 | 说明 | 优点 | 缺点 |
> |------|------|------|------|
> | **分数加权** | hybrid_score = α × vector_score + (1-α) × bm25_score | 简单 | 量纲不一致 |
> | **RRF（Reciprocal Rank Fusion）** | RRF_score = Σ 1/(k + rank_i) | 避免量纲问题 | 不考虑分数 |
> | **学习排序** | 训练排序模型融合两路结果 | 效果最好 | 需要训练数据 |
>
> **RRF 公式**：
> ```
> RRF_score(D) = Σ(i=1 to n) 1 / (k + rank_i(D))
>
> 其中：
> - rank_i(D)：文档 D 在第 i 路检索中的排名
> - k：常数（通常 60）
> ```
>
> **比例经验**：
> - 通用场景：向量 60% : BM25 40%
> - 客服场景（口语化问题）：BM25 更重要
>
> **2026 年趋势**：RRF 成为混合检索的标准方法

**追问**：
- 为什么 RRF 比分数加权好？→ 避免量纲不一致问题
- 如何确定 α 值？→ A/B 测试，选择 Recall@K 最高的 α
- 混合检索的缺点是什么？→ 延迟增加（需要两路检索）

**面试加分点**：
- 提到混合检索的必要性
- 提到 3 种融合方法（分数加权、RRF、学习排序）
- 提到 RRF 公式
- 提到比例经验（向量 60% : BM25 40%）

### 7.3 高级话题题（区分度最高）

#### Q7: 向量数据库的索引算法有哪些？HNSW 和 IVF 有什么区别？（阿里高频）

**参考答案**：
> **向量数据库索引算法**：
>
> | 算法 | 核心思想 | 优点 | 缺点 | 适用场景 |
> |------|---------|------|------|---------|
> | **HNSW** | 分层导航小世界图 | 召回率高、延迟低 | 内存占用大 | 高质量场景 |
> | **IVF** | 倒排文件索引 | 内存占用小 | 召回率较低 | 大规模数据 |
> | **IVF-PQ** | IVF + 乘积量化 | 内存压缩 10-20x | 召回率较低 | 超大规模数据 |
>
> **HNSW（Hierarchical Navigable Small World）**：
> ```
> 核心思想：分层图结构，从顶层粗搜索逐层细化
>
> 参数：
> - M：邻居数（通常 16-64）
> - efConstruction：构建范围（通常 100-500）
> - efSearch：查询范围（通常 50-200）
>
> 影响：
> - M 越大：召回率越高，内存占用越大
> - efConstruction 越大：构建时间越长，图质量越好
> - efSearch 越大：查询时间越长，召回率越高
> ```
>
> **IVF（Inverted File Index）**：
> ```
> 核心思想：先聚类再搜索
>
> 参数：
> - nlist：簇数（通常 100-10000）
> - nprobe：探查数（通常 1-100）
>
> 影响：
> - nlist 越大：聚类越细，构建时间越长
> - nprobe 越大：召回率越高，查询时间越长
> ```
>
> **向量数据库选型**：
>
> | 数据库 | 索引算法 | 优点 | 缺点 | 适用场景 |
> |--------|---------|------|------|---------|
> | **Milvus** | HNSW / IVF-PQ / 混合 | 生态最全，支持分布式 | 运维复杂 | 企业级 |
> | **Qdrant** | HNSW | 性能好，Rust 实现 | 生态不丰富 | 通用场景 |
> | **Weaviate** | HNSW + 混合检索 | 内置 BM25 | 文档偏少 | 混合检索 |
> | **Chroma** | HNSW（近似） | 轻量级，Python 优先 | 不适合大规模 | 快速原型 |
> | **FAISS** | IVF-PQ / HNSW | 算法最全，性能最优 | 只是库不是数据库 | 研究 |
>
> **选型建议**：
> - 10 万以下：Chroma
> - 10 万-千万：Qdrant 或 Milvus 单机
> - 千万以上：Milvus 分布式
>
> **2026 年趋势**：HNSW 成为高质量场景的首选，IVF-PQ 成为超大规模数据的首选

**追问**：
- HNSW 的内存占用如何优化？→ 减小 M、efConstruction
- IVF 的召回率如何提升？→ 增加 nprobe
- 如何选择向量数据库？→ 根据数据规模、质量要求、运维能力

#### Q8: Re-rank 是什么？为什么需要这一层？（腾讯高频）

**参考答案**：
> **Re-rank（重排序）**：对检索结果进行精排，提升最终结果质量
>
> **为什么需要 Re-rank？**
>
> | 阶段 | 方法 | 优点 | 缺点 |
> |------|------|------|------|
> | **粗排** | Bi-Encoder（向量检索） | 快 | 无法捕捉细粒度交互 |
> | **精排** | Cross-Encoder（Re-rank） | 效果好 | 慢 |
>
> **Bi-Encoder vs Cross-Encoder**：
>
> | 维度 | Bi-Encoder | Cross-Encoder |
> |------|-----------|---------------|
> | **编码方式** | Query 和 Doc 独立编码 | Query 和 Doc 拼接后一起编码 |
> | **交互** | 无交互 | 充分交互 |
> | **速度** | 快（可预计算 Doc 向量） | 慢（每次都要重新编码） |
> | **效果** | 一般 | 好 |
> | **适用场景** | 粗排（Top-40） | 精排（Top-3） |
>
> **Re-rank 能识别什么？**
> 1. **否定词**：如"不是"、"没有"
> 2. **时间限定**：如"2026 年"、"昨天"
> 3. **条件限定**：如"在 Linux 下"、"用 Python"
>
> **工业标准**：
> ```
> 向量检索粗排（Top-40）→ Cross-Encoder 精排（Top-3）
> ```
>
> **Re-rank 模型选型**：
>
> | 模型 | 语言 | 优点 | 缺点 | 适用场景 |
> |------|------|------|------|---------|
> | **Cohere Rerank** | 多语言 | 效果好 | 贵 | 高质量场景 |
> | **BGE-Reranker** | 中英文 | 开源免费 | 效果一般 | 通用场景 |
> | **Cross-Encoder** | 多语言 | 开源免费 | 效果一般 | 通用场景 |
>
> **2026 年趋势**：Re-rank 成为生产级 RAG 的标配

**追问**：

- Re-rank 的缺点是什么？→ 延迟增加

#### Q9: RAG 的幻觉问题如何解决？Self-RAG 是什么？（阿里高频）

**参考答案**：
> **RAG 幻觉问题**：
>
> | 幻觉类型 | 说明 | 原因 |
> |---------|------|------|
> | **文本幻觉** | 生成的文本与检索结果不一致 | LLM 不忠实于检索结果 |
> | **功能幻觉** | 调用了不存在的工具或 API | LLM 不知道工具的限制 |
>
> **解决幻觉的方法**：
>
> | 方法 | 说明 | 优点 | 缺点 |
> |------|------|------|------|
> | **引用验证** | 检查生成的文本是否有引用依据 | 简单 | 需要额外的验证模型 |
> | **输出自校验** | LLM 生成后自我检查 | 简单 | 增加延迟 |
> | **Self-RAG** | 模型自我反思和修正 | 效果好 | 需要训练 |
> | **CRAG（Corrective RAG）** | 纠正性 RAG | 效果好 | 复杂 |
>
> **Self-RAG 核心思想**：
> ```
> 1. 生成答案
> 2. 自我评估：答案是否有检索依据？
> 3. 如果有依据：输出答案
> 4. 如果无依据：重新检索或修正答案
> ```
>
> **CRAG（Corrective RAG）核心思想**：
> ```
> 1. 检索文档
> 2. 评估检索质量：文档是否相关？
> 3. 如果相关：生成答案
> 4. 如果不相关：重新检索或使用其他知识源
> ```
>
> **2026 年趋势**：Self-RAG 和 CRAG 成为解决幻觉的主流方法

**追问**：
- 如何评估幻觉？→ 人工标注、自动化评估（如 RAGAS）
- Self-RAG 和 CRAG 的区别？→ Self-RAG 自我反思，CRAG 纠正性检索
- 如何减少幻觉？→ 引用验证、输出自校验、Self-RAG

## 八、最佳实践

### 8.1 开发建议

| 建议 | 说明 |
|------|------|
| 优先使用 KnowledgeBase 句柄 | 不要直接操作 VectorStore，KnowledgeBase 封装了嵌入 + 去重 + 懒创建 |
| 选择合适的 chunk_size | 太小丢失上下文，太大降低精度。推荐 256-512 近似 token |
| 设置合理的 overlap | 推荐 chunk_size 的 10%-20%，保证切片间上下文连贯 |
| 使用 metadata_filter 做隔离 | 多租户场景必须使用，不要依赖应用层过滤 |
| static 模式适合简单场景 | 复杂推理场景用 agentic 模式让模型决定何时检索 |

### 8.2 性能优化

| 优化点 | 方法 |
|--------|------|
| 批量嵌入 | `insert_document` 一次调用嵌入所有 chunk，减少 API 调用 |
| 并发检索 | `search` 内部用 `asyncio.gather` 并发搜索多个 query vector |
| 跨 KB 并发 | `_search_across` 并发搜索多个 KnowledgeBase |
| collection 懒创建 | 首次操作后 memoize，后续操作跳过 round-trip |
| 进程池解析 | IndexWorker 支持 `ProcessPoolExecutor` 处理 CPU 密集的 PDF/PPT 解析 |
| Qdrant scroll 优化 | `list_documents` 使用 `with_vectors=False` 减少数据传输 |

### 8.3 安全建议

| 建议 | 说明 |
|------|------|
| 必须使用 metadata_filter | 多租户场景下防止数据逃逸 |
| 不要信任 parser 的 metadata | metadata_filter 会覆盖 parser 提供的同名字段 |
| search 结果可能跨 KB 不可比 | 不同 embedding 模型的分数不严格可比，混合部署考虑 RRF 融合 |
| 权限检查 | `_SearchKnowledgeTool` 默认 ALLOW（只读操作），但应确认业务层权限 |

## 九、总结

> **一句话总结**：AgentScope RAG 是一个模块化、可插拔的检索增强生成系统，通过 Parser → Chunker → Embedding → VectorStore 流水线实现文档索引，通过 KnowledgeBase 句柄统一运行时操作，通过 RAGMiddleware（static/agentic 双模式）无缝集成到 Agent 推理循环，并原生支持多模态、多租户深度防御和分布式索引部署。
