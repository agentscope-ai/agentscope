# AgentScope API 源码驱动学习总纲与 AI 执行协议

> 用途：这是一份给 AI 使用的执行说明书，用于持续、分批、可验证地分析 AgentScope 的 API、Web UI、Agent Runtime、Plan、多 Agent、RAG、Workspace、Schedule 等完整源码链路，并沉淀成面试材料。

---

## 一、目标

本目录用于沉淀一套完整的 AgentScope 源码学习资料库：

```text
产品流程
  +
前端状态机
  +
后端 API
  +
Service / Manager / MessageBus
  +
Agent Runtime / Tool / Middleware
  +
测试证据
  +
面试沉淀
```

最终目标不是只解释“接口怎么调用”，而是让学习者能够讲清楚：

```text
一个用户动作如何穿过 Web UI、HTTP API、Service、MessageBus、Agent Runtime，
再通过事件流回到 UI，并且在异常、取消、刷新、HITL、多 Agent 协作场景下保持一致。
```

## 三、AI 执行原则

AI 执行源码分析时必须遵守以下原则。

### 3.1 先搜索，再判断

不得凭印象编造调用链。每次分析必须先搜索源码：

```text
1. Router / API 文件
2. 前端 api 封装
3. 前端 hook / page / component
4. Service / Manager / Middleware
5. Storage / MessageBus / Workspace / Toolkit
6. Agent / Tool / Event / State
7. tests 中的对应测试
```

推荐搜索方式：

```text
rg -n "接口路径|函数名|类名|事件名|工具名" src examples tests
```

### 3.2 每次只分析一个单位

优先单位：

```text
一个 HTTP endpoint
一个工具接口
一个专题主链路
```

不要一次性分析全部接口。每次产出一个文件，文件完成后再进入下一个。

### 3.3 必须结合前后端

除非该接口确实没有前端入口，否则每份分析必须包含：

```text
前端入口
前端状态变化
后端调用链
事件回流
页面刷新/重连/异常处理
```

### 3.4 必须有测试证据

每份分析都要搜索 `tests/`：

```text
tests/*_test.py
tests/service_*_test.py
tests/toolkit_*_test.py
tests/task_tool_test.py
```

如果没有找到测试，要明确写：

```text
未找到直接测试，建议补充测试：
...
```

### 3.5 面试沉淀必须跟随每个文件

不要只在总面试题库里写面试内容。每个接口/专题文件必须包含：

```text
## 面试沉淀
```

这样学习者读一个文件，就能同时获得源码理解和面试表达。

## 四、单接口分析模板

每个 `interfaces/` 文件使用以下结构。

```text
# 接口名：METHOD /path

## 1. 结论先行

用 3-5 句话说明这个接口解决什么问题、在产品流程中的位置、最值得学习的设计点。

## 2. 用户场景

说明用户在 Web UI 上做了什么动作，为什么会触发这个接口。

## 3. 前端链路

列出：
- 页面文件
- 组件文件
- hook
- api 封装
- 关键 React state
- loading / error / optimistic update / phase 状态

格式：

```text
用户动作
  ↓
Component
  ↓
Hook
  ↓
api.xxx
  ↓
HTTP request
```

## 4. HTTP 设计

说明：
- method
- path
- query
- body
- response
- status code
- 幂等性
- 404 / 409 / 202 / 204 等语义

## 5. 后端调用链

格式：

```text
Router
  ↓
Service / Manager
  ↓
Storage / MessageBus / Workspace / Toolkit
  ↓
Agent / Tool / Middleware
```

必须写源码文件路径。

## 6. 数据模型

说明相关 Pydantic / TS 类型：
- Request
- Response
- Record
- State
- Event
- ToolCall / ToolResult

## 7. 状态变化

分别说明：
- React state 变化
- Storage 变化
- AgentState 变化
- MessageBus queue/log/pubsub/registry/lock 变化
- Msg / AgentEvent 变化

## 8. 事件回流

如果有 SSE / CustomEvent / ReplyEvent，需要说明：
- 谁发布事件
- 发布到哪个 key/channel
- 前端谁接收
- 如何影响 UI

## 9. 并发、异常与一致性

重点说明：
- 是否有锁
- 是否允许重复点击
- 是否有 no-op 语义
- 是否有 retry / timeout
- 是否有 finally 清理
- 是否使用 asyncio.shield
- 进程崩溃或前端重连后如何恢复

## 10. 测试证据

列出相关测试文件，并总结测试覆盖点。

如果没有测试，写建议补测点。

## 11. 设计权衡

回答：
- 为什么这样设计？
- 不这样设计会有什么问题？
- 和常见方案相比有什么 trade-off？

## 12. 面试沉淀

### 一句话回答

30 秒内讲清楚。

### 白板流程

用 ASCII 调用链画出来。

### 高频追问

列 5-8 个面试官可能追问的问题。

### 对比题

列 2-4 个对比问题，例如：
- 同步 API vs fire-and-forget
- Pub/Sub vs Replay Log
- Agent 配置态 vs Session 运行态

### 项目表达

把源码理解包装成项目经验表达。

## 13. 后续待深挖

列出还没完全确认的点。
```

## 十四、完成定义

一个接口或专题文件被认为“完成”，必须满足：

```text

6. 可以指出测试证据或测试缺口。
7. 可以直接拿“面试沉淀”章节复习面试。
```

如果只描述 API 参数，不算完成。

如果只描述后端源码，不算完成。

如果没有前端链路或没有说明“无前端入口”，不算完成。

如果没有面试沉淀，不算完成。

## 十五、分批执行策略与额度控制

全量分析不要一次性执行。推荐按“先核心、再扩展、最后补齐”的方式分批跑。

原因：

```text
1. 全量接口数量多，直接执行容易产出过厚、难审阅的文档。
2. 不同模块复杂度差异很大，Chat / Plan / 多 Agent 值得深挖，CRUD 接口适合简析。
3. 分批执行可以先确认文档风格、深度、面试沉淀方式是否符合预期。
4. 可以控制 Plus / agentic 额度消耗，避免一次跑太多。
```
