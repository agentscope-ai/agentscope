# 专题五：多 Agent 与 Team 协作

> 本专题覆盖 AgentScope 的多 Agent 实现：team 不是"进程内 new 多个 Agent 对象"，而是把每个成员建模成独立的 agent/session。`TeamCreate`/`AgentCreate`/`TeamSay`/`AgentInvite`/`TeamDelete` 是注入到 Toolkit 的工具；`TeamSay` 经 MessageBus inbox + wakeup 做跨 session 通信；`SubagentHitlProjector` 把 worker 的 HITL 确认卡投影到 leader UI。前端用 `TeamSidebar` + URL 的 `:memberId` 在 leader/team 上下文中切换聚焦 session。

---

## 1. 这个专题解决什么问题

**产品问题**：一个复杂任务要拆给多个专精 Agent 并行做，由 leader 协调、收集汇报、产出最终答案；用户主要面对 leader，子 Agent 的 HITL 确认要能在 leader 页面完成。

**工程问题**：成员如何建模（独立 session 才能独立上下文/状态/消息流/可中断/可观察）？成员间如何通信（不能同步直调，要可持久、可恢复、可唤醒）？worker 的 HITL 怎么让 leader 看见并代为确认？

核心结论：**多 Agent 被做成可持久化、可恢复、可中断、可观察的产品能力——每个成员是独立 agent/session，team 是 session 级关系，通信走 MessageBus inbox + wakeup。**

## 2. 总体架构

```text
Leader Agent 调 TeamCreate
  → 创建 TeamRecord(session_id=leader.session_id, member_ids=[])
  → session.set_session_team_id(leader, team.id)
  → StateChangeMiddleware 推 team_updated → 前端 refetchSessions → TeamSidebar 出现

Leader 调 AgentCreate(name, desc, prompt)
  → 创建 worker AgentRecord(source="team") + worker SessionRecord（继承 leader 的 workspace/model/permission）
  → set_session_team_id(worker, team.id)；TeamMember(role="created")
  → 初始任务 HintBlock 入 worker inbox + enqueue_run_trigger(wake) 唤醒 worker

Leader 调 AgentInvite(target, prompt)
  → 借用已有 user-owned AgentRecord，不创建新的 AgentRecord
  → 创建 team-scoped borrowed SessionRecord，TeamMember(role="invited")
  → 复用被邀请 Agent 的 workspace/model 优先，权限上下文重新开始
  → 初始任务 HintBlock 入 borrowed session inbox + enqueue_run_trigger(wake)

任意成员调 TeamSay(content, to?)
  → 按 TeamRecord 构建 name→(session_id, agent_id) 通讯录
  → HintBlock 入目标 inbox + enqueue_run_trigger(wake) 唤醒目标

worker 产生 RequireUserConfirmEvent
  → SubagentHitlProjector.maybe_project → 投影到 leader（registry）+ 推 CustomEvent(subagent_require_user_confirm)
  → leader UI 显示 SubagentHitlCard
  → 用户在 leader 确认 → POST /chat/ 发到 leader → chat_router 用 resolve 找到 worker session → enqueue resume
```

## 4. 后端运行链路

### 4.1 Toolkit 按 session team 角色注入团队工具（`_service/_toolkit.py` L170–232）
- 读 `session_record.team_id` + `team.session_id` 判定 `team_role`：`leader` / `worker` / None（L186–192）。
- **worker** → 仅 `TeamSay(role="worker")`；
- **leader or 非 team** → `TeamCreate / AgentCreate / TeamSay(role="leader") / TeamDelete`，并按 `invitable_pool` 条件加 `AgentInvite`（L193–232）。
- 注意：门控依据是 **session 的 team 角色**，不是 `agent_record.source`（`_toolkit.py` L67–76 注释）——受邀（borrowed）agent 的 session 也要当 worker，尽管其 `AgentRecord.source='user'`。

### 4.2 TeamCreate（`_tool/_team_create.py`）
- 前置校验：session 必须存在、且 `session.team_id is None`（一个 session 只能领导一个 team，L98–112）；
- 创建 `TeamRecord(user_id, session_id=leader.session_id, data=TeamData(member_ids=[]))`，`upsert_team` + `set_session_team_id(leader, team.id)`（L114–128）。

### 4.3 AgentCreate（`_tool/_agent_create.py`）
- 前置：session 在 team 且是 leader（`team.session_id == self._session_id`，L328–340）；
- 团队内 name 唯一性（含 leader 名，拒绝 `@`，L389–435）；
- 创建 worker `AgentRecord(source="team")` + worker `SessionRecord`，**继承 leader 的 workspace_id / chat_model_config / fallback**，permission 经 `_merge_leader_permissions` 按模板 flag 合并（L445–510）；
- 加入 team roster（`role="created"`），初始任务 `HintBlock` 入 worker inbox + `enqueue_run_trigger(wake)` 唤醒（L512–558）。

### 4.4 AgentInvite（`_tool/_agent_invite.py`）

`AgentInvite` 和 `AgentCreate` 是多 Agent 里最值得区分的一组设计：

- `AgentCreate` 是 **创建新 worker**：生成新的 `AgentRecord(source="team")`，适合为当前 team 定制角色、system prompt、权限模板；
- `AgentInvite` 是 **借用已有 Agent**：复用一个用户已有的 `AgentRecord(source="user")`，只为这个 team 额外创建一个 team-scoped `SessionRecord`。

关键源码点：

- `InviteConfig` 在 `storage/_model/_agent.py` 中定义：`invitable=True` 必须有非空 `invite_description`，否则 Pydantic 校验失败（`InviteConfig._check_invitable_has_description`）；
- `get_toolkit` 只在可见 Agent 中存在 `invitable=True` 且 `invite_description` 非空时，给 leader 工具集注入 `AgentInvite`；
- `AgentInvite.__init__` 会把可邀请 Agent 快照转成 `target` enum，格式是 `"<name>@<agent_id[:8]>"`，并把 `invite_description` 写进工具描述，供 leader LLM 决策；
- `AgentInvite.__call__` 会重新从 storage 读取目标 Agent，二次确认仍然 invitable，避免“工具列表生成后用户关闭邀请”的竞态；
- 同一个 team 不能重复借用同一个 Agent：`existing_members` 中已有 `agent_id` 会拒绝；
- 借用成功后不会新建 AgentRecord，而是在目标 Agent 上新建一个 `SessionRecord`，并写入 `TeamMember(role="invited")`。

借用 session 的配置策略：

```text
如果被邀请 Agent 已有 primary session：
  borrowed workspace_id = primary.config.workspace_id
  borrowed chat_model_config = primary.config.chat_model_config or leader.config.chat_model_config
  borrowed fallback = primary.config.fallback_chat_model_config or leader.config.fallback

如果被邀请 Agent 没有 session：
  borrowed workspace_id = workspace_manager.assign_workspace_id(...)
  borrowed model = leader session 的 model config
```

权限策略是重点：

```text
AgentInvite 不继承 leader 的 PermissionContext。
AgentInvite 也不继承 invited agent 自己 primary session 的 PermissionContext。
borrowed session 使用新的 AgentState()，permission_context 和 tasks_context 都重新开始。
```

原因：

- leader 的权限规则和 working directories 绑定 leader workspace，受邀 Agent 可能使用自己的 workspace；
- 直接继承会把 leader 文件路径、allow/deny/ask 规则错误带到另一个运行环境；
- invited agent 自己 primary session 的用户确认，也不应该静默跨到 team-scoped 会话；
- 因此敏感工具在 borrowed session 中需要重新 HITL 确认。

初始任务投递：

```text
AgentInvite
  ↓
生成 system-reminder + <team-message from="leader">
  ↓
MessageBus.queue_push(MessageBusKeys.inbox(borrowed.id), HintBlock)
  ↓
enqueue_run_trigger(... borrowed.id, invited.id)
  ↓
borrowed session 被 WakeupDispatcher 唤醒运行
```

测试证据：

- `tests/service_team_tools_test.py::TestAgentDataInvitableValidator`：`invitable=True` 必须有描述，关闭邀请时可保留草稿描述；
- `TestAgentInviteSuccess`：借用成功不创建新 AgentRecord，borrowed session 与 primary session 不同，继承 primary workspace，fresh `PermissionContext`，初始 prompt 只进入 borrowed inbox；
- `TestAgentInviteRejections`：拒绝 malformed target、未知 handle、toggle-off 后 stale snapshot、非 leader、重复借用；
- `TestTeamSayInvitedRouting`：leader 用 `Monday@<handle>` 路由到 borrowed session，而不是 primary session；
- `TestTeamDeletePreservesInvited`：TeamDelete 只删除 borrowed session，保留 invited AgentRecord 和 primary session；
- `TestDeleteInvitedAgentReverseCascade`：删除被借用的 Agent 时，会从 team roster 中清理 stale invited entry。

面试表达：

```text
AgentInvite 不是创建子 Agent，而是把已有用户 Agent 借进 team。
它复用 AgentRecord，新建一个 team-scoped SessionRecord，因此被邀请 Agent 的主会话和团队会话互不污染。
workspace/model 优先继承被邀请 Agent 的主 session，但权限上下文故意重置，避免把 leader 的文件路径和确认规则带到另一个 workspace。
这让多 Agent 既能复用用户已有专长 Agent，又保持 session 级隔离和安全边界。
```

### 4.5 TeamSay（`_tool/_team_say.py`）
- 运行时从 storage 解析 team + 构建 `name → (session_id, agent_id)` 通讯录（leader + members，invited 显示 `<name>@<agent_id[:8]>` 防撞名，L205–249）；
- 把 `HintBlock`（`<team-message from=...>`）`queue_push` 到目标 `inbox(sid)` + `enqueue_run_trigger` 唤醒（L324–334）；
- `is_concurrency_safe=True, is_read_only=True`（L94–95）：读多写少、可并发。

### 4.6 TeamDelete（`_tool/_team_delete.py` + `SessionService.delete_team`）

Team 删除是 `AgentInvite` 生命周期设计的落点。

`TeamDelete` 自身只做 leader 前置校验，然后委托 `SessionService.delete_team`：

```text
TeamDelete
  ↓
校验当前 session 在 team 中且是 leader
  ↓
SessionService.delete_team(user_id, team.id)
```

`StorageBase.delete_team` 的契约明确区分成员角色：

```text
role == "created":
  delete_agent(worker_agent_id)
  → 删除该 team-spawned AgentRecord 及其 session

role == "invited":
  delete_session(borrowed_session_id)
  → 只删除 team-scoped borrowed session
  → invited AgentRecord 和其他 session 保留
```

这和产品语义一致：

- `AgentCreate` 生成的成员只属于当前 team，team 解散后应完全删除；
- `AgentInvite` 借来的成员原本属于用户，team 解散后只能移除借用关系，不能删除用户原 Agent。

### 4.7 SubagentHitlProjector（`_service/_projectors/_subagent_hitl.py`）
- `maybe_project`（L93–195）：仅 team session 且事件是 HITL 类；`team.session_id == session_record.id` 则跳过（leader 自身 HITL 直达客户端）；否则 upsert 到 leader 的 projection registry + 推 `CustomEvent(name=subagent_require_user_confirm)`；resume/ReplyEnd 时 delete + 推 `subagent_user_confirm_result`。
- `resolve`（L197–228）：确认结果 POST 到 leader 时，按 `reply_id` 在 leader 的 pending 里找到 worker session/agent，供 `chat_router` 路由。

### 4.8 前端 SSE 注入 HITL 卡（`_session.py` L737–776）
worker parked 后 leader 刷新时，replay-log 没有该卡，但 `SessionProjection.list(leader, SubagentHitlProjector.KIND)` 读取持久 registry，`_worker_still_asking` reconcile 注入。

## 6. 核心源码解读

### 6.1 为什么 team 绑在 Session 而非只绑 Agent？
同一用户 Agent 可在不同 session 领导不同 team（`_toolkit.py` 注释 / `AgentRecord.source` 不再作为门控）。team 是运行态关系，必须随 session 生命周期，而不是配置态。

### 6.2 为什么 worker 是独立 session？
每个子 Agent 需要自己的上下文、状态、消息流、运行锁、可中断性。独立 session 让 worker 的运行完全隔离又可被 leader 的 HITL 投影观察（`_agent_create.py` L445–510）。

### 6.3 为什么 TeamSay 走 inbox + wakeup 而非同步调用？
worker 可能在另一进程/未运行。`HintBlock` 入 inbox 持久化，`enqueue_run_trigger` 唤醒任意进程的 `WakeupDispatcher` 去 spawn run；下次 run 时 `InboxMiddleware` 自然 drain（见 `_chat.py` L499–531 wake-up 守卫注释）。

### 6.4 为什么 worker HITL 要投影到 leader？
用户只面对 leader。投影器把 worker 的 pending 确认卡镜像到 leader 的 projection registry，前端统一在 leader 页面渲染（`SubagentHitlProjector.KIND`），确认时后端按 `reply_id` resolve 回 worker（`_subagent_hitl.py` L197–228）。

### 6.5 前端为何用 URL `:memberId` 切换而非开新页面？
在同一个 team 上下文中切换"当前聚焦 session"，ChatPage 维护 leader 选择、TeamSidebar 维护成员导航、ChatViewport 只收 `effectiveSessionId`（`index.tsx` L119–120、`ChatViewport.tsx` L48）。

### 6.6 AgentInvite 和 AgentCreate 的核心区别

| 维度 | AgentCreate | AgentInvite |
|---|---|---|
| AgentRecord | 新建 `source="team"` | 复用已有 `source="user"` |
| SessionRecord | 新建 worker session | 新建 borrowed team-scoped session |
| system prompt | 由 SubAgentTemplate 生成 | 保留被邀请 Agent 原配置 |
| workspace | 继承 leader workspace | 优先使用被邀请 Agent primary session workspace |
| model config | 继承 leader | 优先用被邀请 Agent primary session，否则 fallback 到 leader |
| permission_context | 按模板与 leader 合并 | fresh PermissionContext，不继承 |
| tasks_context | 可由模板预置 | fresh TaskContext |
| 删除 team | 删除 AgentRecord + session | 只删 borrowed session，保留 AgentRecord |
| 适用场景 | 为当前任务定制 worker | 复用已有专长 Agent |

## 7. 边界情况

| 场景 | 行为 |
|---|---|
| leader 已领导一个 team 再 TeamCreate | 报错（一个 session 一个 team） |
| 同名成员 | AgentCreate 拒绝（含 leader 名、拒绝 `@`） |
| TeamSay 给不存在成员 | 报错并列出已知成员 |
| worker 报错/crash 未清卡 | reconcile-on-read 在 leader 重连时删 ghost |
| 用户确认 worker HITL | POST 到 leader，`resolve` 路由到 worker resume |
| team 删除 | `created` 成员删除 AgentRecord + session；`invited` 成员只删除 borrowed session，保留原 Agent |
| 被邀请 Agent 被删除 | 反向清理 team roster 中 stale invited entry |

## 9. 设计权衡

- **独立 session vs 进程内多 Agent**：可持久、可中断、可观察、可恢复。
- **team 绑 session vs 绑 agent**：运行态关系随 session 生命周期。
- **inbox + wakeup vs 同步调用**：解耦、可跨进程、可重连。
- **HITL 投影 vs 直接暴露 worker**：用户只面对 leader，体验统一。
- **AgentCreate vs AgentInvite**：前者定制新 worker，后者复用已有 Agent；复用带来专长和已有 workspace，但必须重置权限上下文避免跨 workspace 污染。

**待验证（重要）**：`tests/service_toolkit_test.py` 的 docstring（L14–16）仍描述"team tools are role-gated by `agent_record.source`"，但当前 `get_toolkit` 实现（L186–193）已改为按 **session 的 team 角色**（leader/worker）门控。该测试可能基于旧契约，需回归确认是否仍通过或已更新。建议下批核对测试体与实现的匹配。

## 10. 面试沉淀

### 一句话回答
AgentScope 的多 Agent 把每个成员建模成独立的 agent/session，team 是 session 级关系；成员间通信通过 TeamSay 把 HintBlock 投进目标 inbox 并 wakeup 唤醒，而不是同步调用；worker 的 HITL 确认卡经 SubagentHitlProjector 投影到 leader，用户在 leader 页面确认后后端按 reply_id 路由回 worker。整套设计可持久、可恢复、可中断、可观察。

### 白板流程
```text
TeamCreate → TeamRecord + set_session_team_id(leader)
AgentCreate → worker AgentRecord(source=team) + worker Session + 继承配置 + 唤醒
TeamSay → inbox(HintBlock) + enqueue_run_trigger(wake) → 目标唤醒
worker HITL → SubagentHitlProjector → leader projection registry + CustomEvent
leader 确认 → POST /chat(leader) → resolve(reply_id) → worker resume
```

### 高频追问
1. 为什么 team 绑 session 不绑 agent？——team 是运行态，随 session 生命周期。
2. 为什么 worker 是独立 session？——独立上下文/状态/锁/可中断/可观察。
3. 为什么 TeamSay 走 inbox + wakeup？——跨进程、可持久、可唤醒，而非同步直调。
4. leader 怎么知道 worker 的 HITL？——SubagentHitlProjector 投影 + registry 镜像。
5. 前端怎么切到 worker？——URL 第三段 `:memberId` 决定 ChatViewport 聚焦 session。
6. AgentInvite 和 AgentCreate 有什么区别？——AgentCreate 新建 team worker；AgentInvite 借用已有 AgentRecord，只新建 borrowed session。
7. AgentInvite 为什么不继承 leader 权限？——leader 权限规则和 working directories 绑定 leader workspace，跨到 invited workspace 有安全风险。

### 对比题
- 独立 session vs 进程内多 Agent：隔离 vs 共享。
- inbox + wakeup vs 同步 RPC：解耦 vs 紧耦合。
- HITL 投影 vs 暴露 worker：统一入口 vs 多页面。
- AgentCreate vs AgentInvite：定制新成员 vs 借用已有专长 Agent。

### 项目表达
"我们多 Agent 不是简单 new 几个 Agent，而是把每个成员做成独立 session——有独立上下文、运行锁、可中断。成员通信靠 TeamSay 把消息投进对方 inbox 再唤醒，完全异步解耦。最有意思的是子 Agent 的 HITL：worker 停在等确认时，投影器把确认卡镜像到 leader 的 registry，用户在 leader 页面确认，后端按 reply_id 路由回 worker resume。这让多 Agent 协作变成可持久、可恢复、可观察的产品能力。"
