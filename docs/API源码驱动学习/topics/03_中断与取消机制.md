# 专题三：Interrupt 与取消机制

> 本专题覆盖 `POST /sessions/{sid}/interrupt` 的两条路径：**运行中**（持有锁）→ `CancelDispatcher` 跨进程广播 cancel → 本地 `task.cancel()` → `Agent` 在 `CancelledError` 清理路径生成 interrupted tool result + `ReplyEndEvent(INTERRUPTED)`；**非运行中**（parked on HITL）→ enqueue `UserInterruptEvent` → `WakeupDispatcher` resume → agent 短路关闭 pending tool call。**关键设计：cancel 与 interrupt 分离、跨进程、幂等、状态一致。**

---

## 1. 这个专题解决什么问题

**产品问题**：用户要能 Stop 一个正在生成的回复；也要能取消一个停在"等用户确认"的 HITL 回复。两种场景状态语义不同，但 UI 上都是同一个 Stop 按钮。

**工程问题**：
- 运行中的 task 在另一个进程怎么办？（无法直杀本地 task）
- 取消要能生成干净的 interrupted 结果，而不是留半个 tool call；
- idle session 的 interrupt 必须是 no-op（不能误触发）；
- 前端 Stop 后若 SSE 终止事件丢失，UI 不能卡死。

---

## 2. 总体架构

```text
POST /sessions/{sid}/interrupt  (202 Accepted)
  → ChatService.interrupt(user_id, sid, agent_id)
       │
       ├─ is_locked(session_lock)?  YES (running)
       │     → publish(session_interrupt_channel, {session_id})
       │         → CancelDispatcher._interrupt_session(sid)
       │             → registry.get(sid).cancel()   # 仅取消 chat-run task
       │     → Agent: CancelledError
       │         → _close_unfinished_tool_calls (INTERRUPTED results)
       │         → ReplyEndEvent(INTERRUPTED)
       │
       └─ NO (not running / parked)
             → enqueue_run_trigger(kind=RESUME, inputs=UserInterruptEvent)
                 → WakeupDispatcher: is_locked? 若锁仍在→退避重排
                 → ChatService.run(input=UserInterruptEvent)
                     → Agent._reply_impl: has_awaiting_tool_calls?
                         → YES: ReplyEndEvent(INTERRUPTED) + 关闭 pending
                         → NO: 静默 no-op
```

## 3. 前端产品流程

`useMessages.interrupt`（`useMessages.ts` L406–424）：

1. `phase` 仅当 `streaming` 时转 `interrupting`（避免已 idle 误转）；
2. 启动 10s 兜底 timer：`interruptTimerRef` 到时 `interrupting → idle`（L413–416）；
3. `await sessionApi.interrupt(sessionId, agentId)`（`session.ts` L39–42，`POST /sessions/{sid}/interrupt`）；
4. SSE 收到 `ReplyEndEvent` → `clearInterruptTimer` + `phase=idle`（L198–204）；
5. 若 `sessionApi.interrupt` 抛错 → 清 timer 回 `idle` + setError（L419–422）。

前端 `phase` 收尾完全由 SSE 的 `ReplyEndEvent` 驱动，10s timer 仅防丢帧。

## 4. 后端运行链路

### 4.1 Router（`_session.py` L379–419）
`interrupt_session`：`status_code=202`，薄封装 `chat_service.interrupt`；`LookupError` → 404（session 不存在）。注释强调**幂等**：idle 目标是 agent 层静默 no-op。

### 4.2 Service（`_chat.py` L223–280）
`ChatService.interrupt`：
- `get_session` 不存在 → `LookupError`；
- `is_locked(session_lock(sid))` → `publish(session_interrupt_channel(), {session_id})` 然后 return（running 路径，L264–271）；
- 否则 `enqueue_run_trigger(kind=RESUME, inputs=UserInterruptEvent(reply_id=state.reply_id))`（L273–280）。

### 4.3 Running 路径：`CancelDispatcher`
`_cancel_dispatcher.py`：
- `__aenter__` 起三个循环：`_session_cancel_loop`（删 session 用）、`_task_cancel_loop`（单 BG task）、`_interrupt_loop`（L65–92）；
- `_interrupt_loop`（L204–246）订阅 `session_interrupt_channel`，收到 `session_id` → `_interrupt_session`（L227–246）：**只 cancel chat-run task，不 cancel BG tasks**（区别于 `_cancel_session`）。

### 4.4 Agent 收敛：`CancelledError` 清理（`_agent.py`）
- `_reply_impl` `try` 块（L676–889）：running 时被外部 `task.cancel()` → 抛 `CancelledError`；`except CancelledError`（L888–898）设 `end_event = ReplyEndEvent(INTERRUPTED)`；若 `interruption_raise_cancelled_error` 配置则 re-raise，否则吞。
- `finally`（L900–914）：若 `end_event` 是 INTERRUPTED → `_close_unfinished_tool_calls()`（L605–662）把每个 awaiting tool call 改为 `ToolCallState.FINISHED` 并 append `ToolResultBlock(INTERRUPTED)` + 发 `ToolResultEndEvent(INTERRUPTED)`，再 yield fallback `AssistantMsg`（`react_config.interruption_message`），最后 yield `end_event`。

### 4.5 Not-running 路径：`UserInterruptEvent` 短路（`_agent.py` L700–712）
`if isinstance(inputs, UserInterruptEvent): if has_awaiting_tool_calls(name): end_event = ReplyEndEvent(INTERRUPTED); return` —— 复用 `finally` 的同一关闭逻辑，不进 reasoning-acting 循环。若没有 awaiting tool call（idle），`end_event` 为 None → `finally` 不 yield 任何东西 → 静默 no-op。

### 4.6 WakeupDispatcher 的 resume 重排（`_wakeup_dispatcher.py`）
`enqueue` 的 `RESUME` 由唯一 dispatcher 消费：`_dispatch_one`（L207–321）若 `is_locked` 且是 resume → `_schedule_resume_retry`（L323–375，0.1s 退避重排），直到 parked run 释放锁再 spawn；孤儿 session（storage 已删）直接 drop。

## 5. 关键状态模型

| 状态 | 位置 | 说明 |
|---|---|---|
| `MessageBusKeys.session_lock(sid)` | MessageBus | running 判定依据 |
| `MessageBusKeys.session_interrupt_channel()` | MessageBus | 中断广播（cancel chat-run task）|
| `MessageBusKeys.wakeup_queue()` / `wakeup_signal()` | MessageBus | resume 触发器（含 UserInterruptEvent）|
| `ChatRunRegistry._tasks[sid]` | 进程内 | 本地 task 句柄，供 CancelDispatcher lookup |
| `ToolCallState.FINISHED` + `ToolResultState.INTERRUPTED` | `message` | 中断后工具结果语义 |
| `ReplyEndReason.INTERRUPTED` | `event/_event.py` L93–98 | 回复结束原因 |

## 6. 核心源码解读

### 6.1 为什么 cancel 与 interrupt 分离？
- **running**：进程持有 task，直接 `task.cancel()` 最及时，但必须跨进程广播找到持有者 → 走 `session_interrupt_channel` + `CancelDispatcher` 自选举（谁持有谁取消）。
- **parked**：agent 已 yield 出 awaiting tool call 没在跑，cancel task 无效；正确做法是投 `UserInterruptEvent` 让 agent 在下次 resume 时短路关闭 → 走 `enqueue_run_trigger(RESUME)` + `WakeupDispatcher`。
两者都收敛到 `_reply_impl` 的 `finally` INTERRUPTED 分支，保证 interrupted 结果一致。

### 6.2 为什么返回 202？
中断是"已接受、异步生效"，HTTP 立即返回，真正的 `ReplyEndEvent` 经 SSE 到达。符合 202 Accepted 语义（`_session.py` L381）。

### 6.3 跨进程如何工作？
publisher 不关心哪个 worker 持有 session：只 `publish(session_interrupt_channel, {session_id})`，每个进程的 `CancelDispatcher` 都订阅，但只有 `registry.get(sid)` 非 None 且未完成的进程才真正 `cancel()`（`_cancel_dispatcher.py` L239–246），其余静默 no-op。

### 6.4 幂等与 no-op
- idle session 的 interrupt：`UserInterruptEvent` 命中 `_reply_impl` 的 `has_awaiting_tool_calls=False` 分支 → `end_event=None` → finally 不 yield → 静默（前端 spam 安全，`useMessages.ts` L403–404）。
- 已结束的 parked reply：resume 的 `RESUME` 经 WakeupDispatcher 重排直到锁释放，spawn 后 agent 短路收尾。

---

## 7. 边界情况

| 场景 | 行为 |
|---|---|
| 运行中（持有锁） | broadcast cancel → 本地 task.cancel → INTERRUPTED 收尾 |
| parked on HITL | enqueue UserInterruptEvent → resume → 短路关闭 pending |
| idle（无 awaiting） | 静默 no-op |
| 取消时工具执行中 | `finally` 把 awaiting tool call 标 INTERRUPTED，不丢半截 |
| 取消发生在外部执行等待 | 同上，`_close_unfinished_tool_calls` 覆盖 |
| SSE 终止事件丢失 | 前端 10s timer 兜底回 idle |
| session 已删除 | WakeupDispatcher 孤儿守卫 drop；Router 404 |

## 9. 设计权衡

- **cancel vs interrupt 分离**：running 实时 kill，parked 事件驱动关闭，统一收敛到 `finally` INTERRUPTED。
- **协作式取消 vs 强杀**：只用 `task.cancel()` + `CancelledError` 清理，保证 partial context 被安全关闭，不破坏 state。
- **202 vs 200**：异步生效、事件驱动收尾，比同步返回更符合长任务语义。
- **跨进程广播自选举**：publisher 无状态，持有者自取消，扩展性好。

## 10. 面试沉淀

### 一句话回答
AgentScope 的 interrupt 不是简单杀线程：根据 session 是否持锁分两路——运行中走跨进程 `CancelDispatcher` 找到本地 task 调 `cancel()`，agent 在 `CancelledError` 的 `finally` 里把 pending tool call 标 INTERRUPTED 并结束；非运行中则把 `UserInterruptEvent` 投进 wakeup 队列让 parked HITL 被一致关闭；idle 是静默 no-op。整条链路幂等、跨进程、状态一致。

### 白板流程
```text
POST /interrupt (202)
  ├─ locked?  → publish(interrupt_channel) → CancelDispatcher → task.cancel()
  │              → Agent CancelledError → finally: 关闭tool call(INTERRUPTED)+ReplyEnd(INTERRUPTED)
  └─ not locked? → enqueue(RESUME, UserInterruptEvent) → WakeupDispatcher(退避重排)
                   → Agent._reply_impl: has_awaiting? → ReplyEnd(INTERRUPTED) : no-op
```

### 高频追问
1. 为什么不直接 kill 进程里的 task？——跨进程，持有者可能不在这个进程。
2. interrupted tool result 什么时候生成？——`finally` 的 `_close_unfinished_tool_calls`，保证不丢半截。
3. idle 为什么是 no-op？——没有 awaiting tool call，`end_event=None`，finally 不 yield。
4. 202 还是 200？——异步生效，用 202，收尾靠 SSE。
5. 前端怎么知道停了？——`ReplyEndEvent` 驱动 phase，10s 兜底防丢。

### 对比题
- Cancel（running kill）vs Interrupt（parked event）：执行中 vs 等待中。
- 强杀进程 vs 协作式 `task.cancel()`：状态安全 vs 破坏性。
- 同步返回 vs 202 + SSE：短任务 vs 长任务。

### 项目表达
"我们的 Stop 设计核心是 cancel/interrupt 分离。运行中的任务通过 MessageBus 广播找到持有进程的 task 调 cancel，agent 在 CancelledError 的 finally 里把没完成的工具调用标记成 INTERRUPTED 并干净收尾——不会留下半截状态。Parked 在 HITL 的回复则投一个 UserInterruptEvent 走唤醒队列去短路关闭。两条路最终都收敛到同一个 INTERRUPTED 收尾逻辑，所以状态永远一致。"
