# 专题四：Plan 计划模式

> 本专题覆盖 AgentScope 的"计划"能力：它不是独立页面或 HTTP CRUD，而是 Agent Runtime 内部的任务状态——LLM 通过 `TaskCreate`/`TaskList`/`TaskGet`/`TaskUpdate` 工具维护计划，状态保存在 `AgentState.tasks_context`，由 `StateChangeMiddleware` 通过 hash 对比检测变化并发布 `state_updated` 事件，前端 `TaskPanel` 只读投影。

---

## 1. 这个专题解决什么问题

**产品问题**：用户希望看到 Agent 的"待办清单 / 进度"，理解长任务的分解与完成度，但又不希望用户手动编辑计划打乱 Agent 的推理。

**工程问题**：计划状态放哪？放独立 API 会脱离 Agent 推理上下文、难以和 tool call 对齐；放 Agent 内部状态则天然随 session 持久化、随 HITL 恢复。

核心结论：**Plan 是 AgentState 的一部分，不是单独数据库表；任务变化由工具调用产生，经 StateChangeMiddleware 变成实时 UI 事件；前端 Plan 面板是只读投影。**

---

## 2. 总体架构

```text
LLM 决定建计划
  → Agent 调 TaskCreate / TaskUpdate（tool call）
  → 修改 _agent_state.tasks_context.tasks
  → StateChangeMiddleware.on_acting：前后 hash 对比
       ├─ 变化 → publish_session_event(CustomEvent(name="state_updated",
       │            value={tasks_context, permission_context}))
       └─ 无变化 → 不推
  → SSE 推到前端
  → useMessages.processEvent：CUSTOM + state_updated → onStateUpdated(value)
  → ChatViewport.handleStateUpdated → setTasksContext(value.tasks_context)
  → TaskPanel 渲染任务列表/进度/依赖/状态
```

## 4. 后端运行链路

### 4.1 Toolkit 默认注入（`_service/_toolkit.py` L135–136）
```python
tools += [TaskCreate(), TaskList(), TaskGet(), TaskUpdate()]
```
**始终注入每个 Agent 的 Toolkit**（不依赖 session/team 角色），所以 Plan 能力全局可用。

### 4.2 任务工具修改 `AgentState`（`tool/_task/_create_task.py`、`_update_task.py`）
- `TaskCreate.call`（`_create_task.py` L83–132）：生成顺序 `next_id`（从现有 numeric id 取 max+1），`Task(id, subject, description, metadata)` 追加到 `_agent_state.tasks_context.tasks`，全部 `pending` 状态。
- `TaskUpdate.call`（`_update_task.py` L135–269）：按 `task_id` 改 `subject/description/status/owner/metadata`，处理 `add_blocks`/`add_blocked_by` 依赖（经 `_update_block_relation`，L271–294），`status='deleted'` 时 pop 并从其它任务的 blocks/blocked_by 移除。

`Task` 模型位于 `state/_task.py`（本批未展开，引用 `state/_state.py` L10 的 `from ._task import Task`）；`tasks_context: TaskContext` 是 `AgentState` 字段（`_state.py` L142–185）。

### 4.3 StateChangeMiddleware（`_service/.../middleware/_state_change_middleware.py`）
- `_state_hash`（L70–90）：只 hash `tasks_context` + `permission_context`（**排除 `context` 消息历史**，因为它每步都变、与本中间件无关）。
- `on_acting`（L154–196）：工具执行前后 hash 对比，变了就 `_publish_state`（L92–115）推 `CustomEvent(name="state_updated", value={tasks_context, permission_context})` 经 `publish_session_event`。
- `on_reply`（L117–152）：包裹整轮 reply，捕捉 `on_acting` 窗口之外的变化（如处理 `UserConfirmResultEvent` 时改的 permission 规则）。
- 注意：事件经 `publish_session_event` 写入 bus，所以 `GET /sessions/{sid}/stream` 像普通 session 事件一样推给前端（`_state_change_middleware.py` L22–26 注释）。

## 5. 关键状态模型

| 状态 | 位置 | 说明 |
|---|---|---|
| `AgentState.tasks_context: TaskContext` | `state/_state.py` L184 | 计划任务集合 |
| `TaskContext.tasks: list[Task]` | `state/_task.py` | 单任务 |
| `Task` 字段 | `state/_task.py` | id/subject/description/status/owner/blocks/blocked_by/metadata |
| `CustomEvent(name="state_updated")` | `event/_event.py` L485–516 | 推给前端的增量通知 |
| `ChatViewport.tasksContext` | 前端 React state | 投影渲染源 |

`status` 工作流（`_update_task.py` L96–100）：`pending → in_progress → completed`，`deleted` 永久移除。

## 6. 核心源码解读

### 6.1 为什么 Task 工具默认注入每个 Agent？
计划是 Agent 推理-行动循环的一部分——Agent 自己决定何时分解任务、标记完成。若做成人手填的表单，会脱离 Agent 的实际执行上下文，也无法和 tool call 对齐。注入为标准工具后，LLM 自主管理计划，前端只投影。

### 6.2 为什么 `tasks_context` 放 `AgentState` 而非独立 Task API？
`AgentState` 随 Session 持久化（`ChatService._run_impl` 的 `update_session_state`），因此计划天然随 session 存、随 HITL 恢复、随刷新回放。独立 API 要额外解决"和哪次 reply、哪个 tool call 关联"的问题。

### 6.3 为什么 `StateChangeMiddleware` 用 hash 对比？
工具执行可能产生多次 state 变更，且 `on_acting` 只在 tool 窗口内；用 md5 hash 前后对比，零侵入地检测"tasks/permission 是否真变了"，变了才推一次 `state_updated`，避免每个 tool 步骤都刷 UI。

### 6.4 前端为何只读投影？
`TaskPanel` 渲染的数据来自 `onStateUpdated` 推来的 `value.tasks_context`，用户不直接编辑（编辑会破坏 Agent 的 `tasks_context` 与 tool call 一致性）。这是"Agent 主导计划，人类观察"的设计。

## 7. 边界情况

| 场景 | 行为 |
|---|---|
| 计划中途刷新 | `messages` 返回历史 Msg + `state` 持久化（含 tasks_context），重连后 `state_updated` 增量继续 |
| HITL 等待时计划变化 | `on_reply` 兜底捕获窗口外变化（权限规则在确认时改）|
| 任务依赖成环 | `TaskUpdate` 仅 append 到 `blocks/blocked_by`，无环检测（待验证：未找到环校验源码） |
| 并发工具改同一任务 | 单 session 锁串行，无并发写冲突 |

## 9. 设计权衡

- **Plan 工具化 vs 表单 CRUD**：工具化让计划成为 Agent 推理的一部分，强表单则脱离执行上下文。
- **tasks_context 进 AgentState vs 独立表**：随 session 持久/恢复，省去关联成本。
- **hash 对比 vs 事件驱动**：低开销检测变化，避免刷屏。
- **前端只读 vs 可编辑**：保持 Agent 主导、状态一致。

## 10. 面试沉淀

### 一句话回答
AgentScope 的 Plan 不是项目管理 CRUD，而是 Agent Runtime 内部的任务状态：LLM 通过 TaskCreate/TaskUpdate 等工具维护计划，存在 `AgentState.tasks_context`，`StateChangeMiddleware` 用 hash 检测变化并发布 `state_updated` 事件，前端 TaskPanel 实时只读投影。这把计划变成了 Agent 推理-行动循环的一部分。

### 白板流程
```text
LLM → TaskCreate/Update → _agent_state.tasks_context.tasks
  → StateChangeMiddleware(on_acting/on_reply) hash 对比
  → 变化? → publish_session_event(CustomEvent state_updated)
  → SSE → useMessages → onStateUpdated → setTasksContext → TaskPanel
```

### 高频追问
1. 为什么 Plan 不放独立数据库？——随 AgentState 持久化/恢复，与 session 对齐。
2. 为什么 Task 工具默认注入？——计划是 Agent 推理的一部分，LLM 自主维护。
3. 为什么前端只读？——避免破坏 Agent 的 tasks_context 与 tool call 一致性。
4. 为什么用 hash 而不是每次都推？——零侵入检测变化，避免刷 UI。
5. 页面刷新后计划还在吗？——在，tasks_context 随 state 持久化。

### 对比题
- Plan 工具化 vs 表单 CRUD：Agent 主导 vs 人主导。
- AgentState 内嵌 vs 独立 Task 表：随 session 恢复 vs 需关联。
- hash 对比 vs 显式事件：低开销 vs 精确。

### 项目表达
"我们没把计划做成独立页面，而是让 Agent 通过 Task 工具自己管理计划，状态存在 AgentState 里随 session 恢复。StateChangeMiddleware 用 md5 hash 对比 tasks_context 和 permission_context，变了就发一个 state_updated 事件，前端 TaskPanel 只读投影。这样计划天然跟着 Agent 的推理走，刷新、HITL 都不丢。"
