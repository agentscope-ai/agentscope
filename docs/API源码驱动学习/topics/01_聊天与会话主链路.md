# 专题一：Chat 与 Session 主链路

> 本专题覆盖：一个用户消息如何从前端 `useMessages.send` 出发，穿过 `POST /chat/`、FastAPI Router、`ChatRunRegistry`、`ChatService.run`、分布式锁、`Agent.reply_stream`，再经 MessageBus 的 replay-log + Pub/Sub 回流到前端 SSE，最终合并成 `Msg` 渲染的全过程。同时覆盖 Session 作为"运行态边界"的本质，以及刷新/重连/并发提交等边界情况。

---

## 1. 这个专题解决什么问题

**产品问题**：用户希望在 Web UI 里和 Agent 连续对话，且要求（a）长任务不阻塞请求；（b）工具调用、流式输出、HITL 确认、前端刷新都能走同一套机制；（c）多进程部署下同一 Session 不会并发跑两个 run。

**工程问题**：一次 Agent 运行是"长生命周期、可中断、可恢复、跨进程"的工作，不能塞进一个 HTTP 请求里。AgentScope 的解法是把"触发"和"执行"解耦：`POST /chat/` 只负责点火（fire-and-forget），真正的运行在后台任务里完成，事件通过独立 SSE 通道回流。

核心结论先行：**`POST /chat/` 不是问答接口，而是一次 Agent 运行的异步触发器；运行事件通过 `GET /sessions/{sid}/stream` 以 SSE 推给前端。**

---

## 2. 总体架构

```text
┌─────────────────────────── 前端（examples/web_ui/frontend） ───────────────────────────┐
 TextInput → ChatContent.onSend → useMessages.send                                       │
   → 乐观追加 UserMsg 到 msgsRef                                                          │
   → chatApi.trigger  ──POST /chat/──┐                                                    │
                                     │                                                    │
 useMessages 初始化：                 │            ┌──────── 后端（src/agentscope/app） ──┐ │
   GET /sessions/{sid}/messages      │            │ chat_router.chat                      │ │
     (历史 Msg)                       │            │   → ChatRunRegistry.spawn             │ │
   GET /sessions/{sid}/stream (SSE) ←┼── SSE ─────┤   → ChatService.run                   │ │
        │                            │            │     → MessageBus.acquire_lock          │ │
   processEvent 合并事件为 Msg        │            │     → Agent.reply_stream              │ │
        ↓                            │            │       → publish_session_event          │ │
   React 重渲染                      │            │         → bus.log_append + publish     │ │
└────────────────────────────────────┘            └──────────────────────────────────────┘
```

关键解耦点：**`POST /chat/` 的 HTTP 生命周期 ≠ Agent 真实运行生命周期**。前端不能靠 POST 是否返回判断回答结束，而靠 SSE 里的 `ReplyEndEvent`。

## 3. 前端产品流程

- **页面/组件**：`examples/web_ui/frontend/src/pages/chat/index.tsx`、`pages/chat/ChatViewport.tsx`、`components/chat/ChatContent.tsx`、`components/chat/TextInput.tsx`、`components/chat/MessageBubble.tsx`。
- **Hook**：`examples/web_ui/frontend/src/hooks/useMessages.ts` —— 状态机核心。
- **API 封装**：`examples/web_ui/frontend/src/api/chat.ts`（`chatApi.trigger`）、`api/session.ts`（`sessionApi.messages` / `streamEvents`）。

`useMessages` 的双通道设计（`useMessages.ts` 注释 L78–100）：

1. **History**：`GET /sessions/{sid}/messages` 取已持久化 Msg（每个是一条完整回复）。
2. **Live stream**：`GET /sessions/{sid}/stream` 打开长连接 SSE，接收 `AgentEvent` 增量。
3. 用户消息/HITL 确认都走 `POST /chat/`（fire-and-forget），结果经已打开的 SSE 回流。

`phase` 状态机（`useMessages.ts` L73、`ReplyPhase = 'idle' | 'streaming' | 'interrupting'`）：

- `ReplyStartEvent` → `streaming`（创建 `AssistantMsg` 并 `setPhase('streaming')`，L190–197）；
- `ReplyEndEvent` → `idle`（L198–204）；
- 其它事件 `appendEvent` 合并进当前 `currentReplyRef`（L205–207）。

## 4. 后端运行链路

文件链（`src/agentscope/app/_router/_chat.py` → `_service/_chat.py` → `agent/_agent.py`）：

1. `chat_router.chat`（`_chat.py` L54–160）：
   - 若 `request.input` 是 `UserConfirmResultEvent` / `ExternalExecutionResultEvent` → 走 HITL resume 路径（`SubagentHitlProjector.resolve` 解析 worker + `enqueue_run_trigger(kind=RESUME)`，L113–136）。
   - 否则（新用户消息 / `None`）→ `ChatRunRegistry.spawn(chat_service.run(...))`（L142–151）。若同一 session 已有活跃 run，registry 抛 `RuntimeError` → 转为 `409 CONFLICT`（L152–156）。
2. `ChatRunRegistry.spawn`（`_manager/_chat_run_registry.py` L36–92）：按 `session_id` 单飞（一个 session 至多一个本地 task），task 完成后自动 `_cleanup` 移除。
3. `ChatService.run`（`_service/_chat.py` L162–221）：`try/except` 包裹 `_run_impl`，异常仅记录日志后吞掉，避免单点失败拖垮触发方（HTTP 请求任务 / 唤醒 dispatcher）。
4. `ChatService._run_impl`（`_service/_chat.py` L282–645）：
   - 校验 `agent_record`（404）/ `session_record`（404）/ `workspace`；
   - 装配 middlewares（Inbox / StateChange / ToolOffload + 可选 extras），按需注入 TTS / RAG；
   - `get_toolkit` 装配工具；`get_model` 解析 chat/fallback 模型；
   - `async with self._message_bus.acquire_lock(lock_key, ttl_secs=SESSION_RUN_TTL_SECS)`（L538–541）拿到分布式锁；
   - `async for event in agent.reply_stream(inputs=input_msg)`：每事件 `publish_session_event`（写 replay-log + 广播 live，L561–565）；
   - `finally` 里 `_persist()` 持久化 `Msg` + `agent.state` + `log_trim`，并用 `asyncio.shield` 保护（L616–645）。

## 5. 关键状态模型

| 状态 | 位置 | 说明 |
|---|---|---|
| `SessionRecord.config.workspace_id` | `storage` | Session 绑定的工作区 |
| `SessionRecord.state` (`AgentState`) | `storage` | 持久化上下文、reply_id、permission、tasks_context |
| `SessionRecord.state.context` 尾部 `AssistantMsg` | `storage` | 恢复时判断是否 parked on HITL |
| `MessageBusKeys.session_lock(sid)` | MessageBus | 分布式运行锁（实时运行态）|
| `MessageBusKeys.session_events(sid)` | MessageBus | replay log（晚到订阅者）|
| `MessageBusKeys.session_interrupt_channel()` | MessageBus | 中断广播通道 |
| `InMemoryMessageBus` / `RedisMessageBus` | `message_bus/_base.py` | 传输层实现 |

**Session 是运行态边界，Agent 是配置态边界**：同一个 Agent（`AgentRecord`）可被多个 Session（`SessionRecord`）复用，运行态（锁、消息、state）只存在 Session 上。

## 6. 核心源码解读

### 6.1 fire-and-forget 的两类触发（非对称设计）

`_chat.py` L10–22 注释明确：新消息直接 spawn 进 registry，单飞规则天然变成 409 双提交守卫；HITL 结果则 enqueue 到 wakeup 队列，由唯一的 `WakeupDispatcher` 串行进 spawn，避免"resume 与 worker 仍在收尾的 parked run"碰撞出 409。

### 6.2 事件发布 = replay log + live Pub/Sub

`publish_session_event`（`_bus_ops.py` L39–65）：

```python
key = MessageBusKeys.session_events(session_id)
entry_id = await bus.log_append(key, event, max_len=SESSION_REPLAY_MAX_LEN)  # 持久回放
await bus.publish(key, {**event, "_entry_id": entry_id})                      # 实时广播
```

即同一份事件既进 replay-log（供晚到 SSE 订阅者回放），又进 live 广播通道（供已订阅者实时收）。

### 6.3 为什么 `finally + asyncio.shield` 对一致性很关键

`_service/_chat.py` L616–645：持久化（upsert_message + update_session_state + log_trim）放在 `finally` 的 `_persist()` 协程里，并用 `asyncio.shield` 包裹。原因（注释 L617–645）：

- 必须在**锁释放之前**完成写盘，否则另一进程可能抢到锁并读到 stale state；
- `shield` 保证即使外层（触发方 task）被 cancel，持久化仍跑完；`CancelledError` 分支再 `await persist_task` 后重新 raise，保证锁只在存储一致后才释放。

### 6.4 wake-up 对 parked run 的保护

`_run_impl` L514–531：当 `input_msg is None` 且尾部 assistant 消息停在 `ASKING`/`SUBMITTED` tool call 时，直接 return —— 不踢一个 `None` run 去撞 parked HITL，inbox 内容留给真正的 resume 自然 drain。

## 7. 边界情况

| 场景 | 行为 | 源码 |
|---|---|---|
| 重复点击发送 | 第二次 spawn 同 session → registry 抛错 → 409 | `_chat_run_registry.py` L72–77 |
| 前端刷新 / 重连 | 先 `messages`（含 `is_running`）+ 再 `stream` 接增量；尾部 parked tool_call 时 `phase=streaming` | `useMessages.ts` L254–277 |
| 进程崩溃 | 运行锁有 TTL（`SESSION_RUN_TTL_SECS`，默认 600s，由 heartbeat 续租），崩溃后至多 TTL 即释放；replay-log 保留历史 | `_base.py` L324–351 |
| 单 run 异常 | `ChatService.run` 吞异常，不影响触发方 | `_chat.py` L211–221 |
| wake-up 撞 running | `WakeupDispatcher` 跳过 `wake`，`resume` 退避重排 | `_wakeup_dispatcher.py` L256–271 |

## 9. 设计权衡

- **为什么 `POST /chat/` 不返回流？** 长任务 + 跨进程运行无法绑定单 HTTP 连接；fire-and-forget + SSE 让刷新、重连、HITL、多进程恢复都走同一条事件机制。
- **为什么需要 replay log？** SSE 是 transient 广播（后订阅者收不到历史），replay-log 让晚加入/重连的前端先回放已产生事件再接 live。
- **为什么 running 状态来自锁而非 DB 字段？** 分布式下进程可能崩溃，DB 字段无法及时反映"是否已停止"；锁由 bus 心跳续租，崩溃后自动释放。
- **单 session 锁 vs 数据库状态**：锁=实时运行态，Storage=持久状态，两者分工（见 `ChatService` 类注释 L64–70）。

## 10. 面试沉淀

### 一句话回答
`POST /chat/` 是 Agent 运行的异步触发器，点火后由 `ChatRunRegistry` 单飞 + `MessageBus` 分布式锁保证单 session 串行；运行事件同步写入 replay-log 并广播 live，前端靠独立 SSE（`GET /sessions/{sid}/stream`）回流合并成 `Msg`，所以"请求结束"不等于"回答结束"。

### 白板流程
```text
TextInput → useMessages.send（乐观追加 UserMsg）
  → POST /chat/（fire-and-forget）
  → ChatRunRegistry.spawn → ChatService.run
  → acquire_lock(session_lock)
  → Agent.reply_stream → publish_session_event（log_append + publish）
  → 前端 SSE: ReplyStart → Text/Data/ToolCall delta → ReplyEnd
  → finally: shield(upsert_message + update_state + log_trim) → 释放锁
```

### 高频追问
1. 为什么 409 用 registry 而不是 DB 唯一约束？——registry 是进程内单飞，DB 跨进程用锁；两者配合，409 是快速失败守卫。
2. `asyncio.shield` 不写会怎样？——外层 cancel 可能让持久化中断，锁释放后别进程读到 stale state。
3. replay-log 和 Pub/Sub 有什么区别？——前者多消费者各自维护游标、有界截断；后者仅当前订阅者收到、无历史。
4. 前端刷新后怎么知道该停在 streaming？——`messages` 返回的 `is_running` + 尾部 tool_call 的 `ASKING/SUBMITTED` 状态。
5. 进程崩溃时运行到一半怎么办？——锁 TTL 自动释放；已落盘的部分 Msg/state 保留；前端重连接上 live。

### 对比题
- 同步问答 API vs fire-and-forget + SSE：长任务、可恢复性、跨进程。
- 数据库状态 vs MessageBus 锁：持久 vs 实时运行态。
- replay log vs Pub/Sub：有界多消费者回放 vs 瞬时广播。

### 项目表达
"我们 AgentScope 的 Chat 设计把一次运行拆成触发、加锁、执行、事件流、持久化、释放锁六个阶段。最值得讲的是 `finally + asyncio.shield` 保证存储一致性，以及 replay-log + live 双写让前端刷新零丢失。面试时我常拿这个讲分布式 Agent Runtime 的状态一致性。"
