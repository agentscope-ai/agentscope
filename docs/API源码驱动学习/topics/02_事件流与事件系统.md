# 专题二：Stream 与事件系统

> 本专题聚焦 `GET /sessions/{sid}/stream` 的 SSE 实现，以及 MessageBus 的"消费语义分层"设计。核心问题：后端的 `AgentEvent` 如何可靠、低延迟、可重连地送达前端，并支撑 HITL 投影卡的重放。

---

## 1. 这个专题解决什么问题

**产品问题**：前端要实时渲染 Agent 的流式输出（文本增量、工具调用、HITL 确认卡、Plan 更新、跨进程 TeamSay）。要求：
- 低延迟（模型一产出就推）；
- 可重连（刷新页面不丢历史增量）；
- 多事件类型（SSE 里混着 `AgentEvent` 与 `CustomEvent`）；
- 心跳保活（穿透反向代理）。

**工程问题**：如何在一个 HTTP 长连接上，把"已产生事件回放" + "后续实时事件"无缝衔接，同时承载 HITL 投影卡这类"不在 replay-log 里、却在重连时必须出现"的持久状态。

---

## 2. 总体架构

MessageBus 按**消费语义**而非业务概念分层（`message_bus/_base.py` L11–41）：

| 模式 | 原语 | 语义 |
|---|---|---|
| A — drain queue | `queue_push` / `queue_drain` | 单消费者、ack-on-read、TTL 兜底 |
| C — replay log | `log_append` / `log_read` / `log_trim` | 多消费者、各自游标、有界截断 |
| D — transient broadcast | `publish` / `subscribe` | 仅当前订阅者收到、无历史 |
| E — 分布式锁 | `acquire_lock` / `is_locked` | 集群互斥 |
| F — registry map | `registry_set` / `getall` / `drop` | hash 命名空间 |

Session 事件流同时用了 **C（回放）+ D（实时）**：先 `log_read` 回放，再 `subscribe` 接 live。

```text
Agent.reply_stream
   → publish_session_event
       ├─ log_append(session_events)   # replay log（有界 max_len）
       └─ publish(session_events)      # live broadcast
                 │
   SSE 端点 stream_session_events
       ├─ log_read 回放已有事件
       ├─ 注入 worker HITL 投影卡（registry 读取）
       └─ subscribe 实时事件 → feeder queue → heartbeat 穿插输出
                 │
   useMessages.streamEvents (fetch SSE) → processEvent 合并为 Msg
```

## 3. 前端产品流程

- `api/session.ts` `streamEvents`（`session.ts` L67–103）：用 fetch-based SSE（非原生 `EventSource`，以便带 `X-User-ID` 头），逐行解析 `data: {...}` 帧，跳过的 `:` 注释帧即心跳。
- `useMessages.ts` L286–301：history 取完后立即开 SSE；`processEvent`（L164–235）按 `event.type` 路由：
  - `CUSTOM` → 交 `onTeamUpdated` / `onStateUpdated` / `subagent_*` 回调，不进 Msg；
  - `REPLY_START` → 建 `AssistantMsg`、`phase=streaming`；
  - `REPLY_END` → 收尾、`phase=idle`；
  - 其它 → `appendEvent` 合并进 `currentReplyRef`。

## 4. 后端运行链路

SSE 端点：`session_router.stream_session_events`（`_session.py` L681–837）。

`_sse_generator` 三段式（L729–828）：

1. **Replay**（L731–735）：`message_bus.log_read(session_events(sid), max_count=SESSION_REPLAY_MAX_LEN)`，逐条 `yield f"data: {json}"`。
2. **注入 worker HITL 卡**（L737–776）：从 `SessionProjection.list(sid, SubagentHitlProjector.KIND)` 读持久 hash；对每条做 reconcile-on-read——用 `_worker_still_asking`（`_session.py` L626–678）查 worker 自己的 `state.context` 是否仍 `ASKING/SUBMITTED`，是则 push `CustomEvent(name="subagent_require_user_confirm")`，否则删 ghost。
3. **Live**（L778–828）：起 `_feeder` 后台 task 把 `subscribe(session_events)` 推入 `asyncio.Queue`；主循环 `wait_for(queue.get(), timeout=30s)`，正常就 `yield data:`，超时则 `yield ":\n\n"` 心跳。

心跳常量 `_HEARTBEAT_INTERVAL_SECS = 30`（`_session.py` L622）。响应头 `Cache-Control: no-cache`、`X-Accel-Buffering: no` 防止缓冲（L833–836）。

> 注意 feeder 用 `asyncio.Queue` 而非直接 `wait_for(__anext__())`，原因注释 L782–785：直接 cancel 挂起的 `__anext__` 会让生成器停在 running 态导致 `aclose()` 失败。

## 5. 关键状态模型

| 状态 | 位置 | 说明 |
|---|---|---|
| `MessageBusKeys.session_events(sid)` replay-log | MessageBus | 当前 run 事件，有界 `SESSION_REPLAY_MAX_LEN`（默认 1000，`_base.py` L476） |
| `Registry: session projection (SubagentHitlProjector.KIND)` | MessageBus | 持久 HITL 投影卡，无 TTL，靠 reconcile-on-read 自愈 |
| `EVENT_TYPE` / `ReplyEndReason` | `event/_event.py` | 事件枚举与结束原因 |
| `useMessages.currentReplyRef` | 前端 | 正在累积的 assistant 消息 |

## 6. 核心源码解读

### 6.1 回放 + 实时如何无缝衔接
`_sse_generator` 先 `log_read`（拿到此刻及之前所有事件）再 `subscribe`（拿到之后所有事件）。因为 replay-log 与 live 通道都挂在同一个 key `session_events(sid)` 上，且 `publish_session_event` 同时写两者，订阅者不会漏事件（subscribe 建立后才会有新 publish，回放覆盖了建立前的全部）。

### 6.2 HITL 投影卡为何不在 replay-log 里
`_session.py` L737–746 注释明确：投影卡存在**持久 Redis hash**，**不进 replay-log**（per-run 会被 `log_trim` 截掉），也**不进 leader 自己的 Msg 历史**。所以重连时 replay-log 里没有它，必须显式从 `SessionProjection` 读并 reconcile，否则 worker parked 后 leader 刷新会丢确认卡。

### 6.3 事件类型全貌（`event/_event.py`）
- 生命周期：`ReplyStartEvent` / `ReplyEndEvent`（`ReplyEndReason`: completed/interrupted/exceed_max_iters）。
- 模型：`ModelCallStart/EndEvent`。
- 文本/数据/thinking block 的 start/delta/end。
- 工具：`ToolCallStart/Delta/EndEvent`、`ToolResultStart/TextDelta/DataDelta/EndEvent`（`ToolResultState`: INTERRUPTED 等）。
- HITL：`RequireUserConfirmEvent` / `RequireExternalExecutionEvent` / `UserConfirmResultEvent` / `UserInterruptEvent` / `ExternalExecutionResultEvent`。
- 扩展：`CustomEvent`（name=state_updated / team_updated / subagent_require_user_confirm 等）。

## 7. 边界情况

| 场景 | 行为 | 源码 |
|---|---|---|
| 刷新后 worker 仍 parked | replay 无 HITL 卡，但 `_worker_still_asking` reconcile 注入 | `_session.py` L737–776 |
| 代理静默断连 | 30s 心跳 `:\n\n` 保活 | `_session.py` L622 / L821–822 |
| 事件帧丢失 / 后端 bug | 前端 `interrupting` 有 10s 兜底回 `idle` | `useMessages.ts` L411–416 |
| SSE 中途异常 | `useMessages` catch 非 AbortError 才 setError | `useMessages.ts` L296–300 |
| replay-log 超长 | `log_trim(max_len)` 截断头部 | `_service/_chat.py` L635 |

## 9. 设计权衡

- **为何 replay + live 双通道而非纯 WebSocket/纯 poll？** SSE 天然单向 server→client、HTTP 友好、可穿透代理；replay 解决迟到订阅，live 解决实时性。
- **为何 HITL 卡走 registry 而非 replay-log？** 卡的权威状态在 worker 自己的 `state.context`，投影只是镜像；registry 无 TTL 可 indefinite pending，且 reconcile-on-read 自愈，避免"被 trim 掉"或"残留 ghost"。
- **为何 feeder + queue 而非直接 await 订阅？** 避免 cancel 挂起生成器导致 `aclose` 失败（见 §4）。

## 10. 面试沉淀

### 一句话回答
AgentScope 的 SSE 端点先把 replay-log 回放、再接 live 订阅，用 30s 心跳保活；特殊的是 worker 的 HITL 确认卡不走 replay-log（会被 trim），而是存在持久 registry，在每次重连时 reconcile-on-read 注入，保证刷新不丢卡。

### 白板流程
```text
stream_session_events
  → log_read(replay)  → yield data
  → projection.list(HITL) → reconcile(_worker_still_asking) → yield CustomEvent
  → subscribe(live) → feeder → queue → wait_for(30s)
        ├─ 有事件 → yield data
        └─ 超时   → yield ":\n\n" 心跳
```

### 高频追问
1. 回放和实时会不会重复/遗漏？——同一 key 双写，先读后订，订阅建立后的新事件才走 live，无重复。
2. 为什么 HITL 卡不进 replay-log？——per-run 会被 trim，且权威态在 worker context，registry 镜像 + reconcile 更稳。
3. 心跳丢了会怎样？——10s 前端兜底 + 代理可能断，但重连会重新 replay+注入。
4. MessageBus 为什么按消费语义分模式？——queue/log/pubsub/lock/registry 生命周期不同，分层让调用方自己选对的方式。

### 对比题
- replay log vs Pub/Sub：有界多消费者回放 vs 瞬时广播。
- SSE vs WebSocket：单向流 vs 全双工。
- registry 投影卡 vs Msg 历史：镜像+自愈 vs 权威记录。

### 项目表达
"我把 Agent 事件流设计成 replay + live 双通道，配合 30 秒心跳。最有意思的是跨进程 HITL：worker 的确认卡不能丢在会被 trim 的 replay-log 里，所以我用 MessageBus 的 registry 做持久镜像，前端每次重连都 reconcile-on-read 检查 worker 是否还 parked，既保证刷新不丢卡，又不会留下 ghost 卡。"
