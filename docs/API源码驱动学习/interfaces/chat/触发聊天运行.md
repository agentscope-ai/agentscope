# 接口：`POST /chat/`

## 1. 结论先行

`POST /chat/` 是 Agent 运行的**异步触发器**（fire-and-forget），不是问答接口。它把用户消息或 HITL 确认事件交给后端点火：新消息直接 `ChatRunRegistry.spawn` 进后台任务，HITL 结果（确认/外部执行）则 enqueue 到 wakeup 队列由 `WakeupDispatcher` 串行进 resume。运行事件不从这个接口返回，而是通过 `GET /sessions/{sid}/stream` 的 SSE 推给前端。设计亮点：单 session 单飞（registry 抛 409）、HITL resume 与 worker parked run 不撞车、跨进程可路由。

---

## 2. 用户场景

Web UI 聊天页：用户输入文本点 Send → `useMessages.send` 乐观追加 `UserMsg` 并 `chatApi.trigger`；或用户在确认卡点确认/拒绝 → `onUserConfirm` / `onSubagentConfirm` 构造 `UserConfirmResultEvent` 走同一接口。用户不等待此接口返回内容，回答由已打开的 SSE 流入。

---

## 3. 前端链路

```text
TextInput.handleSend
  → ChatContent.onSend
  → useMessages.send / onUserConfirm / onSubagentConfirm
  → chatApi.trigger({agent_id, session_id, input})   # api/chat.ts L23-24
  → POST /chat/
```
关键 React state（`useMessages.ts`）：`msgs`（乐观追加 userMsg）、`phase`（`ReplyStartEvent`→streaming、`ReplyEndEvent`→idle）、`subagentHitl`（leader 投影卡）。`chatApi.trigger` 仅返回 `{status, session_id}`（`chat.ts` L4–24）。

---

## 4. HTTP 设计

- **method**：`POST`
- **path**：`/chat/`
- **body**：`ChatRequest { agent_id, session_id, input }`（`input` 为 `Msg | list[Msg] | UserConfirmResultEvent | ExternalExecutionResultEvent | None`）
- **response**：`ChatTriggerResponse { status: "started", session_id }`（`_chat.py` L31, L157–160）
- **status code**：`200`（started）；`409` 当同 session 已有活跃 run（新消息路径，L152–156）；`404` 当 agent/session 不存在（经 `ChatService._run_impl` 的 resolve/404，最终在 run 内抛 HTTPException，但 router 层 spawn 本身不验证，404 在后台 run 中体现——**注意：spawn 成功的 200 不保证 run 内部成功**，run 异常被吞）
- **幂等性**：新消息路径非幂等（重复提交 → 409）；HITL resume 路径天然幂等（enqueue，dispatcher 串行）
- **404/409 语义**：409=双提交守卫（快速失败）；404=资源不存在

> 待验证：router 层对 `agent_id`/`session_id` 的前置 404 校验实际发生在 `ChatService._run_impl`（异步 task 内），而非 `chat_router.chat` 同步返回。即 HTTP 200 "started" 仅表示"已点火"，真正的 404 出现在后台 run 的日志与（若有）SSE 错误事件。建议核对是否有对 spawn 前的同步校验。

## 5. 后端调用链

```text
chat_router.chat (_chat.py L54)
  ├─ input is UserConfirmResultEvent/ExternalExecutionResultEvent?
  │     → SubagentHitlProjector.resolve(leader, reply_id)  # 解析 worker
  │     → enqueue_run_trigger(kind=RESUME, inputs=event)   # _chat.py L113-136
  │     → return {status:"started", session_id: worker_sid}
  └─ else (Msg/list/None)
        → ChatRunRegistry.spawn(chat_service.run(...), session_id)  # L142-151
        → 409 if existing active task (L152-156)
        → return {status:"started", session_id}
              ↓ (后台)
        ChatService.run → _run_impl
          → acquire_lock(session_lock)
          → Agent.reply_stream → publish_session_event
```

## 6. 数据模型

- **Request**：`ChatRequest`（`_router/_schema`，`agent_id: str`、`session_id: str`、`input: Msg|list[Msg]|UserConfirmResultEvent|ExternalExecutionResultEvent|None`）
- **Response**：`ChatTriggerResponse(status: str, session_id: str)`
- **Event**：`AgentEvent` 全族（`event/_event.py`）；`UserConfirmResultEvent`（`_event.py` L434–444，含 `reply_id` + `confirm_results`）
- **State**：`AgentState`（`state/_state.py`），run 内更新 `context`/`reply_id`/`tasks_context`

## 7. 状态变化

| 变化 | 位置 |
|---|---|
| 后台 task 注册 | `ChatRunRegistry._tasks[session_id]` |
| 分布式运行锁获取 | `MessageBus.acquire_lock(session_lock)` |
| Msg 持久化（用户输入 + 回复） | `storage.upsert_message` |
| AgentState 持久化 | `storage.update_session_state` |
| 事件写入 replay-log + live | `MessageBus.log_append` + `publish` |
| HITL resume：wakeup 队列入队 | `MessageBus.queue_push(wakeup_queue)` |

---

## 8. 事件回流

- 触发结果（`{status, session_id}`）由 HTTP 返回。
- 运行事件（ReplyStart/Text/ToolCall/ReplyEnd 等）经 `publish_session_event` 写入 bus，由前端已打开的 `GET /sessions/{sid}/stream` SSE 接收（`useMessages.streamEvents` → `processEvent`）。
- HITL 确认结果：POST 到 leader，经 `SubagentHitlProjector.resolve` 路由到 worker session 的 resume（`_chat.py` L119–136）。

---

## 9. 并发、异常与一致性

- **单 session 单飞**：`ChatRunRegistry.spawn` 同 sid 已有未完成 task → `RuntimeError` → 409（协作式双提交守卫）。
- **HITL resume 不撞车**：走唯一 `WakeupDispatcher` 串行 spawn，resume 在 parked run 释放锁前退避重排（`_wakeup_dispatcher.py` L256–271, L323–375）。
- **异常吞掉**：`ChatService.run` try/except 仅记录日志（`_chat.py` L211–221），不拖垮触发方（HTTP 任务/dispatcher）。
- **持久化一致性**：`finally` 内 `_persist` 用 `asyncio.shield` 保证锁释放前落盘（`_chat.py` L616–645）。
- **进程崩溃/重连**：运行锁 TTL 自动释放；前端重连接上 live + replay。

## 11. 设计权衡

- **fire-and-forget vs 同步流**：长任务、跨进程、可重连、HITL 统一走事件机制。
- **两路触发非对称**：新消息直接 spawn（registry 单飞=409 守卫）；HITL 经队列（dispatcher 串行，避免 resume 撞 parked run）。
- **200 started vs 真实结果**：HTTP 只确认"已点火"，结果靠 SSE——解耦请求生命周期与运行生命周期。

## 12. 面试沉淀

### 一句话回答
`POST /chat/` 是 Agent 运行的异步触发器：新消息直接 spawn 进 `ChatRunRegistry`（单 session 单飞，重复提交 409），HITL 确认则 enqueue 到 wakeup 队列由 `WakeupDispatcher` 串行进 resume；运行事件不从此接口返回，而是经 SSE 回流。

### 白板流程
```text
POST /chat/
  ├─ HITL event? → resolve(worker) → enqueue(RESUME) → 202-equivalent started
  └─ Msg/None?   → ChatRunRegistry.spawn(ChatService.run) → 409 if busy
        → run: acquire_lock → Agent.reply_stream → publish_session_event → SSE
```

### 高频追问
1. 为什么不在 POST 里直接返回流？——长任务 + 跨进程，请求生命周期 ≠ 运行生命周期。
2. 409 怎么来的？——registry 单飞守卫，协作式双提交防护。
3. HITL resume 为什么不也直接 spawn？——避免和 worker 仍在收尾的 parked run 撞 409，dispatcher 串行 + 退避重排。
4. POST 返回 200 就成功了吗？——只表示"已点火"，run 内 404/异常在后台，靠 SSE/日志体现。
5. leader 确认怎么到 worker？——`SubagentHitlProjector.resolve` 按 reply_id 找 worker session。

### 对比题
- 同步问答 vs fire-and-forget + SSE
- 直接 spawn vs enqueue+dispatcher（新消息 vs HITL resume）
- 数据库唯一约束 vs 进程内 registry 单飞

### 项目表达
"我们的 Chat 接口是 fire-and-forget：POST 只负责点火，返回 started。新消息直接 spawn 进 registry 保证单 session 单飞，重复点就 409；HITL 确认走 wakeup 队列由唯一 dispatcher 串行进 resume，这样 resume 不会和 worker 还在收尾的 parked run 撞车。真正的事件全走 SSE，前后端完全解耦。"
