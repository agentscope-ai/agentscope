# 接口：`POST /sessions/{session_id}/interrupt`

## 1. 结论先行

`POST /sessions/{session_id}/interrupt` 是 Stop 按钮的后端入口，返回 `202 Accepted`（异步生效）。它按 session 是否持锁分两路：`running`（锁被持有）→ 广播 `session_interrupt_channel`，由持有进程的 `CancelDispatcher` 找到本地 task 调 `cancel()`，agent 在 `CancelledError` 清理路径生成 INTERRUPTED 收尾；`not running`（parked on HITL）→ enqueue `UserInterruptEvent` 经 `WakeupDispatcher` resume，agent 短路关闭 pending tool call。整条链路**幂等、跨进程、状态一致**，idle 目标是静默 no-op。

---

## 2. 用户场景

Web UI 聊天页：Assistant 正在回复或停在确认卡时，Send 按钮切换为 Stop（`TextInput`），用户点击 → `useMessages.interrupt` → `sessionApi.interrupt` → `POST /sessions/{sid}/interrupt`。Stop 不是终止 HTTP 请求（真实运行不在 POST 里），而是请求后端取消/唤醒关闭，UI 收尾由 SSE 的 `ReplyEndEvent` 驱动（10s 兜底防丢帧）。

---

## 3. 前端链路

```text
TextInput (Send→Stop)
  → useMessages.interrupt                    # useMessages.ts L406-424
  → phase: streaming → interrupting (+10s 兜底 timer)
  → sessionApi.interrupt(sessionId, agentId) # api/session.ts L39-42
  → POST /sessions/{sid}/interrupt
  ← SSE ReplyEndEvent → clearInterruptTimer + phase=idle
```
关键 React state：`phase`（`idle|streaming|interrupting`）、`interruptTimerRef`（10s 兜底，`useMessages.ts` L76, L413–416）。`sessionApi.interrupt` 发 `POST .../interrupt` 带 `agent_id` query，返回 `InterruptSessionResponse`（`session.ts` L39–42）。

---

## 4. HTTP 设计

- **method**：`POST`
- **path**：`/sessions/{session_id}/interrupt`
- **query**：`agent_id`（归属 agent，用于资源校验）
- **body**：无（`null`）
- **response**：`InterruptSessionResponse { session_id }`
- **status code**：`202 ACCEPTED`（`_session.py` L381）；`404` 当 session 不存在（`LookupError` → 404，L412–418）
- **幂等性**：幂等。idle 目标是 agent 层静默 no-op；running 重复 interrupt 只是重复广播 cancel（task 已 done 则 `CancelDispatcher` 跳过）。
- **202 语义**：已接受中断请求、异步生效，真正的 `ReplyEndEvent` 经 SSE 到达，而非同步返回。

## 6. 数据模型

- **Request**：path `{session_id}` + query `agent_id`；无 body
- **Response**：`InterruptSessionResponse(session_id: str)`（`_session.py` L31 schema）
- **Event 输出（异步，经 SSE）**：`ToolResultEndEvent(state=INTERRUPTED)`、`ReplyEndEvent(finished_reason=INTERRUPTED)`
- **State 变化**：`ToolCallState.FINISHED` + `ToolResultState.INTERRUPTED`（pending tool call 被关闭）、`ReplyEndReason.INTERRUPTED`

---

## 7. 状态变化

| 变化 | 位置 |
|---|---|
| running 路径 | `session_interrupt_channel` 广播 → `ChatRunRegistry` task 被 `cancel()` |
| parked 路径 | wakeup 队列写入 `UserInterruptEvent`（RESUME） |
| Agent 收敛 | `AgentState.context` 尾部 assistant 的 awaiting tool call 改为 `ToolResultBlock(INTERRUPTED)` |
| 回复结束 | `ReplyEndEvent(INTERRUPTED)` 经 `publish_session_event` 入 replay-log + live |
| 持久化 | `finally` 内 `upsert_message` + `update_session_state` + `log_trim`（在锁释放前，`_chat.py` L616–645）|

---

## 8. 事件回流

- HTTP 仅返回 `202 {session_id}`。
- 真正的终止事件 `ReplyEndEvent(INTERRUPTED)`（及 `ToolResultEndEvent(INTERRUPTED)`）由 `Agent.reply_stream` 产出 → `publish_session_event` → 前端 SSE 接收 → `useMessages.processEvent` 把 `phase` 从 `interrupting`/`streaming` 置 `idle`（`useMessages.ts` L198–204）。
- 若终止事件丢失：前端 10s `interruptTimerRef` 兜底回 `idle`（L413–416）。

---

## 9. 并发、异常与一致性

- **跨进程**：publisher 只广播 `{session_id}`，每个进程 `CancelDispatcher` 订阅；只有 `registry.get(sid)` 非 None 且未完成的进程才真正 `cancel()`，其余 no-op（`_cancel_dispatcher.py` L239–246）。
- **区分 chat-run 与 BG task**：`_interrupt_session` **只 cancel chat-run task，不 cancel BG tasks**（区别于 `_cancel_session`，L227–246）。
- **收敛一致**：running 与 parked 两路都收敛到 `_reply_impl` 的 `finally` INTERRUPTED 分支（`_agent.py` L900–914），interrupted 结果语义统一。
- **幂等/no-op**：idle（`has_awaiting_tool_calls=False`）→ `end_event=None` → finally 不 yield（`_agent.py` L700–712）。
- **持久化一致性**：`finally` 内 `shield(_persist)` 保证锁释放前落盘（`_chat.py` L616–645）。
- **进程崩溃**：运行锁 TTL 释放；前端重连重放。

## 11. 设计权衡

- **cancel vs interrupt 分离**：running 实时 kill（跨进程广播找持有者），parked 事件驱动关闭（走唤醒队列）。
- **协作式取消 vs 强杀**：只用 `task.cancel()` + `CancelledError` 清理，保证 partial context 被安全关闭，不破坏 state。
- **202 vs 200**：异步生效、事件驱动收尾，比同步返回更符合长任务语义。
- **跨进程广播自选举**：publisher 无状态，持有者自取消，扩展性佳。

## 12. 面试沉淀

### 一句话回答
`POST /sessions/{sid}/interrupt` 返回 202，按 session 是否持锁分两路：running 走跨进程 `CancelDispatcher` 找到本地 task 调 `cancel()`，agent 在 `CancelledError` 的 `finally` 把 pending tool call 标 INTERRUPTED 并结束；parked 则投 `UserInterruptEvent` 经唤醒队列让 agent 短路关闭；idle 是静默 no-op。整条链路幂等、跨进程、状态一致。

### 白板流程
```text
POST /interrupt (202)
  ├─ locked? → publish(interrupt_channel) → CancelDispatcher → task.cancel()
  │             → Agent CancelledError → finally: 关闭tool call(INTERRUPTED)+ReplyEnd(INTERRUPTED)
  └─ not locked? → enqueue(RESUME, UserInterruptEvent) → WakeupDispatcher(退避重排)
                   → Agent: has_awaiting? → ReplyEnd(INTERRUPTED) : no-op
```

### 高频追问
1. 为什么不直接 kill 进程里的 task？——跨进程，持有者可能不在这个进程。
2. interrupted tool result 何时生成？——`finally` 的 `_close_unfinished_tool_calls`，不丢半截。
3. idle 为何是 no-op？——无 awaiting tool call，`end_event=None`，finally 不 yield。
4. 为什么 202 不是 200？——异步生效，收尾靠 SSE 的 `ReplyEndEvent`。
5. 前端怎么知道停了？——`ReplyEndEvent` 驱动 `phase`，10s 兜底防丢帧。

### 对比题
- Cancel（running kill）vs Interrupt（parked event）
- 强杀进程 vs 协作式 `task.cancel()`
- 同步返回 vs 202 + SSE

### 项目表达
"我们的 Stop 设计核心是 cancel/interrupt 分离。运行中的任务通过 MessageBus 广播找到持有进程的 task 调 cancel，agent 在 CancelledError 的 finally 里把没完成的工具调用标记成 INTERRUPTED 并干净收尾。Parked 在 HITL 的回复则投一个 UserInterruptEvent 走唤醒队列去短路关闭。两条路最终都收敛到同一个 INTERRUPTED 收尾逻辑，状态永远一致。HTTP 返回 202，真正的结束事件经 SSE 到达，前端有 10 秒兜底防丢帧。"
