# 错误处理与异常语义地图

> 面试定位：成熟的 Agent 系统不能只讲 happy path。这里整理 AgentScope 中常见的错误语义：HTTP 状态码、资源不可见、运行态异常、事件丢失、worker 崩溃、工具失败、RAG 索引失败和前端兜底。

---

## 1. 错误处理的总原则

AgentScope 的错误处理可以概括为：

```text
同步接口明确失败
  -> 404 / 409 / 422 / 204 等 HTTP 语义

异步运行不中断入口
  -> ChatService.run 记录异常，事件流/状态负责恢复

可恢复状态优先落盘
  -> finally + shield 保护持久化

前端不只相信 HTTP
  -> SSE / polling / refetch / timeout 共同修正 UI 状态
```

中文说明：Agent 系统里很多失败发生在 HTTP 返回之后，所以不能只靠 HTTP status 表达业务终态。

---

## 2. HTTP 层错误语义

| 状态码 | 语义 | 示例 |
|---|---|---|
| 201 | 已创建 | 创建 session、credential、agent、schedule |
| 202 | 已接收，异步生效 | interrupt session |
| 204 | 删除成功，无返回体 | 删除 session、agent、credential |
| 404 | 资源不存在或不可见 | session/agent/credential/kb 不存在，或共享不可见 |
| 422 | 请求体 schema 不合法 | FastAPI / Pydantic 自动校验 |

面试表达：

```text
404 在这里不只是“不存在”，也常表示“对当前用户不可见”。
中文：这是资源隔离和安全设计，避免暴露别人资源是否存在。
```

---

## 3. 资源访问错误

资源访问统一经过 `ResourceAccessService`：

```text
自己的资源
  -> 可读/可写

共享资源
  -> 可读，credential 会脱敏，editable=false

不可见资源
  -> 404
```

知识延伸：

```text
为什么不返回 403？
中文：如果返回 403，攻击者可以知道资源 id 存在；返回 404 可以隐藏资源存在性。
```

---

## 4. Chat 运行异常

`ChatService.run` 是 fire-and-forget 触发后的后台运行入口。它不能把异常同步返回给 `POST /chat/`，因为 HTTP 可能早已返回。

因此它采用：

```text
run()
  -> try _run_impl()
  -> except Exception
  -> logger.exception(...)
```

关键点：

```text
1. 不让单次失败撕裂触发源。
2. 运行状态通过事件和持久化恢复。
3. finally 中仍要落盘 agent.state。
```

建议面试延伸：

```text
如果要增强用户可见性，可以把 run failure 转成 CustomEvent 或错误消息事件，让前端明确展示。
```

---

## 5. 事件流异常

SSE 连接可能断开、代理可能丢帧、前端可能刷新。

AgentScope 的恢复手段：

```text
Replay log
中文：新连接先读取 session_events replay log。

Live pub/sub
中文：随后订阅实时事件。

Heartbeat
中文：每 30 秒发送注释帧，防止连接被代理断开。

History fetch
中文：前端先拉 persisted messages，再接 SSE。
```

知识延伸：

```text
事件流系统常见组合是：持久化历史 + 短 replay log + live stream。
中文：历史负责最终状态，replay log 负责补运行中事件，live stream 负责低延迟。
```

---

## 6. 工具失败

工具失败可以表现为：

```text
ToolResponse(state=ERROR)
中文：工具自身返回错误结果，Agent 可继续 reasoning。

Exception
中文：中间件/执行层捕获后转成错误或让 span 标 ERROR。

Background task failed
中文：ToolOffloadMiddleware watcher 记录 warning，不投递结果。
```

面试点：

```text
工具失败不等于整个 Agent run 失败。
中文：合理设计应该让模型看到工具错误，并决定是否重试、换工具或向用户解释。
```

---

## 7. RAG 索引失败

RAG 的错误主要发生在异步 worker：

```text
上传成功
  -> 只是文档和 blob 登记成功

索引失败
  -> document status 变 failed
  -> 前端轮询看到失败
```

知识延伸：

```text
上传接口不能承诺“文档可检索”。
中文：它只能承诺“文档已进入索引流程”。真正是否可检索取决于 worker 解析、分块、embedding、向量库写入。
```

---

## 8. 前端错误兜底

前端常见兜底：

```text
loading/error state
中文：接口失败直接展示错误。

phase timeout
中文：interrupt 后 10 秒没收到 ReplyEnd，恢复 idle。

refetch
中文：更新 session/model/credential 后重新拉列表。

polling
中文：知识库文档状态异步变化，需要轮询。
```

面试表达：

```text
前端不是被动显示后端结果，而是用状态机对异步系统做体验补偿。
```

---

## 9. 面试沉淀

### 一句话回答

AgentScope 的错误处理分同步和异步两层：资源类接口用 HTTP 状态码明确表达，异步 Agent run 则通过日志、事件流、持久化状态、replay 和前端兜底来恢复一致性。

### 3 分钟讲解版

```text
我看 AgentScope 的错误处理会分层理解。资源接口，比如 agent、credential、session、knowledge base，主要用 HTTP 语义表达，404 同时表示不存在或当前用户不可见。Chat run 不一样，它是 fire-and-forget，POST 返回后真正运行在后台，所以异常不能同步返回，只能在 ChatService.run 中记录，并依靠事件和持久化状态恢复。事件流层面，SSE 断开后会先读 replay log，再接 live pub/sub；前端也会先拉历史消息。RAG 上传也是异步语义，上传成功不代表可检索，索引失败通过 document status 暴露。整体思路是：同步接口明确失败，异步流程用状态和事件表达终态。
```

### 高频追问

| 追问 | 回答方向 |
|---|---|
| 为什么共享资源不可见返回 404？ | 避免泄露资源存在性。 |
| ChatService.run 异常怎么返回前端？ | 当前主要记录日志；业务终态依赖事件和状态，后续可增强错误事件。 |
| SSE 丢了怎么办？ | 历史消息 + replay log + live subscribe + 前端兜底。 |
| 上传文档成功能马上检索吗？ | 不能，上传只是进入异步索引流程。 |
| 工具失败会终止 Agent 吗？ | 不一定，工具错误可作为 ToolResponse 交给模型继续决策。 |
