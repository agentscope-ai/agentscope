## 一、核心概念

### 1.1 什么是计划模式？

**计划模式（Planning）** 是 Agent 将复杂请求拆分成**离散、有序、可追踪步骤**的方式。

AgentScope 提供了一组内置工具，让 Agent 通过普通的工具调用来维护一份**显式、结构化的任务清单**：

```
┌─────────────────────────────────────────────────────────────┐
│                    计划模式全景                                │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  TaskCreate  │  │   TaskGet    │  │  TaskList    │      │
│  │  (创建任务)   │  │  (获取任务)   │  │  (列出任务)   │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  TaskUpdate  │  │  Task 模型   │  │ TaskContext  │      │
│  │  (更新任务)   │  │  (数据结构)   │  │  (存储层)    │      │
│  └──────────────┘  └──────────────┘  └──────────────      │
└─────────────────────────────────────────────────────────────┘
```

**关键理解** 🔴：
- **显式任务清单**：任务通过工具调用创建、查询、更新
- **状态注入式工具**：四个工具都设置 `is_state_injected = True`，直接读写 `agent.state.tasks_context`
- **以 Agent 为作用域**：任务清单随 Agent 的其余持久化状态一同跨越推理步骤、ReAct 轮次以及 HITL 暂停而保留
- **适用场景**：跨越三步以上的非平凡步骤、涉及子任务之间的依赖，或需要把进度对用户可见时

---

### 1.2 为什么需要计划模式？

| 需求 | 没有计划模式 | 有计划模式 |
|------|-------------|-----------|
| 复杂任务 | Agent 容易迷失方向 | 结构化任务清单跟踪进度 |
| 任务依赖 | 无法表达先后关系 | `blocks` / `blocked_by` 依赖边 |
| 进度可见 | 用户不知道做到哪了 | `TaskList` 展示全局状态 |
| 断点恢复 | 丢失工作进度 | 任务状态随 AgentState 持久化 |
| 多步骤协调 | 容易遗漏步骤 | 显式创建、标记完成 |

**核心矛盾**：
- LLM 擅长单步推理，但不擅长长期规划
- 复杂任务需要显式的进度跟踪

**AgentScope 的解法**：通过工具调用维护结构化任务清单

## 二、核心接口

### 2.1 四个 Plan 工具

| 工具 | 操作 | 只读 | 说明 |
|------|------|------|------|
| `TaskCreate` | 向任务清单末尾追加新任务 | 否 | 提供 `subject` 和 `description`，ID 为单调递增数字串 |
| `TaskGet` | 按 ID 获取单个任务的完整信息 | 是 | 返回描述、状态、依赖等完整信息 |
| `TaskList` | 列出所有任务及其状态 | 是 | 返回紧凑摘要，含 owner、阻塞关系 |
| `TaskUpdate` | 更新任务的状态、字段或依赖边 | 否 | 亦可删除任务（硬删除） |

### 2.2 使用示例

```python
from agentscope.agent import Agent
from agentscope.tool import Toolkit, TaskCreate, TaskGet, TaskList, TaskUpdate

toolkit = Toolkit(
    tools=[
        TaskCreate(),
        TaskGet(),
        TaskList(),
        TaskUpdate(),
    ],
)

agent = Agent(
    name="planner",
    system_prompt="You are a planning assistant.",
    model=model,
    toolkit=toolkit,
)
```

> **注**：每个工具的 `description` 已包含详细 prompt，无需额外的 system prompt 工程。`check_permissions()` 硬编码为 `ALLOW`，因为 plan 工具是纯内存状态变更。

## 三、设计原理

### 3.1 任务生命周期

```
1. 登记工作：收到新指令时，调用 TaskCreate 为每个离散步骤创建任务
2. 查看队列：调用 TaskList 获取紧凑摘要，挑选下一个可做的任务
3. 认领并开始：调用 TaskUpdate 将任务的 status 置为 in_progress
4. 获取完整上下文：调用 TaskGet 获取特定任务的完整描述和依赖边
5. 完成或重新规划：完成时调用 TaskUpdate 将状态翻转为 completed
```

**状态流转**：
```
pending → in_progress → completed
              ↓
           deleted（硬删除，任意状态均可）
```

---

### 3.2 依赖关系

任务暴露两条对称的依赖边：

| 字段 | 说明 |
|------|------|
| `blocks` | 在本任务完成前不能开始的任务 ID 列表 |
| `blocked_by` | 必须在本任务开始前完成的任务 ID 列表 |

使用 `TaskUpdate` 的 `add_blocks` 与 `add_blocked_by` 参数可**自动修改两端**，保持数据一致：

```python
# 让任务 "2" 依赖任务 "1"
await TaskUpdate()(
    task_id="2",
    add_blocked_by=["1"],
    _agent_state=agent.state,
)
```

> **注**：依赖边是协调信号，执行层面仅建议性，运行时不会硬性阻止模型去做被阻塞的任务。任务被删除时，其 ID 会自动从其他任务的依赖中移除。

### 3.3 数据结构

```python
# src/agentscope/state/_task.py:11
class Task(BaseModel):
    id: str                       # 单调递增的数字串
    subject: str                  # 一句话命令式描述
    description: str              # 详细的需求 / 上下文
    state: Literal["pending", "in_progress", "completed"] = "pending"
    owner: str | None = None
    blocks: list[str] = []        # 被本任务阻塞的任务 ID
    blocked_by: list[str] = []    # 阻塞本任务的任务 ID
    metadata: dict[str, Any] = {}
    created_at: str               # ISO-8601 时间戳

# src/agentscope/state/_state.py:141
class TaskContext(BaseModel):
    tasks: list[Task] = []
```

**存储特性**：
- **可被序列化保存**：调用 `agent.state_dict()` 会完整保存任务清单
- **以 Agent 为单位**：两个 Agent 默认不共享任务清单
- **可在 LLM 循环之外修改**：任何能拿到 `agent.state` 的代码都可以直接读写任务

### 4.2 TaskCreate 实现

```python
# src/agentscope/tool/_task/_create_task.py:83
async def call(self, _agent_state: AgentState, subject, description, metadata=None):
    """创建任务"""
    # 1. 计算下一个 ID（从现有任务中找最大数字 ID）
    max_numeric = 0
    for t in _agent_state.tasks_context.tasks:
        try:
            max_numeric = max(max_numeric, int(t.id))
        except (ValueError, TypeError):
            pass
    next_id = str(max_numeric + 1)
    
    # 2. 创建 Task 对象
    task = Task(
        id=next_id,
        subject=subject,
        description=description,
        metadata=metadata or {},
    )
    
    # 3. 添加到任务列表
    _agent_state.tasks_context.tasks.append(task)
    
    return ToolChunk(content=[TextBlock(text=f"Task (id={next_id}) created")])
```

**关键点** 🔴：
- ID 是单调递增的数字串（`"1"`, `"2"`, ...）
- 从现有任务中找最大数字 ID，兼容非数字 ID（如遗留 UUID）
- 直接修改 `agent.state.tasks_context`

### 4.3 TaskUpdate 实现

```python
# src/agentscope/tool/_task/_update_task.py:135
async def call(self, _agent_state, task_id, subject=None, description=None,
               add_blocks=None, status=None, add_blocked_by=None,
               owner=None, metadata=None):
    """更新任务"""
    # 1. 查找任务
    index = None
    for i, task in enumerate(_agent_state.tasks_context.tasks):
        if task.id == task_id:
            index = i
    
    if index is None:
        return ToolChunk(content=[TextBlock(text="Task not found")], state=ERROR)
    
    # 2. 更新字段
    if subject:
        _agent_state.tasks_context.tasks[index].subject = subject
    
    # 3. 更新依赖边（自动同步两端）
    if add_blocks:
        for block_id in add_blocks:
            self._update_block_relation(task_id, block_id, _agent_state)
    
    if add_blocked_by:
        for blocked_by_id in add_blocked_by:
            self._update_block_relation(blocked_by_id, task_id, _agent_state)
    
    # 4. 删除任务（硬删除）
    if status == "deleted":
        _agent_state.tasks_context.tasks.pop(index)
        # 从其他任务的依赖中移除
        for task in _agent_state.tasks_context.tasks:
            if task_id in task.blocks:
                task.blocks.remove(task_id)
            if task_id in task.blocked_by:
                task.blocked_by.remove(task_id)
        return ToolChunk(content=[TextBlock(text=f"Task deleted")])
    
    # 5. 更新状态
    if status:
        _agent_state.tasks_context.tasks[index].state = status
```

**关键点** 🔴：
- `_update_block_relation()` 自动同步 `blocks` 和 `blocked_by` 两端
- 删除任务时自动清理其他任务的依赖边
- 支持部分更新（只传需要更新的字段）

---

### 4.4 依赖边同步机制

```python
# src/agentscope/tool/_task/_update_task.py:271
@staticmethod
def _update_block_relation(block_id, blocked_by_id, _agent_state):
    """同步更新依赖边的两端"""
    for task in _agent_state.tasks_context.tasks:
        # 更新 block_id 的 blocks 字段
        if task.id == block_id and blocked_by_id not in task.blocks:
            task.blocks.append(blocked_by_id)
        
        # 更新 blocked_by_id 的 blocked_by 字段
        if task.id == blocked_by_id and block_id not in task.blocked_by:
            task.blocked_by.append(block_id)
```

**关键点** 🔴：
- 一次调用同步更新两个任务的依赖字段
- 避免重复添加（检查 `not in`）
- 保持数据一致性

### 4.6 关键技术点

| 技术 | 作用 | 实现方式 |
|------|------|---------|
| **状态注入** | 工具直接访问 Agent 状态 | `is_state_injected = True` |
| **恒放行权限** | Plan 工具无需用户确认 | `check_permissions() → ALLOW` |
| **单调递增 ID** | 任务 ID 自动计算 | 从现有任务中找最大数字 ID |
| **依赖边同步** | 保持 blocks/blocked_by 一致 | `_update_block_relation()` |
| **硬删除** | 删除任务并清理依赖 | `status = "deleted"` |
| **序列化持久化** | 任务随 AgentState 保存 | `TaskContext` 是 Pydantic 模型 |

**Task 数据模型**（`state/_task.py`）：

> Task 是计划模式的核心数据结构，每个任务包含标题、描述、状态、依赖关系等信息。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `str` | 单调递增数字串（"1", "2", ...），由 TaskCreate 自动计算 |
| `subject` | `str` | 命令式标题（如 "修复登录 bug"） |
| `description` | `str` | 详细描述（任务的具体要求和上下文） |
| `status` | `Literal["pending", "in_progress", "completed"]` | 任务状态（默认 pending） |
| `owner` | `str \| None` | 拥有者（Agent 名称，用于多 Agent 协作） |
| `blocks` | `list[str]` | 被本任务阻塞的任务 ID 列表（本任务完成后它们才能开始） |
| `blocked_by` | `list[str]` | 阻塞本任务的任务 ID 列表（这些任务完成后才能开始本任务） |
| `metadata` | `dict[str, Any]` | 任意元数据（如来源、优先级等） |
| `created_at` | `str` | ISO-8601 创建时间戳 |

## 七、面试题

### 7.1 基础题

#### Q1: 计划模式的核心职责是什么？

**参考答案**：
> 计划模式让 Agent 将复杂请求拆分成离散、有序、可追踪的步骤。通过四个内置工具（TaskCreate/TaskGet/TaskList/TaskUpdate）维护显式任务清单，支持任务依赖管理和状态持久化。

**关键点**：
- 显式任务清单
- 四个内置工具
- 依赖管理

---

#### Q2: 四个 Plan 工具分别做什么？

**参考答案**：
> - `TaskCreate`：创建新任务，ID 单调递增
> - `TaskGet`：按 ID 获取任务详情
> - `TaskList`：列出所有任务摘要
> - `TaskUpdate`：更新状态/字段/依赖边，或删除任务

**关键点**：
- 创建/获取/列表/更新
- ID 单调递增
- 支持硬删除

---

#### Q3: 任务状态有哪些？

**参考答案**：
> 任务状态有三种：`pending`（待办）、`in_progress`（进行中）、`completed`（已完成）。此外还有 `deleted` 用于硬删除任务。状态流转：`pending → in_progress → completed`，任意状态均可转为 `deleted`。

**关键点**：
- 三种正常状态
- `deleted` 硬删除
- 单向流转

---

### 7.2 进阶题

#### Q4: 依赖边是如何管理的？

**参考答案**：
> 任务暴露两条对称的依赖边：`blocks`（本任务完成后才能开始的任务）和 `blocked_by`（必须在本任务开始前完成的任务）。`TaskUpdate` 的 `add_blocks` 和 `add_blocked_by` 参数通过 `_update_block_relation()` 自动同步两端，保持数据一致。

**关键点**：
- 两条对称依赖边
- `_update_block_relation()` 同步
- 数据一致性

---

#### Q5: 状态注入是如何实现的？

**参考答案**：
> 四个 Plan 工具都设置 `is_state_injected = True`。当 `Toolkit.call_tool()` 执行工具时，会将 `AgentState` 作为 `_agent_state` 参数注入。工具直接读写 `agent.state.tasks_context.tasks` 来管理任务。

**关键点**：
- `is_state_injected = True`
- `_agent_state` 参数
- 直接读写 `tasks_context`

---

#### Q6: 任务是如何持久化的？

**参考答案**：
> `TaskContext` 是 Pydantic 模型，包含 `tasks: list[Task]`。它作为 `AgentState` 的字段，随 AgentState 一起序列化保存。调用 `agent.state_dict()` 会完整保存任务清单，恢复 state 时计划一并恢复。

**关键点**：
- Pydantic 模型
- 随 AgentState 序列化
- 断点恢复

---

#### Q7: 删除任务时依赖边是如何清理的？

**参考答案**：
> 当任务状态设为 `deleted` 时，`TaskUpdate` 会从任务列表中移除该任务，并遍历所有其他任务，从它们的 `blocks` 和 `blocked_by` 字段中移除被删除任务的 ID。这确保了依赖关系的一致性。

**关键点**：
- 从列表中移除
- 清理其他任务的依赖
- 保持一致性

---

### 7.3 场景题

#### Q8: 如何预置任务？

**参考答案**：
> 在 Agent 第一次 reply 之前，直接编程方式修改 `agent.state.tasks_context.tasks`：

```python
agent.state.tasks_context.tasks.extend([
    Task(id="1", subject="...", description="..."),
    Task(id="2", subject="...", description="...", blocked_by=["1"]),
])
agent.state.tasks_context.tasks[0].blocks.append("2")
```

**关键点**：
- 直接修改 `tasks_context`
- 手动保持依赖边双向一致
- 使用数字串 ID

---

#### Q9: 计划模式与 ReAct 循环的关系是什么？

**参考答案**：
> 计划模式是 ReAct 循环的补充。Agent 在 ReAct 循环中通过工具调用管理任务清单。任务清单帮助 Agent 在多次推理-行动轮次中保持方向，避免迷失。任务状态随 AgentState 跨轮次保留。

**关键点**：
- 补充 ReAct 循环
- 通过工具调用管理
- 跨轮次保留

---

#### Q10: 依赖边是强制性的吗？

**参考答案**：
> 不是。依赖边是协调信号，执行层面仅建议性。运行时不会硬性阻止模型去做被阻塞的任务。这是设计上的权衡：保持灵活性，让 LLM 可以根据实际情况调整执行顺序。

**关键点**：
- 建议性，非强制性
- 保持灵活性
- LLM 可调整顺序

### 7.1 基础概念题（必问）

#### Q1: ReAct 和 Plan-and-Execute 的本质区别是什么？如何选择？（字节、腾讯高频）

**参考答案**：
> **ReAct（Reasoning + Acting）**：边想边做，每一步都重新推理
> **Plan-and-Execute**：先规划再执行，规划一次后按步骤执行
>
> **核心区别**：
>
> | 维度 | ReAct | Plan-and-Execute |
> |------|-------|------------------|
> | **推理方式** | 每步重新推理（一步一想） | 先全局规划，再逐步执行 |
> | **灵活性** | 高（可根据中间结果调整） | 低（计划固定，难以调整） |
> | **Token 消耗** | 高（每步都推理全局） | 低（规划一次，执行用便宜模型） |
> | **延迟** | 高（每步都等 LLM） | 低（执行步骤可并行） |
> | **适用场景** | 任务步骤不确定、需要灵活调整 | 步骤固定、执行顺序明确 |
> | **失败模式** | Token 浪费、路径混乱 | 计划错误难以修正 |
>
> **如何选择**：
>
> | 场景 | 推荐方案 | 原因 |
> |------|---------|------|
> | 任务步骤不确定 | ReAct | 需要根据中间结果灵活调整 |
> | 步骤有强依赖、顺序固定 | Plan-and-Execute | 计划一次后按步骤执行 |
> | 需要降低成本 | Plan-and-Execute | 执行步骤可用便宜模型 |
> | 需要高灵活性 | ReAct | 每步都可调整策略 |
>
> **2026 年趋势**：混合使用（Plan-and-Execute 做全局规划，ReAct 做每步内的灵活执行）

**追问**：
- ReAct 的 Token 消耗为什么高？→ 每步都推理全局上下文
- Plan-and-Execute 的计划错误如何修正？→ 重新规划或人工介入
- 如何评估两种模式的效果？→ 任务完成率、Token 消耗、延迟

**面试加分点**：
- 提到 ReAct 的"一步一想" vs Plan-and-Execute 的"先全局规划"
- 提到混合使用策略（Plan-and-Execute + ReAct）

#### Q2: 四种 Agent 设计模式是什么？各自适用什么场景？（阿里高频）

**参考答案**：
> **四种 Agent 设计模式**（Andrew Ng 提出）：
>
> | 模式 | 核心思想 | 适用场景 | 失败模式 |
> |------|---------|---------|---------|
> | **ReAct** | 边想边做，每步重新推理 | 任务步骤不确定、需要灵活调整 | Token 浪费、路径混乱 |
> | **Plan-and-Execute** | 先规划再执行，规划一次 | 步骤固定、执行顺序明确 | 计划错误难以修正 |
> | **Reflection** | 自我反思校正，迭代优化 | 高质量输出（代码、法律文书） | 延迟高、迭代次数多 |
> | **Multi-Agent** | 多 Agent 协作，分工合作 | 复杂任务、需要多角色协作 | 协调成本高、通信开销 |

> **Reflection 详解**：

> 2. 自我评估（LLM 评估输出质量）

> 2. 角色分配（每个 Agent 负责一个子任务）
> 3. 并行执行（多个 Agent 同时工作）
> 4. 结果聚合（合并各 Agent 的输出）
> ```
>
> **如何选择**：
>
> | 任务类型 | 推荐模式 | 原因 |
> |---------|---------|------|
> | 简单问答 | ReAct | 快速响应，无需复杂规划 |
> | 多步骤任务 | Plan-and-Execute | 计划一次，按步骤执行 |
> | 高质量输出 | Reflection | 自我反思，迭代优化 |
> | 复杂项目 | Multi-Agent | 分工合作，并行执行 |

#### Q3: 计划模式的核心职责是什么？AgentScope 如何实现计划模式？

**参考答案**：
> 计划模式负责将复杂任务拆分成离散、有序、可追踪的步骤，核心职责：
>
> | 职责 | 实现方式 | 目的 |
> |------|---------|------|
> | **任务创建** | `TaskCreate` 工具 | 将任务拆分为子任务 |
> | **任务查询** | `TaskGet` 工具 | 获取任务详情 |
> | **任务列表** | `TaskList` 工具 | 查看所有任务状态 |
> | **任务更新** | `TaskUpdate` 工具 | 更新任务状态、依赖 |
> | **依赖管理** | `blocks` / `blocked_by` | 表达任务间的先后关系 |

> 1. **显式任务清单**：任务通过工具调用维护，而非隐式在 LLM 记忆中

### 7.2 工程实现题（字节高频）

#### Q4: ReAct 的工作流程是什么？具体是如何实现的？

**参考答案**：
> **ReAct 工作流程**：
> ```
> 1. 接收用户问题
> 2. LLM 推理（Thought）：分析当前状态，决定下一步行动
> 3. LLM 行动（Action）：调用工具或生成回答
> 4. 观察结果（Observation）：获取工具返回结果
> 5. 检查是否完成：
>    - 未完成：回到步骤 2，继续推理
>    - 已完成：生成最终回答
> ```
>
> **关键细节**：
> 1. **每步重新推理**：每一步都重新分析全局上下文，决定下一步
> 2. **工具调用循环**：可多次调用工具，直到得出最终答案
> 3. **执行轨迹透明**：每一步的 Thought、Action、Observation 都记录，便于审计
>
> **代码示例**：
> ```python
> async def react_loop(query: str):
>     messages = [{"role": "user", "content": query}]
>     
>     while True:
>         # 1. LLM 推理
>         response = await llm.chat(messages, tools=tools)
>         
>         # 2. 检查是否有工具调用
>         if response.tool_calls:
>             # 3. 执行工具
>             for tool_call in response.tool_calls:
>                 result = await execute_tool(tool_call)
>                 
>                 # 4. 添加观察结果
>                 messages.append({
>                     "role": "assistant",
>                     "content": None,
>                     "tool_calls": [tool_call]
>                 })
>                 messages.append({
>                     "role": "tool",
>                     "content": result
>                 })
>         else:
>             # 5. 生成最终回答
>             return response.content
> ```
>
> **ReAct 的优缺点**：
>
> | 优点 | 缺点 |
> |------|------|
> | 灵活性高（每步可调整） | Token 消耗高（每步推理全局） |
> | 执行轨迹透明（便于审计） | 延迟高（每步等 LLM） |
> | 通用性强（适配多种任务） | 复杂任务易路径混乱 |

**追问**：
- ReAct 的 Token 消耗如何优化？→ 限制工具返回结果长度、使用便宜模型

#### Q5: Plan-and-Execute 的工作流程是什么？如何优化成本？

**参考答案**：
> **Plan-and-Execute 工作流程**：
> ```
> 1. 接收用户问题
> 2. LLM 规划（Planning）：生成完整的执行计划（步骤列表）
> 3. 逐步执行（Execution）：
>    - 按计划执行每个步骤
>    - 每个步骤可用便宜模型（如 GPT-3.5）
>    - 步骤间可并行执行
> 4. 结果聚合：合并各步骤的输出
> 5. 生成最终回答
> ```
>
> **成本优化策略**：
>
> | 策略 | 实现方式 | 效果 |
> |------|---------|------|
> | **模型路由** | 规划用强模型（GPT-4），执行用便宜模型（GPT-3.5） | 成本降低 10-20x |
> | **并行执行** | 无依赖的步骤并行执行 | 延迟降低 2-5x |
> | **结果缓存** | 相同步骤返回缓存结果 | 成本降低 30-50% |
> | **提前终止** | 检测到计划错误时提前终止 | 避免浪费 |
>
> **代码示例**：
> ```python
> async def plan_and_execute(query: str):
>     # 1. 规划（用强模型）
>     plan = await planner_llm.chat(
>         messages=[{"role": "user", "content": f"制定执行计划：{query}"}],
>         response_format={"type": "json_object"}
>     )
>     steps = json.loads(plan.content)["steps"]
>     
>     # 2. 逐步执行（用便宜模型）
>     results = []
>     for step in steps:
>         # 检查依赖
>         if not check_dependencies(step, results):
>             continue
>         
>         # 执行步骤（用便宜模型）
>         result = await executor_llm.chat(
>             messages=[{"role": "user", "content": step["instruction"]}],
>             tools=step.get("tools")
>         )
>         results.append(result)
>     
>     # 3. 结果聚合
>     final_answer = await aggregator_llm.chat(
>         messages=[{"role": "user", "content": f"聚合结果：{results}"}]
>     )
>     return final_answer.content
> ```
>
> **Plan-and-Execute 的优缺点**：
>
> | 优点 | 缺点 |
> |------|------|
> | Token 消耗低（规划一次） | 灵活性低（计划固定） |
> | 延迟低（步骤可并行） | 计划错误难以修正 |
> | 成本低（执行用便宜模型） | 不适用于不确定任务 |

- 如何检测计划错误？→ 步骤执行失败、结果不符合预期
- 如何评估 Plan-and-Execute 的效果？→ 任务完成率、成本、延迟

#### Q7: 如何处理计划模式的错误和异常？（腾讯高频）

**参考答案**：
> **计划模式的常见错误**：
>
> | 错误类型 | 原因 | 解决方案 |
> |---------|------|---------|
> | **计划错误** | LLM 生成的计划不合理 | 重新规划、人工调整 |
> | **执行失败** | 工具调用失败、API 超时 | 重试、降级、人工介入 |
> | **依赖循环** | 任务间形成循环依赖 | 检测循环、提示调整 |
> | **状态丢失** | AgentState 未持久化 | 定期保存、断点恢复 |
> | **路径混乱** | ReAct 每步重新推理导致路径混乱 | 使用计划模式、设置最大迭代 |
>
> **错误处理策略**：
>
> | 策略 | 实现方式 | 适用场景 |
> |------|---------|---------|
> | **重试机制** | 指数退避重试（1s → 2s → 4s → 8s） | 临时错误（API 超时、网络错误） |
> | **降级策略** | 强模型失败切换弱模型 | 模型错误（GPT-4 失败切换 GPT-3.5） |
> | **人工介入** | 关键错误暂停等待人工处理 | 复杂错误（计划错误、依赖循环） |
> | **提前终止** | 检测到计划错误时提前终止 | 避免浪费（连续失败 3 次） |
> | **回滚机制** | 执行失败时回滚到上一个状态 | 状态一致性（任务状态回滚） |
>
> **代码示例**：
> ```python
> async def execute_with_error_handling(task: Task):
>     max_retries = 3
>     retry_delay = 1.0
>     
>     for attempt in range(max_retries):
>         try:
>             # 执行任务
>             result = await execute_task(task)
>             return result
>         except TemporaryError as e:
>             # 临时错误：重试
>             if attempt == max_retries - 1:
>                 raise
>             await asyncio.sleep(retry_delay * (2 ** attempt))
>         except PermanentError as e:
>             # 永久错误：降级或人工介入
>             if task.critical:
>                 # 关键任务：人工介入
>                 await notify_human(task, e)
>                 raise
>             else:
>                 # 非关键任务：降级
>                 return await fallback_execute(task)
> ```
>
> **2026 年错误处理趋势**：
> 1. **智能重试**：根据错误类型自动选择重试策略
> 2. **自动降级**：强模型失败自动切换弱模型
> 3. **人工介入**：关键错误自动通知人工处理
> 4. **回滚机制**：执行失败自动回滚到上一个状态

## 八、最佳实践

### 8.1 开发建议

1. **复杂任务才用计划**：三步以上的非平凡步骤才需要任务清单
2. **及时更新状态**：开始工作时标记 `in_progress`，完成时标记 `completed`
3. **使用依赖边**：有先后关系的任务设置 `blocks` / `blocked_by`
4. **定期查看列表**：完成一个任务后调用 `TaskList` 找下一个可用任务

---

### 8.2 性能优化

1. **避免重复创建**：创建前调用 `TaskList` 检查是否已存在
2. **合理设置 ID**：使用数字串 ID，便于 `TaskCreate` 自动计算下一个 ID
3. **及时删除无用任务**：不再需要的任务设为 `deleted`

---

### 8.3 安全建议

1. **权限恒放行**：Plan 工具是纯内存操作，无需用户确认
2. **状态注入安全**：只有 `is_state_injected = True` 的工具才能访问 AgentState
3. **依赖边一致性**：使用 `TaskUpdate` 的 `add_blocks` / `add_blocked_by` 而非直接修改
