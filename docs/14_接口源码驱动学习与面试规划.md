# AgentScope API 源码驱动学习与面试规划

> 目标：从 AgentScope 提供的 API 入手，沿着真实调用链阅读源码，逐步建立框架使用能力、源码理解能力和技术面试表达能力。

---

## 一、学习总原则

学习 AgentScope 不建议从源码目录逐个文件阅读，而应该从一个真实 API 场景出发：

```text
API 入口
  ↓
Router 参数校验与 HTTP 语义
  ↓
Service 业务编排
  ↓
Storage / MessageBus / Workspace / Model / Tool
  ↓
Agent Runtime 执行逻辑
  ↓
测试用例验证边界
  ↓
沉淀成面试表达
```

这种方式的优势是：

| 维度 | 收获 |
|---|---|
| 使用框架 | 知道 API 怎么调、对象怎么创建、状态怎么流转 |
| 理解源码 | 能顺着一次请求追完整调用链 |
| 工程能力 | 看到并发、持久化、取消、恢复、事件流等真实设计 |
| 面试表达 | 能把源码设计讲成系统设计、并发编程和工程实践案例 |

一句话总结：

> AgentScope 最值得学习的不是某个 API 怎么调用，而是它如何把一次 Agent 运行拆成“触发、锁定、执行、事件流、持久化、恢复、取消”这一整套分布式 Agent Runtime 设计。

## 二、API 学习地图

AgentScope 的后端 API 可以按产品使用链路理解：

```text
Credential / Model
        ↓
Agent 配置
        ↓
Session 创建
        ↓
Chat 触发运行
        ↓
Session Stream 接收事件
        ↓
Interrupt / HITL / Tool / RAG / Schedule 扩展能力
```

核心源码入口：

| API 模块 | Router 文件 | 学习重点 |
|---|---|---|
| Credential | `src/agentscope/app/_router/_credential.py` | API Key 管理、资源隔离、模型凭证抽象 |
| Model | `src/agentscope/app/_router/_model.py` | 可用模型发现、模型配置结构 |
| Agent | `src/agentscope/app/_router/_agent.py` | Agent 配置态、system prompt、React 配置 |
| Session | `src/agentscope/app/_router/_session.py` | 运行态、状态持久化、消息查询、事件流 |
| Chat | `src/agentscope/app/_router/_chat.py` | 异步触发、运行注册、HITL resume |

## 三、推荐学习顺序

### 第一阶段：基础资源 API

先学习：

```text
/credential
/model
/agent
```

重点问题：

1. Credential 如何把不同模型供应商的 API Key 抽象成统一资源？
2. Agent 是如何保存配置的？
3. `system_prompt`、`context_config`、`react_config` 分别影响运行时的哪一部分？
4. 用户资源隔离和共享访问是如何设计的？

推荐源码：

```text
src/agentscope/app/_router/_credential.py
src/agentscope/app/_router/_model.py
src/agentscope/app/_router/_agent.py
src/agentscope/app/_service/_access.py
src/agentscope/app/storage/_base.py
```

面试表达：

```text
AgentScope 把 Agent 定义和 Agent 运行分开。
Agent API 管配置，Session/Chat API 管运行。
这种设计让同一个 Agent 可以被多个 Session 复用，也方便做权限、分享和调度。
```

---

### 第二阶段：Session API 主线

重点 API：

```text
POST /sessions/
GET /sessions/
GET /sessions/{sid}/status
GET /sessions/{sid}/messages
```

重点问题：

1. 为什么 Session 是 Agent 的一次运行实例？
2. `workspace_id` 如何绑定执行环境？
3. Session state 为什么要持久化？
4. running 状态为什么来自 MessageBus lock，而不是只看数据库字段？
5. `RUNNING / HITL / IDLE` 这类状态如何由运行锁和上下文尾部状态推导出来？

推荐源码：

```text
src/agentscope/app/_router/_session.py
src/agentscope/app/_service/_session.py
src/agentscope/app/storage/_base.py
src/agentscope/app/storage/_model/_session.py
src/agentscope/state/_state.py
```

面试表达：

```text
Session 是运行态边界，Agent 是配置态边界。
运行状态不能只存在数据库里，因为分布式运行中进程可能崩溃。
AgentScope 用 MessageBus lock 表示实时运行态，用 Storage 表示持久状态。
```

---

### 第三阶段：Chat + Stream 主链路

重点 API：

```text
POST /chat/
GET /sessions/{sid}/stream
```

核心调用链：

```text
POST /chat/
   ↓
ChatRunRegistry.spawn
   ↓
ChatService.run
   ↓
MessageBus.acquire_lock
   ↓
Agent.reply_stream
   ↓
publish_session_event
   ↓
GET /sessions/{sid}/stream SSE 推给前端
   ↓
finally 中持久化 message + state + trim replay log
```

重点问题：

1. 为什么 `/chat/` 是 fire-and-forget？
2. 为什么事件不直接从 `/chat/` 返回，而是通过 `/sessions/{sid}/stream`？
3. SSE 和消息总线如何解耦请求生命周期？
4. 为什么每个 Session 需要分布式锁？
5. 为什么 `finally + asyncio.shield` 对状态一致性很关键？
6. replay log 为什么需要 trim？

推荐源码：

```text
src/agentscope/app/_router/_chat.py
src/agentscope/app/_router/_session.py
src/agentscope/app/_service/_chat.py
src/agentscope/app/_bus_ops.py
src/agentscope/app/message_bus/_base.py
src/agentscope/app/message_bus/_redis_message_bus.py
src/agentscope/agent/_agent.py
```

面试表达：

```text
AgentScope 的 Chat API 不是同步问答接口，而是异步运行触发器。
POST /chat 只负责启动任务，事件通过 SSE 独立订阅。
这样可以支持长任务、工具调用、HITL、人类确认、跨进程恢复和前端重连。
```

---

### 第四阶段：Interrupt / Cancel / HITL 高级控制

重点 API：

```text
POST /sessions/{sid}/interrupt
POST /chat/ 提交 UserConfirmResultEvent
POST /chat/ 提交 ExternalExecutionResultEvent
DELETE /sessions/{sid}
```

`interrupt` 核心流程：

```text
POST /sessions/{sid}/interrupt
   ↓
ChatService.interrupt
   ↓
判断 session 是否正在运行
   ├─ running:
   │    ↓
   │  publish interrupt channel
   │    ↓
   │  CancelDispatcher
   │    ↓
   │  task.cancel()
   │    ↓
   │  Agent 捕获 CancelledError
   │    ↓
   │  生成 interrupted tool result + ReplyEndEvent
   │
   └─ not running:
        ↓
      enqueue UserInterruptEvent
        ↓
      WakeupDispatcher resume
        ↓
      parked HITL 被关闭 / idle no-op
```

重点问题：

1. Cancel 和 Interrupt 为什么要分离？
2. 为什么 running 状态下走 `task.cancel()`，HITL parked 状态下走 `UserInterruptEvent`？
3. 为什么该接口适合返回 `202 Accepted`？
4. 为什么 idle session 的 interrupt 可以是 no-op？
5. `CancelledError` 清理路径如何生成 interrupted tool result？
6. 如果取消发生在工具执行、用户确认、外部执行等待中，状态如何收敛？

推荐源码：

```text
src/agentscope/app/_router/_session.py
src/agentscope/app/_service/_chat.py
src/agentscope/app/_manager/_cancel_dispatcher.py
src/agentscope/app/_manager/_wakeup_dispatcher.py
src/agentscope/app/_manager/_chat_run_registry.py
src/agentscope/agent/_agent.py
tests/agent_interrupt_test.py
tests/service_agent_interrupt_test.py
tests/service_cancel_dispatcher_test.py
```

面试表达：

```text
AgentScope 的 interrupt 不是简单杀线程。
它根据 session 是否持有运行锁分成两条路径：
运行中通过跨进程 broadcast 找到本地任务并 cancel；
非运行中通过 wakeup queue 投递 UserInterruptEvent，让 parked HITL 状态也能被一致地关闭。
这让 interrupt 具备跨进程、幂等、可恢复和状态一致性。
```

## 四、每个 API 的固定分析模板

以后学习任何 API，都按这个模板沉淀：

### 1. API 用途

这个接口解决什么用户问题？

### 2. HTTP 设计

关注：

```text
method
path
status code
query/body/header
幂等性
错误语义
404 / 409 / 202 / 204 的选择
```

### 3. 请求与响应模型

关注：

```text
Pydantic schema
字段默认值
字段约束
Union 类型
是否允许 None
是否有向后兼容字段
```

### 4. 完整调用链

用如下格式追踪：

```text
Router
  ↓
Service
  ↓
Storage / MessageBus / Workspace / Access
  ↓
Agent / Model / Toolkit / Middleware
  ↓
Event / State / Message
```

### 5. 状态变化

回答：

```text
写了哪些数据库记录？
更新了哪些 session state？
是否新增 message？
是否发布 event？
是否写入 queue / log / registry？
是否持有 lock？
```

### 6. 并发与一致性

重点看：

```text
是否允许重复请求？
是否有单 session 锁？
取消时是否能保证持久化？
跨进程如何通知？
异常是否会吞掉？
finally 中做了什么？
```

### 7. 测试证据

每个 API 至少找 1 到 3 个测试文件：

```text
tests/service_*_test.py
tests/*_test.py
```

从测试里提炼：

```text
正常路径
异常路径
并发路径
取消路径
边界状态
```

### 8. 面试输出

每个 API 最终沉淀为：

```text
一句话回答
架构图 / 调用链
设计权衡
对比题
追问题
源码证据
```

## 十、结合 Web UI 做前后端闭环分析

只分析后端 API，容易只看到“接口和源码”；结合 `examples/web_ui`，才能看到完整的产品形态：

```text
用户动作
  ↓
React 页面 / 组件
  ↓
Hook 管理前端状态
  ↓
API client 发起 HTTP / SSE
  ↓
FastAPI Router
  ↓
Service / MessageBus / Storage / Agent
  ↓
AgentEvent 返回 SSE
  ↓
Hook 合并事件为 Msg
  ↓
组件重新渲染
```

因此，后续每个 API 的学习单位应该从“单接口”升级为“用户流程”。

### 10.1 Chat 页面整体结构

前端聊天页核心文件：

```text
examples/web_ui/frontend/src/pages/chat/index.tsx
examples/web_ui/frontend/src/pages/chat/ChatViewport.tsx
examples/web_ui/frontend/src/hooks/useMessages.ts
examples/web_ui/frontend/src/api/chat.ts
examples/web_ui/frontend/src/api/session.ts
examples/web_ui/frontend/src/components/chat/ChatContent.tsx
examples/web_ui/frontend/src/components/chat/TextInput.tsx
examples/web_ui/frontend/src/components/chat/MessageBubble.tsx
examples/web_ui/frontend/src/components/chat/ConfirmCard.tsx
examples/web_ui/frontend/src/components/chat/SubagentHitlCard.tsx
```

职责拆分：

| 层级 | 文件 | 职责 |
|---|---|---|
| 页面路由层 | `pages/chat/index.tsx` | 从 URL 解析 `agentId/sessionId/memberId`，管理左侧 Agent / Session 列表 |
| 会话视图层 | `pages/chat/ChatViewport.tsx` | 管理单个 `(agentId, sessionId)` 的模型、权限、知识库、面板、消息区 |
| 状态 Hook | `hooks/useMessages.ts` | 拉历史消息、建立 SSE、处理事件、发送消息、HITL 确认、中断 |
| API 封装 | `api/chat.ts`, `api/session.ts` | 封装 `POST /chat/`、`GET /messages`、`GET /stream`、`POST /interrupt` |
| 展示组件 | `ChatContent`, `MessageBubble`, `TextInput` | 渲染消息、输入框、发送/停止按钮、工具确认卡片 |

这套拆分非常适合面试表达：

```text
前端页面不直接理解后端运行细节，而是通过 useMessages 把“历史消息 + 实时事件流 + 用户动作”统一成一个消息状态机。
后端也不关心前端组件，只负责通过 Storage 提供历史，通过 MessageBus/SSE 提供增量事件。
```

### 10.2 用户发送消息的完整闭环

用户动作：

```text
用户在 TextInput 输入文本
  ↓
点击 Send
  ↓
ChatContent 调用 onSend
  ↓
ChatViewport 传入 useMessages.send
```

前端链路：

```text
TextInput.handleSend
  ↓
ChatContent.onSend
  ↓
useMessages.send
  ↓
先构造 UserMsg，并乐观追加到 msgsRef
  ↓
chatApi.trigger
  ↓
POST /chat/
```

后端链路：

```text
POST /chat/
  ↓
chat_router.chat
  ↓
ChatRunRegistry.spawn
  ↓
ChatService.run
  ↓
MessageBus.acquire_lock
  ↓
Agent.reply_stream
  ↓
publish_session_event
```

前端接收链路：

```text
useMessages 初始化时已经打开 SSE
  ↓
sessionApi.streamEvents
  ↓
GET /sessions/{sid}/stream
  ↓
收到 ReplyStartEvent
  ↓
创建 AssistantMsg，phase = streaming
  ↓
收到 DataBlock / ToolCall / Text delta
  ↓
appendEvent 合并到当前 AssistantMsg
  ↓
收到 ReplyEndEvent
  ↓
phase = idle
```

这个流程说明一个重要设计：

```text
POST /chat/ 的 HTTP 请求生命周期，和 Agent 真实运行生命周期是解耦的。
前端不能靠 POST /chat/ 是否返回来判断回答是否结束，而要靠 SSE 中的 ReplyEndEvent。
```

面试表达：

```text
前端发送消息时先做乐观更新，把用户消息立即放入本地列表；
后端只返回 started，真正的 assistant 回复由 SSE 增量推送。
这样可以让长时间工具调用、模型流式输出和页面刷新恢复都走同一套事件机制。
```

### 10.3 页面加载与刷新恢复闭环

用户打开一个已有会话时：

```text
URL: /chat/:agentId/:sessionId
  ↓
ChatPage 解析 URL
  ↓
ChatViewport 接收 agentId/sessionId
  ↓
useMessages(agentId, sessionId)
```

`useMessages` 做两件事：

```text
1. GET /sessions/{sid}/messages
   ↓
   加载持久化 Msg 历史

2. GET /sessions/{sid}/stream
   ↓
   打开 SSE 长连接，接收后续事件
```

关键点：

```text
如果 messages 接口返回 is_running = true，前端 phase 初始化为 streaming。
如果历史消息尾部存在 asking/submitted tool_call，也会初始化为 streaming。
```

这说明前端状态不是只靠本地 React state，而是可以从后端持久化状态恢复：

```text
Storage 中的 Msg 历史
  +
MessageBus 中的 running lock
  +
assistant 消息尾部 ToolCallState
  =
前端刷新后的正确 UI 状态
```

面试表达：

```text
这个 Web UI 支持刷新恢复。
它先从 messages API 拿完整历史，再通过 stream API 接上实时增量；
如果会话正在运行或停在 HITL，UI 会恢复为 streaming 状态，继续显示 Stop 或确认卡片。
```

### 10.4 Stop / Interrupt 的完整产品闭环

用户动作：

```text
Assistant 正在回复
  ↓
TextInput 的 Send 按钮切换为 Stop
  ↓
用户点击 Stop
```

前端链路：

```text
TextInput
  ↓
onInterrupt
  ↓
useMessages.interrupt
  ↓
phase: streaming → interrupting
  ↓
启动 10 秒兜底 timer
  ↓
sessionApi.interrupt
  ↓
POST /sessions/{sid}/interrupt
```

后端链路：

```text
ChatService.interrupt
  ↓
判断 session lock
  ├─ running:
  │    publish session_interrupt_channel
  │      ↓
  │    CancelDispatcher task.cancel()
  │      ↓
  │    Agent 处理 CancelledError
  │
  └─ not running:
       enqueue UserInterruptEvent
         ↓
       WakeupDispatcher resume
         ↓
       parked HITL 被关闭 / idle no-op
```

前端收尾：

```text
SSE 收到 ReplyEndEvent
  ↓
clear interrupt timer
  ↓
phase = idle
```

如果 `ReplyEndEvent` 丢失或后端异常：

```text
10 秒 timer 触发
  ↓
phase 从 interrupting 回到 idle
```

面试表达：

```text
Stop 按钮不是直接终止 HTTP 请求，因为真实运行不在 POST /chat 请求里。
前端调用 interrupt API，请求后端取消运行中的 task 或唤醒 parked HITL；
最终 UI 是否结束由 SSE 的 ReplyEndEvent 驱动，同时前端有超时兜底避免按钮永久卡住。
```

### 10.5 HITL 人类确认闭环

普通工具确认：

```text
Agent 产生 RequireUserConfirmEvent
  ↓
SSE 推给前端
  ↓
appendEvent 写入 AssistantMsg 的 tool_call
  ↓
MessageBubble / ConfirmCard 渲染确认卡片
  ↓
用户确认或拒绝
  ↓
useMessages.onUserConfirm
  ↓
构造 UserConfirmResultEvent
  ↓
POST /chat/
  ↓
后端作为 continuation resume 当前 reply
```

团队子 Agent 确认：

```text
worker session 产生确认请求
  ↓
SubagentHitlProjector 投影到 leader session
  ↓
leader 的 SSE 收到 CustomEvent(name="subagent_require_user_confirm")
  ↓
useMessages.subagentHitl 保存 pending 卡片
  ↓
SubagentHitlCard 渲染
  ↓
用户在 leader 视图确认
  ↓
POST /chat/ 发到 leader session
  ↓
后端根据 reply_id 映射到 worker session
  ↓
worker resume
```

这个设计的产品价值：

```text
用户只面对 leader session，不需要知道 worker session 的存在；
后端负责把确认事件路由到真正等待的子 Agent。
```

面试表达：

```text
HITL 不是简单弹窗，而是一个跨前后端的 continuation 协议。
前端把确认动作编码成 UserConfirmResultEvent，仍然通过 POST /chat/ 进入统一运行入口；
后端根据 reply_id 和投影关系恢复对应的 tool call。
```

权限模式 PermissionModeSelect

### 10.7 Plan 计划模式的前后端闭环

AgentScope 的 Plan 不是独立的“计划页面”，而是通过内置任务工具写入 `AgentState.tasks_context`，再实时投影到 Web UI 的 Plan 面板。

核心源码入口：

```text
src/agentscope/tool/_task/_create_task.py
src/agentscope/tool/_task/_list_task.py
src/agentscope/tool/_task/_get_task.py
src/agentscope/tool/_task/_update_task.py
src/agentscope/state/_state.py
src/agentscope/app/_service/_toolkit.py
src/agentscope/app/middleware/_state_change_middleware.py
examples/web_ui/frontend/src/pages/chat/ChatViewport.tsx
examples/web_ui/frontend/src/components/panel/TaskPanel.tsx
examples/web_ui/frontend/src/components/chat/tool-renderers/TaskCreateRenderer.tsx
tests/task_tool_test.py
tests/toolkit_task_test.py
```

后端装配链路：

```text
ChatService.run
  ↓
get_toolkit
  ↓
始终注入 TaskCreate / TaskList / TaskGet / TaskUpdate
  ↓
Agent 在 ReAct acting 阶段调用任务工具
  ↓
任务工具修改 agent.state.tasks_context
  ↓
StateChangeMiddleware 检测 state hash 变化
  ↓
发布 CustomEvent(name="state_updated")
  ↓
SSE 推给前端
```

前端展示链路：

```text
useMessages.processEvent
  ↓
收到 CustomEvent(name="state_updated")
  ↓
ChatViewport.handleStateUpdated
  ↓
setTasksContext(value.tasks_context)
  ↓
TaskPanel 渲染任务列表、完成数、依赖关系、进行中状态
```

Plan 的本质：

```text
Plan 是 AgentState 的一部分，不是单独数据库表。
任务变化由工具调用产生，经过 StateChangeMiddleware 变成实时 UI 事件。
前端 Plan 面板是只读投影，真正的任务状态由 Agent 工具维护。
```

值得重点追的问题：

1. 为什么 Task 工具要默认注入到每个 Agent 的 Toolkit？
2. 为什么 `tasks_context` 放在 `AgentState`，而不是单独建 Task API？
3. `TaskCreate` 和 `TaskUpdate` 如何表达任务依赖、状态流转、metadata？
4. 为什么前端 Plan 面板是只读，而不是用户直接编辑？
5. `StateChangeMiddleware` 为什么通过 hash 对比检测任务变化？
6. 计划状态如何在页面刷新后恢复？

面试表达：

```text
AgentScope 的 Plan 模式不是传统项目管理 CRUD，而是 Agent Runtime 内部的任务状态。
LLM 通过 TaskCreate/TaskUpdate 等工具维护计划，计划状态保存在 AgentState.tasks_context 中；
后端通过 StateChangeMiddleware 把状态变化发布成 state_updated 事件，前端 Plan 面板实时投影。
这种设计让计划成为 Agent 推理-行动循环的一部分，而不是外部强塞给 Agent 的 UI 表单。
```

### 10.8 多 Agent / Team 的前后端闭环

AgentScope 的多 Agent 实现可以理解为：

```text
一个 leader session
  +
多个 worker agent/session
  +
TeamRecord 维护成员关系
  +
MessageBus inbox/wakeup 做跨 session 通信
  +
Web UI 用 TeamSidebar 展示并切换焦点
```

核心源码入口：

```text
src/agentscope/app/_service/_toolkit.py
src/agentscope/app/_tool/_team_create.py
src/agentscope/app/_tool/_agent_create.py
src/agentscope/app/_tool/_agent_invite.py
src/agentscope/app/_tool/_team_say.py
src/agentscope/app/_tool/_team_delete.py
src/agentscope/app/storage/_model/_team.py
src/agentscope/app/storage/_model/_session.py
src/agentscope/app/_service/_projectors/_subagent_hitl.py
src/agentscope/app/_router/_session.py
src/agentscope/app/_router/_chat.py
examples/web_ui/frontend/src/pages/chat/index.tsx
examples/web_ui/frontend/src/components/team/TeamSidebar.tsx
examples/web_ui/frontend/src/components/chat/SubagentHitlCard.tsx
tests/service_toolkit_test.py
tests/service_subagent_hitl_projector_test.py
```

Team 创建链路：

```text
Leader Agent 调用 TeamCreate
  ↓
创建 TeamRecord
  ↓
把当前 session.team_id 设置为 team.id
  ↓
StateChangeMiddleware 发布 team_updated
  ↓
前端 refetchSessions
  ↓
SessionView.team 返回 leader + members
  ↓
TeamSidebar 出现
```

Worker 创建链路：

```text
Leader Agent 调用 AgentCreate
  ↓
校验当前 session 是 team leader
  ↓
根据 SubAgentTemplate 生成 worker AgentRecord
  ↓
为 worker 创建独立 SessionRecord
  ↓
继承 leader 的 workspace_id / model config / fallback model
  ↓
合并 permission_context / working directories / task context
  ↓
把 worker 加入 TeamRecord.members
  ↓
把初始任务包装成 HintBlock 放入 worker inbox
  ↓
enqueue_run_trigger 唤醒 worker session
```

Team 通信链路：

```text
任意 team 成员调用 TeamSay
  ↓
根据 TeamRecord 构建 name → (session_id, agent_id) 通讯录
  ↓
把 team-message HintBlock 写入目标 session inbox
  ↓
enqueue_run_trigger 唤醒目标 session
  ↓
目标 Agent 下次运行时 InboxMiddleware 读入消息
  ↓
目标 Agent 继续推理并通过 SSE 输出自己的事件
```

前端多 Agent 导航：

```text
URL: /chat/:leaderAgentId/:leaderSessionId
  ↓
显示 leader session

URL: /chat/:leaderAgentId/:leaderSessionId/:memberAgentId
  ↓
主侧边栏仍锚定 leader session
  ↓
TeamSidebar 高亮 member
  ↓
ChatViewport 切换到 member.session_id
```

这说明前端不是为每个 worker 打开一个全新页面，而是在同一个团队上下文中切换“当前聚焦 session”：

```text
ChatPage 维护外层 leader 选择
TeamSidebar 维护团队成员导航
ChatViewport 只接收 effectiveAgentId/effectiveSessionId
```

子 Agent HITL 投影链路：

```text
worker session 产生 RequireUserConfirmEvent
  ↓
SubagentHitlProjector 发现它属于某个 team，且不是 leader session
  ↓
把 pending 确认卡片写到 leader session 的 projection registry
  ↓
向 leader stream 发布 CustomEvent(name="subagent_require_user_confirm")
  ↓
leader UI 显示 SubagentHitlCard
  ↓
用户在 leader 页面确认
  ↓
POST /chat/ 发到 leader session
  ↓
chat_router 用 SubagentHitlProjector.resolve 找到 worker session
  ↓
enqueue resume trigger 给 worker
```

多 Agent 的关键设计点：

| 设计点 | 说明 |
|---|---|
| team 是 session-level | 同一个用户 Agent 可以在不同 session 领导不同 team |
| worker 有独立 session | 每个子 Agent 都有自己的上下文、状态、消息流 |
| 通信走 inbox + wakeup | TeamSay 不直接调用对方函数，而是投递消息并唤醒运行 |
| leader 是用户入口 | 用户主要面对 leader，worker HITL 通过投影出现在 leader UI |
| worker 工具受角色限制 | worker 只拿 worker 版 TeamSay，leader 拿 TeamCreate/AgentCreate/TeamSay/TeamDelete 等 |
| 前端用 URL 聚焦成员 | 第三段 `memberId` 决定 ChatViewport 显示哪个 session |

值得重点追的问题：

1. 为什么 team 绑定在 Session 上，而不是只绑定在 Agent 上？
2. `AgentCreate` 为什么要给 worker 创建独立 AgentRecord 和 SessionRecord？
3. worker 为什么继承 leader 的 workspace/model/permission？
4. `TeamSay` 为什么通过 MessageBus inbox + wakeup，而不是直接同步调用 worker？
5. leader 如何知道 worker 的 HITL 请求？
6. 前端为什么用 `/chat/:leaderAgentId/:leaderSessionId/:memberId` 这种路由？
7. 多 Agent 删除时，created member 和 invited member 有什么生命周期差异？

面试表达：

```text
AgentScope 的多 Agent 不是简单在一个进程里 new 多个 Agent 对象，而是把每个成员建模成独立的 agent/session。
TeamRecord 维护 leader 和 members，TeamSay 通过 MessageBus inbox 投递跨 session 消息，WakeupDispatcher 负责唤醒目标 session。
前端则用 TeamSidebar 和 URL 的 memberId 在 leader/team 上下文中切换当前聚焦的 worker。
这种设计把多 Agent 协作做成了可持久化、可恢复、可中断、可观察的产品能力。
```

### 12.11 接口深挖优先级

如果要继续把每个 endpoint 都补成完整分析，建议按下面顺序推进：

| 优先级 | 接口/专题 | 原因 |
|---|---|---|
| P0 | `POST /chat/`, `GET /sessions/{sid}/stream`, `POST /sessions/{sid}/interrupt` | Agent 运行主链路，已深挖 |
| P0 | Plan 工具、Team 工具 | 面试价值最高，体现 Agent 产品工程化 |
| P1 | `PATCH /sessions/{sid}` | 前端模型/权限/RAG 配置如何影响 Runtime |
| P1 | Knowledge Base 上传与索引接口 | RAG 异步 worker、lease、状态轮询 |
| P1 | Workspace MCP/Skill 接口 | 外部工具生态、Toolkit 装配 |
| P2 | Schedule 接口 | 自动运行、cron、后台触发 |
| P2 | Agent/Credential CRUD | 资源管理基础、权限隔离 |
| P3 | Model/TTS Model 列表接口 | 能力发现、动态 UI |

最终目标：

```text
每个接口都有：
1. 前端入口
2. 后端 Router
3. Service / Manager / Tool 调用链
4. 状态变化
5. 事件回流
6. 测试证据
7. 面试表达
```
