## 二、参数依赖关系详解

### 2.1 ID 生成与引用链

```
POST /credential/
   │
   └──► 返回 credential_id (服务端生成 UUID)
         │
         │  引用
         ▼
POST /agent/
   │
   └──► 返回 agent_id (服务端生成 UUID)
         │
         │  引用
         ▼
POST /sessions/
   │  body: { agent_id, chat_model_config: { credential_id, model } }
   │
   └──► 返回 session_id (服务端生成 UUID)
         │
         │  引用
         ▼
POST /chat/
   │  body: { agent_id, session_id, input }
   │
   └──► 触发 Agent 执行
```

**关键点**：
- 所有 ID 由服务端生成，客户端无法指定
- 每个接口都会校验 ID 的归属关系（user_id 隔离）
- Session 创建时会验证 credential_id 和 agent_id 都属于当前用户

---

### 2.2 各接口参数依赖矩阵

| 接口 | 必需参数 | 依赖来源 | 说明 |
|------|---------|---------|------|
| `POST /credential/` | `data.type`, `data.api_key` | 无 | 创建凭证，返回 credential_id |
| `POST /agent/` | `name`, `system_prompt` | 无 | 创建 Agent，返回 agent_id |
| `POST /sessions/` | `agent_id`, `chat_model_config.credential_id` | Agent + Credential | 创建 Session |
| `POST /chat/` | `agent_id`, `session_id`, `input` | Session | 触发对话 |
| `GET /sessions/{id}/stream` | `agent_id` (query) | Session | SSE 事件流 |
| `GET /sessions/{id}/messages` | `agent_id` (query) | Session | 历史消息 |
| `POST /workspace/mcp` | `agent_id`, `session_id` (query) | Session | 添加 MCP |
| `POST /schedule/` | `agent_id`, `cron_expression` | Agent | 定时任务 |

---

### 2.3 参数校验链路

```
POST /sessions/
   │
   ├── 1. 从 Header 获取 user_id
   │
   ├── 2. 验证 agent_id 属于 user_id
   │      └── storage.get_agent(user_id, agent_id)
   │
   ├── 3. 验证 credential_id 属于 user_id
   │      └── storage.list_credentials(user_id)
   │          └── 检查 credential_id 在列表中
   │
   └── 4. 创建 Session
          └── storage.upsert_session(user_id, agent_id, config)
```

### 4.3 ⚠️ main 新增（未发版，#2029）：SQL 存储后端

Redis 之外的第二个生产级存储选项——`AsyncSQLAlchemyStorage`（`src/agentscope/app/storage/_sql/_storage.py`），实现同一 `StorageBase` 接口，可无缝替换：

```python
# 任意 SQLAlchemy async URL，驱动由调用方自装
storage = AsyncSQLAlchemyStorage("sqlite+aiosqlite:///./as.db")
storage = AsyncSQLAlchemyStorage("postgresql+asyncpg://user:pw@host/db",
                                 engine_kwargs={"pool_size": 20})
# 可选：create_tables=True（默认，create_all）/ auto_migrate=True（Alembic upgrade head）
```

**表设计（`_tables.py`）——"payload + 提升列"混合模式**：

| 设计 | 说明 |
|------|------|
| `_JsonRecordMixin` | 每张记录表统一含 `id`(PK) / `created_at` / `updated_at`(索引) / `payload`(JSON 全量记录) |
| 提升列 | 仅把**查询需要过滤/索引的字段**提升为真实列（`user_id`、`agent_id`、`source`、`team_id`、`status`、`lease_expires_at` 等），其余全留在 payload JSON |
| 表清单 | credentials / agents / sessions / schedules / teams / knowledge_bases / knowledge_documents / messages |
| messages 表 | 独立设计：复合主键 `(session_id, msg_id)`，支撑 cursor 分页 |
| 方言中立 | 仅用 dialect-neutral SA 构造，SQLite/PG/MySQL 通吃；时间戳存 naive UTC |
| Alembic 集成 | `auto_migrate=True` 时 `asyncio.to_thread` 里跑 `command.upgrade(head)`（Alembic 同步 runtime 内部自起 event loop，主循环直接调会死锁） |

**面试考点**：为什么不做全字段列映射？记录 schema 由 pydantic 模型演进，全列映射每次加字段都要迁移；payload JSON 保真 + 提升列索引，兼顾灵活性与查询性能——与 Redis 存储的 JSON 序列化策略保持同构，切换后端无语义漂移。

## 五、SSE 事件流详解

### 5.1 事件流架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        前端 (WebUI)                              │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ EventSource('/sessions/{sid}/stream?agent_id=xxx')         ││
│  │    │                                                        ││
│  │    └──► onmessage(event) {                                  ││
│  │           const data = JSON.parse(event.data);              ││
│  │           // 处理事件                                        ││
│  │         }                                                   ││
│  └─────────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────────┘
                              ▲
                              │ SSE (Server-Sent Events)
                              │ text/event-stream
                              │
┌─────────────────────────────────────────────────────────────────┐
│                        服务端                                    │
│  ┌─────────────────────────────────────────────────────────────┐│
│  │ GET /sessions/{sid}/stream                                   ││
│  │    │                                                         ││
│  │    ├── 1. 重放历史事件 (replay log)                           ││
│  │    │      for event in message_bus.log_read(...):           ││
│  │    │          yield f"data: {json.dumps(event)}\n\n"        ││
│  │    │                                                         ││
```

#### ⚠️ main 新增（未发版，#2133）：reply 错误结构化浮出

此前 reply 内部异常只落后端日志，前端只见流静默断开。现在错误沿 `ReplyEndEvent` 结构化下发：

```python
class ReplyEndEvent(EventBase):
    finished_reason: ReplyFinishedReason  # completed | interrupted | exceed_max_iters | error
    error: ErrorInfo | None               # 仅 finished_reason == ERROR 时填充

class ErrorInfo(BaseModel):               # types/_reply.py
    type: ErrorType    # 8 类：authentication / permission / rate_limit / invalid_request
                       #       / upstream / connection / internal / unknown
    message: str       # 已脱敏的人类可读消息
```

要点：
- **分类映射**：`app/_service/_errors.py` 将底层异常（如 openai `AuthenticationError`、httpx 连接错误）归一到 8 个 `ErrorType`，前端可按类型差异化提示（401 引导换 key、rate_limit 提示重试）
- **脱敏**：message 经清洗，不透传含密钥/内部路径的原始异常串
- **兼容**：`finished_reason` 默认 `COMPLETED`，旧前端忽略新字段即可，非 breaking

> **v2.0.4.post1 更新（#2081）**：历史消息接口从 **offset/limit** 改为 **cursor-based** 分页。

> - **⚠️ 面试考点**：为什么流式 / 高并发场景下 offset 分页会丢数据？答：新插入使 offset 语义偏移；cursor 以单调 ID 为稳定锚点，不受写入影响。

#### 7.5.1 文件浏览与读取（v2.0.6 #2187）

**`GET /workspace/directories`** — 列出目录一层：
- 参数：`path` 可为绝对路径或相对工作区根路径，空则列出工作区根
- 路径不局限于工作区根：沙箱后端可达文件系统即沙箱，本地后端调用者本身受信任
- 响应 `DirectoryListing`：`{ path, entries: [{name, is_dir, size_bytes, updated_at}] }`
- `path` 回显解析后的绝对路径，便于用相对路径浏览的调用方展示当前位置

**`GET /workspace/files`** — 流式读取文件：
- 参数：`path`（必填，绝对或相对工作区根）、`download`（强制 Content-Disposition attachment）、`token`（下载令牌，替代 `X-User-ID` 头）
- 认证二选一：`X-User-ID` 头 或 `token` 查询参数，否则 401
- 响应体**分块流式**（`StreamingResponse`）而非整读，避免大文件耗尽共享 API 进程内存
- 目录路径返回 400，文件不存在返回 404

**`POST /workspace/files/download-token`** — 签发短时下载令牌：
- 参数：`path`（令牌将授权的路径）
- 用途：浏览器原生下载（浏览器导航请求不带自定义头，故用 URL 中的凭证）
- 响应 `DownloadTokenResponse`：`{ token, expires_at }`，令牌仅对该 path 有效，过期后拒绝

#### 7.5.2 工作区状态（v2.0.6 #2257）

**`GET /workspace/status`** — 报告 session 指向的目录及其 git 状态：
- 目录来自 session 自身的 `cwd`（而非查询参数），是 session 的锚点
- 响应 `WorkspaceStatus`：`{ workdir, cwd, git }`
  - `workdir`：工作区根绝对路径（后端相关，客户端无法自行推导）
  - `cwd`：session 聚焦的绝对路径，`SessionConfig.cwd` 未设置时等于 `workdir`
  - `git`：`GitStatus | null`，非 git 仓库时为 null（正常情况而非错误）
- `GitStatus`：`{ branch, head, ahead, behind, ... }`（branch 在 detached HEAD 时为 null；head 为完整 SHA 不缩写）
- git 探测为 best-effort：任何失败（缺二进制、容器不可达）都折叠为 `git: null`，其余响应照常返回

### 7.7 `/health` — 健康检查（v2.0.6 #2237）

| 方法 | 路径 | 参数 | 请求体 | 响应 | 说明 |
|------|------|------|-------|------|------|
| GET | `/health` | - | - | `HealthResponse` | 服务存活与各组件就绪度 |

**`GET /health`** — 报告服务是否就绪：
- **I/O-free 设计**：只检查 `app.state` 上挂载的组件，探测时**不触碰** Redis、数据库或工作区后端
- 响应 `HealthResponse`：`{ status, version, components }`
  - `status`：`"ok" | "not_ready"`（任一必需组件缺失即 `not_ready`；disabled 的可选特性不影响）
  - `version`：创建该 app 时的 API 版本
  - `components`：`dict[str, "ok" | "not_ready" | "disabled"]` 逐子系统就绪度
- 组件分类：
  - **eager 组件**（`storage`、`message_bus`、`workspace_manager`）：启动前挂载
  - **lifespan 组件**（`background_task_manager`、`chat_run_registry`、`scheduler_manager`、`resource_access_service`、`chat_service`、`session_service`）：lifespan 启动时按序创建
  - **可选 hub**（`mcp_hubs`、`skill_hubs`）：未注册为 `disabled`（健康态而非失败）
  - **knowledge_base**：未传 manager 时为 `disabled`；传了但 service 缺失为 `not_ready`
- **关键语义**：任一组件为 `not_ready` 时，响应状态码降级为 **503**。在普通 `uvicorn.run(app)` 下 `not_ready` 实际不可达（uvicorn 在接收连接前完成 lifespan）；它主要捕获 **mount-as-sub-app 部署**（Starlette 不运行挂载子应用的 lifespan，导致所有业务端点失效）——把静默配置错误变成一个明确信号

## 八、面试要点

### 8.1 为什么 Chat 是 fire-and-forget？

**答**：
1. **长连接问题**：Agent 执行可能很慢（多轮推理、工具调用），同步等待会占用 HTTP 连接
2. **断线重连**：SSE 支持重连后从 replay log 恢复，不会丢失事件
3. **多路复用**：前端可以同时监听多个 Session 的事件流
4. **解耦**：触发和执行分离，便于扩展（如定时任务、外部触发）

---

### 8.2 Session 和 Agent 的关系？

**答**：
- **Agent** = 配置模板（system_prompt、工具列表、上下文策略）
- **Session** = 运行实例（绑定 Agent + 模型 + 工作空间）
- 一个 Agent 可以有多个 Session（多次独立对话）
- Session 存储运行时状态（context、tool_context、permission_context）
- 删除 Agent 会级联删除所有 Session

---

### 8.3 Credential 为什么单独管理？

**答**：
1. **安全性**：API Key 需要加密存储，不能明文暴露在 Agent 配置中
2. **复用性**：多个 Session 可以共用同一个凭证
3. **灵活性**：用户可以切换不同模型的凭证（DeepSeek/OpenAI/...）
4. **权限控制**：不同用户有不同的凭证，实现多租户隔离

---

### 8.4 Workspace 的作用？

**答**：
- **隔离性**：每个 Session 有独立的工作空间（文件系统目录）
- **MCP 管理**：存储 Session 关联的 MCP 服务器配置
- **Skill 管理**：存储 Session 可用的 Skill 技能
- **持久化**：MCP/Skill 配置持久化到 `.mcp` 文件，重启不丢失

---

## 九、总结

### 9.1 核心接口调用顺序

```
1. POST /credential/     → credential_id
2. POST /agent/          → agent_id
3. POST /sessions/       → session_id (需要 agent_id + credential_id)
4. GET  /sessions/{id}/stream  → 打开 SSE 监听
5. POST /chat/           → 触发对话 (需要 agent_id + session_id)
6. GET  /sessions/{id}/messages → 查询历史 (可选)
```

### 9.2 参数依赖关系

```
Credential ──► Session (通过 credential_id)
Agent ───────► Session (通过 agent_id)
Session ─────► Chat (通过 agent_id + session_id)
Workspace ───► Session (通过 workspace_id)
```

### 9.3 数据存储

所有数据存储在 **Redis** 中，Key 格式：
```
agentscope:user:{user_id}:{resource_type}:{resource_id}
```

重启服务后数据不丢失。
