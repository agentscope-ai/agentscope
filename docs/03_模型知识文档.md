## 一、核心概念

### 1.1 什么是模型模块？

**模型模块**是 AgentScope 中用于**统一封装大语言模型（LLM）调用**的抽象层。

它将不同厂商的 API（OpenAI、Anthropic、DashScope、Gemini 等）统一为一个接口：

```
┌─────────────────────────────────────────────────────────────┐
│                    ChatModelBase（抽象基类）                  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │ OpenAIChat  │  │ Anthropic   │  │ DashScope   │  ...    │
│  │ Model       │  │ ChatModel   │  │ ChatModel   │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
└─────────────────────────────────────────────────────────────┘
```

**关键理解** 🔴：
- **统一接口**：所有模型继承 `ChatModelBase`，对外暴露相同的 API
- **适配器模式**：每个厂商的 SDK 差异被封装在子类中
- **流式/非流式统一**：通过 `ChatResponse` 和 `AsyncGenerator[ChatResponse]` 统一返回类型

---

### 1.2 为什么需要模型模块？

| 需求 | 没有模型模块 | 有模型模块 |
|------|-------------|-----------|
| 切换模型厂商 | 修改大量代码 | 只改配置 |
| 流式输出 | 每个厂商不同实现 | 统一 `AsyncGenerator` |
| 重试机制 | 各自实现 | 基类统一处理 |
| 结构化输出 | 各厂商 API 不同 | 统一 `generate_structured_output` |
| Token 计数 | 各厂商不同 | 统一估算方法 |

**核心矛盾**：
- 不同厂商的 API 格式、参数、错误处理各不相同
- Agent 需要统一的调用接口

**AgentScope 的解法**：模板方法模式 + 适配器模式

## 二、核心接口

### 2.1 公开 API

```python
class ChatModelBase:
    # 核心方法
    async def __call__(messages, tools, tool_choice) -> ChatResponse | AsyncGenerator
    async def count_tokens(messages, tools) -> int
    async def generate_structured_output(messages, structured_model) -> StructuredResponse
    
    # 子类必须实现
    @abstractmethod
    async def _call_api(model_name, messages, tools, tool_choice) -> ChatResponse | AsyncGenerator
```

**关键区别** 🔴：

| 方法 | 返回值 | 用途 |
|------|--------|------|
| `__call__()` | `ChatResponse` 或 `AsyncGenerator` | 调用模型（带重试） |
| `count_tokens()` | `int` | 估算 Token 数 |
| `generate_structured_output()` | `StructuredResponse` | 生成结构化输出 |
| `_call_api()` | 子类实现 | 实际调用厂商 API |

### 3.3 v2.0.4.post1：OpenAI Responses API 的 reasoning 历史重放（#2071）

`OpenAIResponseModel`（`src/agentscope/model/_openai_response/_model.py`）走的是 Responses API 而非 Chat Completions。该 API 对 reasoning 模型（o3 / o4-mini / gpt-5.5）有硬性契约：**每个 `function_call` 输出项，必须伴随其前置的 `reasoning` 项**。

**问题**：早期实现在压缩 / 多轮时丢弃了 reasoning item（或只保留有 summary 的），导致回传历史缺了 `reasoning_item_id`，API 报"function_call 缺少对应 reasoning"。

**修复**（`v2.0.4.post1`）：
- 非流式解析：即便 reasoning item 的 `summary` 为空（如 o1 / o4-mini 不暴露 summary），只要 `reasoning_item_id` 存在就保留为 `ThinkingBlock(reasoning_item_id=...)`。
- 流式 `response.completed`：从完成响应中提取每个 reasoning item 的 id，作为 `reasoning_item_id` 元数据附回，供 formatter 在下一轮历史中原样回传。

**设计动机**：Responses API 用 `reasoning_item_id` 把"思考链"和"工具调用"绑定成因果对，模型需要这层上下文才能正确续接。丢 id = 丢因果链 = API 报错或推理质量下降。

**替代方案 / trade-off**：
- *替代*：每轮重新发送完整 reasoning 文本（而非仅 id）。代价是 token 翻倍、且旧模型根本不返回 summary。
- *trade-off*：仅回传 id（轻量、满足 API 契约）vs 回传全文（重、且不可得）。AgentScope 选 id 回传，契合"最小必要信息"原则。

**⚠️ 面试考点**：
- Responses API 与 Chat Completions 的核心区别？答：Responses 把 reasoning / function_call 作为一等公民 item，且要求 function_call 与前置 reasoning item 配对。
- 为什么空 summary 的 reasoning item 也要保留？答：API 契约只看 `reasoning_item_id` 是否存在，summary 有无并不影响配对。

**⚠️ v2.0.5 新增（#2139）：`redacted_thinking` 块往返保留**

Anthropic 扩展思考在触碰安全策略时会返回 `redacted_thinking` 块（加密不可读，但 API 要求后续轮次**原样回传**以维持推理连续性）。此前 AgentScope 将其当作无 signature 的 ThinkingBlock 丢弃，导致多轮工具调用时 API 报错或思考链断裂。修复：

- `ThinkingBlock` 新增 `redacted_thinking_data` 字段（`message/_block.py`），model 层解析响应时把加密 data 存入
- formatter 回传优先级：有 `redacted_thinking_data` → 还原为 `{"type": "redacted_thinking", "data": ...}`；否则有 `signature` → 正常 thinking 块；两者皆无（他厂 ThinkingBlock）→ 丢弃

设计要点：不新增 block 类型而是给 ThinkingBlock 加可选字段——对上层（事件流、前端渲染）透明，加密内容仅在 Anthropic formatter 往返时可见。

## 四、设计原理

### 4.1 模板方法模式

```python
# src/agentscope/model/_base.py:158
async def __call__(self, messages, tools, tool_choice, **kwargs):
    """模板方法：定义调用骨架"""
    retryable = tuple(self._get_retryable_exceptions())
    last_error = None
    
    for attempt in range(self.max_retries + 1):
        try:
            # 调用子类实现的抽象方法
            return await self._call_api(
                self.model,
                messages=messages,
                tools=tools,
                tool_choice=tool_choice,
                **kwargs,
            )
        except Exception as e:
            if not isinstance(e, retryable):
                raise  # 非重试异常，立即抛出
            last_error = e
            if attempt < self.max_retries:
                await asyncio.sleep(self.retry_delay)
    
    raise last_error
```

**关键点** ：
- `__call__()` 定义重试逻辑骨架
- `_call_api()` 由子类实现具体 API 调用
- `_get_retryable_exceptions()` 由子类声明可重试异常

### 4.3 结构化输出实现（工具调用伪装机制）

#### 4.3.1 核心思路

AgentScope 采用**工具调用伪装**策略实现结构化输出：不依赖各厂商的原生 structured output API，而是将目标 schema 包装成一个"伪工具"的参数定义，利用 LLM 对 tool calling 的高度服从性来保证输出格式。

```
用户期望：LLM 直接返回 {"name": "Alice", "age": 30}
实际做法：让 LLM "调用"一个不存在的工具 generate_structured_output，参数就是目标结构
         ↓ 解析 ToolCallBlock.input 得到 JSON
         ↓ 校验后返回 StructuredResponse(content={"name": "Alice", "age": 30})
```

**设计动机**：不同厂商的原生 structured output API 差异极大（OpenAI 用 `response_format`，Anthropic 用 `tool_use`，DashScope 不支持），而 tool calling 是几乎所有主流 LLM API 的公共能力。

---

#### 4.3.2 三层强制机制 🔴

为确保 LLM 100% 走 tool call 路径，AgentScope 采用了**三重保障**：

**第一层：工具注册 —— 构造"伪工具"**

```python
# src/agentscope/model/_base.py:519-536
tools=[{
    "type": "function",
    "function": {
        "name": "generate_structured_output",       # 固定工具名
        "description": "Call this function to generate structured output required by the user.",
        "parameters": input_schema,                 # ← 目标 schema 直接作为工具参数
    },
}]
```

这个工具**不会被真正执行**，只是借用 tool calling 协议让 LLM 按 schema 格式输出参数。

**第二层：`tool_choice` 强制调用 —— API 层面**

```python
# src/agentscope/model/_base.py:499-500
if tool_choice is None:
    tool_choice = ToolChoice(mode="generate_structured_output")
```

`ToolChoice.mode` 支持 4 种值：

| mode | 含义 | 适用场景 |
|------|------|----------|
| `"auto"` | LLM 自行决定是否调用工具 | 思考模式下的降级方案 |
| `"none"` | 禁止调用工具 | 不使用 |
| `"required"` | 必须调用至少一个工具 | 不使用 |
| `"generate_structured_output"` (具体名称) | **必须调用这个特定工具** | 默认值，强制单工具调用 |

当 `mode` 设为具体工具名时，LLM **被强制**只能调用 `generate_structured_output`，没有其他选择。

**第三层：`<system-reminder>` 指令注入 —— Prompt 层面**

```python
# src/agentscope/model/_base.py:501-517
instruction = (
    "<system-reminder>Now you **MUST** call the tool named "
    "'generate_structured_output' to generate the structured output required "
    "by the user. DON'T do anything else.</system-reminder>"
)

copied_messages = deepcopy(messages)
if copied_messages[-1].role == "user":
    # 情况A：追加到最后一条 user 消息的 content blocks 末尾
    copied_messages[-1].content += [TextBlock(text=instruction)]
else:
    # 情况B：新增一条 user 消息
    copied_messages.append(UserMsg(name="user", content=[TextBlock(text=instruction)]))
```

指令注入在对话**最末端**，确保 LLM 注意力最强。

**三层防御对照表**：

| 层级 | 机制 | 防御场景 |
|------|------|----------|
| `tool_choice=具体名称` | API 层面强制 | 防止 LLM "自作主张"返回文本 |
| `<system-reminder>` | Prompt 层面引导 | 某些 API 不支持强制 tool_choice 时的降级方案（如 DashScope 思考模式） |
| Schema 校验 | 结果层面兜底 | LLM 输出格式不对时触发重试 |

#### 4.3.4 入口层：重试机制

```python
# src/agentscope/model/_base.py:388-451
async def generate_structured_output(self, messages, structured_model, **kwargs):
    """入口方法：校验 + 重试循环"""
    
    if len(messages) == 0:
        raise ValueError("The input messages cannot be empty...")
    
    retryable = tuple(self._get_retryable_exceptions())
    last_error = None
    
    for attempt in range(self.max_retries + 1):
        try:
            return await self._call_api_with_structured_output(
                self.model,
                messages=messages,
                structured_model=structured_model,
                **kwargs,
            )
        except Exception as e:
            if not isinstance(e, retryable):
                raise                    # 非重试异常立即抛出
            last_error = e
            if attempt < self.max_retries:
                await asyncio.sleep(self.retry_delay)   # 重试等待
    
    raise last_error
```

**关键点**：
- 复用 `__call__()` 相同的重试配置（`max_retries`、`retry_delay`）
- Schema 校验失败会抛异常，触发上层重试
- 非重试异常（如 `ValueError`）立即抛出，不浪费重试次数

### 5.2 流式响应处理（以 OpenAI 为例）

```python
# src/agentscope/model/_openai_chat/_model.py:297
async def _parse_stream_response(self, start_datetime, response):
    """解析 OpenAI 流式响应"""
    
    acc_text = TextBlock(text="")           # 累积文本
    acc_thinking = ThinkingBlock(thinking="")  # 累积思考
    acc_tool_calls: OrderedDict = {}        # 累积工具调用
    acc_audio_data: bytearray = bytearray() # 累积音频
    
    async with response as stream:
        async for chunk in stream:
            # 1. 解析 usage（最后一个 chunk 携带）
            if chunk.usage:
                usage = ChatUsage(
                    input_tokens=chunk.usage.prompt_tokens,
                    output_tokens=chunk.usage.completion_tokens,
                    time=(datetime.now() - start_datetime).total_seconds(),
                )
            
            # 2. 解析 delta
            delta = chunk.choices[0].delta
            delta_text = delta.content or ""
            delta_thinking = delta.reasoning_content or ""
            
            # 3. 累积内容
            acc_text.text += delta_text
            acc_thinking.thinking += delta_thinking
            
            # 4. 解析工具调用
            for tool_call in delta.tool_calls or []:
                idx = tool_call.index
                if idx in acc_tool_calls:
                    acc_tool_calls[idx]["input"] += tool_call.function.arguments
                else:
                    acc_tool_calls[idx] = {
                        "id": tool_call.id,
                        "name": tool_call.function.name,
                        "input": tool_call.function.arguments,
                    }
            
            # 5. 产出增量响应
            if delta_contents:
                yield ChatResponse(
                    content=delta_contents,
                    usage=usage,
                    is_last=False,
                )
    
    # 6. 产出最终响应
    yield ChatResponse(
        content=final_contents,
        usage=usage,
        is_last=True,
    )
```

**关键点** 🔴：
- 使用**累积器模式**：`acc_text`、`acc_thinking`、`acc_tool_calls`
- 每个 chunk 产出 `is_last=False` 的增量响应
- 最后一个 chunk 产出 `is_last=True` 的完整响应

### 5.3 Token 计数机制

```python
# src/agentscope/model/_base.py:297
async def count_tokens(self, messages: list[Msg], tools: list[dict] | None) -> int:
    """估算 Token 数（默认实现）"""
    cnt = 0
    acc_texts = []
    data_blocks = []
    
    for msg in messages:
        for block in msg.get_content_blocks():
            if isinstance(block, TextBlock):
                acc_texts.append(block.text)
            elif isinstance(block, ThinkingBlock):
                acc_texts.append(block.thinking)
            elif isinstance(block, ToolCallBlock):
                acc_texts.append(block.input)
            elif isinstance(block, DataBlock):
                data_blocks.append(block)
    
    # 工具 Schema 也计入 Token
    if tools:
        acc_texts.append(json.dumps(tools, ensure_ascii=False))
    
    # 多模态数据（图片/音频）
    for block in data_blocks:
        if isinstance(block.source, Base64Source):
            cnt += len(block.source.data) // 4  # base64 解码后估算
    
    # 文本 Token 估算：UTF-8 字节数 / 4
    acc_text = "".join(acc_texts)
    cnt += int(len(acc_text.encode("utf-8")) / 4 + 0.5)
    
    return cnt
```

**关键点** 🔴：
- 默认实现：`UTF-8 字节数 / 4`（粗略估算）
- 子类可重写（如使用 tiktoken 精确计数）
- 多模态数据单独计算

### 8.1 基础概念题（必问）

#### Q1: Transformer 架构的核心组件是什么？为什么它能取代 RNN？

**参考答案**：
> Transformer 基于**自注意力（Self-Attention）机制**，核心组件包括：
>
> | 组件 | 作用 | 公式 |
> |------|------|------|
> | **Self-Attention** | 计算序列中任意位置的依赖关系 | `Attention(Q,K,V) = softmax(QK^T/√d)V` |
> | **Multi-Head Attention** | 并行计算多个注意力头，捕获不同子空间的信息 | `MultiHead(Q,K,V) = Concat(head_1,...,head_h)W^O` |
> | **Positional Encoding** | 注入位置信息（Transformer 无循环结构） | 正弦/余弦编码或 RoPE |
> | **Feed-Forward Network** | 非线性变换 | `FFN(x) = max(0, xW_1 + b_1)W_2 + b_2` |
> | **Layer Normalization** | 稳定训练（Pre-Norm 或 Post-Norm） | `LayerNorm(x) = (x - μ) / √(σ² + ε) * γ + β` |
>
> **为什么取代 RNN**：
> 1. **并行化**：RNN 序列化计算 O(n)，Transformer 并行化 O(1)
> 2. **长距离依赖**：Self-Attention 直接关注任意距离的词，RNN 长距离梯度消失
> 3. **可扩展性**：Transformer 可堆叠更多层，RNN 难以深度扩展

**追问**：
- Self-Attention 的时间复杂度？→ O(n²·d)，n 是序列长度，d 是维度
- 为什么需要 Multi-Head？→ 单个头只能捕获一种关系模式，多头可以并行捕获语法、语义等不同模式
- Pre-Norm 和 Post-Norm 的区别？→ Pre-Norm 更稳定（2026 年主流），Post-Norm 效果更好但难训练

**面试加分点**：
- 提到 2026 年主流架构：Causal Decoder-only（GPT-5/6、Llama 4、Claude 4）
- 提到 RoPE（Rotary Positional Embeddings）取代正弦编码（长上下文更好）
- 提到 FlashAttention-3 和 GQA（Grouped-Query Attention）优化

### 8.2 推理优化题（字节、阿里高频）

#### Q4: Flash Attention 是如何加速的？核心原理是什么？

**参考答案**：
> **痛点**：原始 Attention 的"富贵病"
> - 时间复杂度 O(n²·d)，空间复杂度 O(n²)
> - GPU 计算快，但内存读写（IO）慢
>
> **核心解法**：分块计算（Tiling）+ IO 感知
>
> | 内存层级 | 容量 | 速度 | 用途 |
> |---------|------|------|------|
> | **HBM**（显存） | 40-80GB | 慢 | 存储模型参数、KV Cache |
> | **SRAM**（缓存） | ~20MB/核 | 快 10x | 分块计算 |
>
> **Flash Attention 逻辑**：
> 1. 将 Q、K、V 矩阵切成小块（Tiling）
> 2. 从 HBM 加载到 SRAM 中计算
> 3. 算完后写回 HBM
> 4. 减少 HBM ↔ SRAM 数据搬运次数
>
> **Softmax 平移不变性**：
> ```
> softmax(x - c) = softmax(x)  # 减去常数不影响结果
> ```
> 利用这个特性，在分块计算时动态更新全局统计量，最终得到和标准 Attention 完全一致的结果。

**追问**：
- Flash Attention 的加速比？→ 2-4x（取决于序列长度）
- 为什么 Flash Attention 省显存？→ 不存储完整的 n×n 注意力矩阵
- FlashAttention-3 的改进？→ 支持 Hopper GPU（H100），异步计算

**面试加分点**：
- 提到 2026 年趋势：FlashAttention-3 成为标配
- 提到 IO 感知算法（IO-Aware Algorithm）
- 提到 HBM vs SRAM 的速度差异（10x+）

---

#### Q5: KV Cache 是什么？显存怎么算？为什么没有 Q Cache？

**参考答案**：
> **KV Cache 的作用**：空间换时间，避免自回归推理重复计算
>
> **推理两阶段**：
> 1. **预填充阶段（Pre-filling）**：处理输入 Prompt，并行计算，建立初始 KV Cache
> 2. **生成阶段（Decoding）**：逐个生成 Token，每生成一个新 Token，只计算新的 K、V，拼接到 Cache 后面
>
> **显存计算公式**：
> ```
> KV Cache 显存 = 2 × n_layers × n_heads × head_dim × seq_len × dtype_size
> 
> 示例：Llama 3 70B
> - n_layers = 80
> - n_heads = 64
> - head_dim = 128
> - seq_len = 4096
> - dtype_size = 2 (FP16)
> 
> KV Cache = 2 × 80 × 64 × 128 × 4096 × 2 = 10.7 GB
> ```
>
> **为什么没有 Q Cache？**
> - K、V 代表"之前所有 token"的特征，是固定的，可以缓存
> - Q 是当前 token 的查询向量，每次生成都变化，无法缓存

**追问**：
- 长上下文时 KV Cache 会把显存吃光怎么办？→ GQA/MQA 优化
- KV Cache 可以卸载到 CPU 吗？→ 可以，但会增加延迟（PagedAttention 优化）

**面试加分点**：
- 提到 2026 年主流：GQA（Grouped-Query Attention）
- 提到 PagedAttention（vLLM 的核心优化）
- 提到 KV Cache 量化（8-bit/4-bit 压缩）

---

#### Q6: MHA、MQA、GQA 的区别？为什么 2026 年流行 GQA？

**参考答案**：
> **三种 Attention 变体对比**：
>
> | 类型 | 机制 | KV Cache 显存 | 效果 | 代表模型 |
> |------|------|--------------|------|---------|
> | **MHA**（Multi-Head Attention） | 每个 Q 头独立 K、V | 最大（n_heads） | 最好 | GPT-3、BERT |
> | **MQA**（Multi-Query Attention） | 所有 Q 头共享一组 K、V | 最小（1x） | 较差 | Falcon |
> | **GQA**（Grouped-Query Attention） | Q 头分组，每组共享一组 K、V | 中等（n_groups） | 平衡 | Llama 2/3、Qwen 2 |
>
> **GQA 的核心思想**：
> ```
> MHA:  8 个 Q 头 → 8 组 K、V
> MQA:  8 个 Q 头 → 1 组 K、V
> GQA:  8 个 Q 头 → 4 组 K、V（每组 2 个 Q 头共享）
> ```
>
> **为什么 2026 年流行 GQA？**
> - 在 MHA 的好效果和 MQA 的高速度之间找到完美平衡
> - KV Cache 显存减少 2-4x，推理速度提升 2-3x
> - 效果损失 <1%（可接受）

**追问**：
- GQA 的分组策略？→ 通常 4 或 8 组（取决于模型规模）
- GQA 可以微调吗？→ 可以，但需要调整注意力头的分组

**面试加分点**：
- 提到 2026 年主流模型都用 GQA（Llama 3、Qwen 2、ChatGLM 3）
> - 提到 GQA 是 MHA 和 MQA 的折中方案
> - 提到 KV Cache 显存优化是长上下文的关键

### 8.3 微调与对齐题（阿里、腾讯高频）

#### Q7: LoRA 和 QLoRA 的区别？为什么 PEFT 成为主流？

**参考答案**：
> **PEFT（Parameter-Efficient Fine-Tuning）**：仅更新少量参数（<1%），冻结其余部分
>
> **LoRA vs QLoRA 对比**：
>
> | 维度 | LoRA | QLoRA |
> |------|------|-------|
> | **核心思想** | 在权重上加低秩矩阵 | LoRA + 4-bit 量化 |
> | **更新参数** | ~1%（低秩矩阵） | ~1%（低秩矩阵） |
> | **基础模型精度** | FP16/BF16 | 4-bit（NF4） |
> | **显存占用** | 中等 | 最小（70B 模型单 GPU） |
> | **效果** | 好 | 略差（<1% 损失） |
> | **适用场景** | 多 GPU、显存充足 | 单 GPU、显存受限 |
>
> **LoRA 核心公式**：
> ```
> W' = W + ΔW = W + BA
> 
> 其中：
> - W: 原始权重（d × d）
> - B: 下投影矩阵（d × r）
> - A: 上投影矩阵（r × d）
> - r: 秩（通常 8-64）
> 
> 更新参数量：2 × d × r（远小于 d²）
> ```
>
> **为什么 PEFT 成为主流？**
> 1. **显存友好**：70B 模型全量微调需要 1TB+ 显存，LoRA 只需 100GB
> 2. **训练快速**：只更新 1% 参数，训练速度提升 10x
> 3. **效果接近**：与全量微调效果差距 <1%
> 4. **多任务适配**：一个基础模型 + 多个 LoRA 适配器

**追问**：
- LoRA 的秩 r 如何选择？→ 通常 8-64，任务越复杂 r 越大
- QLoRA 的量化方法？→ NF4（Normal Float 4-bit）
- LoRA 可以合并到基础模型吗？→ 可以，推理时合并（无额外延迟）

**面试加分点**：
- 提到 2026 年趋势：QLoRA 成为单 GPU 微调标配
- 提到 LoRA 的变体（DoRA、AdaLoRA、LoRA-FA）
- 提到多 LoRA 适配器（一个基础模型服务多个任务）

#### Q8: RLHF、DPO、GRPO 的区别？对齐技术如何演进？

**参考答案**：
> **对齐技术演进路线**：
>
> | 技术 | 年份 | 核心思想 | 优点 | 缺点 |
> |------|------|---------|------|------|
> | **RLHF** | 2022 | 用 PPO 优化偏好数据 | 效果好 | 训练复杂、不稳定 |
> | **DPO** | 2023 | 无 RL，直接从偏好对优化 | 简单、稳定 | 效果略差 |
> | **GRPO** | 2024 | 生成式拒绝偏好优化 | 效果更好 | 计算成本高 |
>
> **RLHF（Reinforcement Learning from Human Feedback）**：
> ```
> 1. SFT：监督微调（学习对话格式）
> 2. 奖励模型：训练偏好模型（学习人类偏好）
> 3. PPO：用奖励模型指导策略优化
> ```
>
> **DPO（Direct Preference Optimization）**：
> ```
> 直接优化偏好对 (y_w, y_l)：
> L_DPO = -log σ(β · (log π(y_w|x)/π_ref(y_w|x) - log π(y_l|x)/π_ref(y_l|x)))
> 
> 无需奖励模型，无需 RL
> ```
>
> **GRPO（Generative Rejection Preference Optimization）**：
> ```
> 2024 年 DeepSeek 提出：
> - 生成多个候选回答
> - 拒绝低质量回答
> - 优化高质量回答
> ```

**追问**：
- 为什么 DPO 比 RLHF 简单？→ 无需训练奖励模型，无需 PPO
- GRPO 的核心创新？→ 生成式拒绝（生成多个候选，拒绝低质量）
- 2026 年主流对齐技术？→ DPO + GRPO 混合

**面试加分点**：
- 提到 2026 年趋势：DPO 成为主流（简单、稳定）
- 提到 Constitutional AI（Anthropic 的自我批评机制）

### 8.4 部署优化题（字节高频）

#### Q9: 如何加速 LLM 推理？量化、并行、缓存策略？

**参考答案**：
> **三大优化方向**：
>
> | 方向 | 技术 | 加速比 | 效果损失 |
> |------|------|--------|---------|
> | **量化** | AWQ/GPTQ（4-bit）、SmoothQuant（8-bit） | 2-4x | <1% |
> | **并行** | Tensor Parallelism、Pipeline Parallelism | 2-8x | 0% |
> | **缓存** | KV Cache、Prompt Caching | 2-10x | 0% |
>
> **量化技术对比**：
>
> | 技术 | 精度 | 原理 | 适用场景 |
> |------|------|------|---------|
> | **AWQ** | 4-bit | 激活感知量化（保护重要权重） | 通用 |
> | **GPTQ** | 4-bit | 基于 Hessian 的量化 | 通用 |
> | **SmoothQuant** | 8-bit | 平滑激活和权重 | 大模型 |
> | **QLoRA** | 4-bit | NF4 量化 + LoRA | 微调 |
>
> **并行策略**：
> ```
> Tensor Parallelism（TP）：
> - 将矩阵乘法切分到多个 GPU
> - 适合单模型推理
> 
> Pipeline Parallelism（PP）：
> - 将模型层切分到多个 GPU
> - 适合大模型训练
> 
> Data Parallelism（DP）：
> - 多个 GPU 处理不同数据
> - 适合批量推理
> ```
>
> **缓存策略**：
> - **KV Cache**：避免重复计算（见 Q5）
> - **Prompt Caching**：相同 Prompt 返回缓存结果
> - **Prefix Caching**：相同前缀共享 KV Cache

**追问**：
- 量化后效果下降怎么办？→ 使用 AWQ（保护重要权重）
- 多 GPU 如何选择并行策略？→ TP 适合推理，PP 适合训练
- vLLM 的核心优化？→ PagedAttention（动态分配 KV Cache）

**面试加分点**：
- 提到 2026 年主流推理框架：vLLM、TensorRT-LLM、SGLang
- 提到 PagedAttention（vLLM 的核心优化，类似操作系统分页）
- 提到 Continuous Batching（动态批处理，提升吞吐量）

### 8.5 提示工程题（腾讯高频）

#### Q11: Zero-shot、Few-shot、CoT、ToT 的区别？如何选择？

**参考答案**：
> **提示工程类型对比**：
>
> | 类型 | 示例 | 适用场景 | 效果提升 |
> |------|------|---------|---------|
> | **Zero-shot** | "翻译这句话：..." | 简单任务 | 基线 |
> | **Few-shot** | 提供 1-5 个示例 | 格式要求 | +10-20% |
> | **CoT**（Chain-of-Thought） | "一步步思考" | 复杂推理 | +20-50% |
> | **ToT**（Tree-of-Thoughts） | 多路径搜索 | 规划任务 | +30-60% |
>
> **CoT（Chain-of-Thought）**：
> ```
> 问题：一个商店有 23 个苹果，卖了 17 个，又进了 6 个，现在有多少个？
> 
> Zero-shot: 12 个（错误）
> 
> CoT: 
> 1. 一开始有 23 个
> 2. 卖了 17 个，剩下 23 - 17 = 6 个
> 3. 又进了 6 个，现在 6 + 6 = 12 个
> 答案：12 个（正确）
> ```
>
> **ToT（Tree-of-Thoughts）**：
> ```
> 1. 生成多个候选思路（分支）
> 2. 评估每个思路的质量（打分）
> 3. 选择最优思路继续（剪枝）
> 4. 重复直到得出最终答案
> ```

**追问**：
- CoT 为什么有效？→ 强制模型分解问题，减少推理跳跃
- Few-shot 示例如何选择？→ 覆盖不同场景，避免偏差
- ToT 的成本？→ 多次 LLM 调用，成本增加 3-5x

**面试加分点**：
- 提到 2026 年趋势：CoT 成为复杂任务标配
- 提到 Self-Consistency（多次采样取多数）
- 提到 Skeleton-of-Thought（先骨架后细节）

### 8.6 生产实战题（区分度最高）

#### Q12: LLM 在生产环境中的常见坑和解决方案？

**参考答案**：
>
> | 问题 | 原因 | 解决方案 |
> |------|------|---------|
> | **幻觉** | 模型生成虚假信息 | RAG（检索增强）、工具验证、人工审核 |
> | **延迟高** | 模型推理慢 | 流式输出、模型量化、KV Cache |

> | **安全风险** | 提示注入、越权 | 输入过滤、权限控制、审计日志 |

## 九、最佳实践

### 9.1 开发建议

1. **优先使用流式输出**：提升用户体验，减少首字延迟
2. **配置合理的 context_size**：影响上下文压缩的触发阈值
3. **使用结构化输出**：需要固定格式输出时，比 prompt 工程更可靠
4. **配置 fallback_model**：生产环境必须配置备用模型

---

### 9.2 性能优化

1. **Token 计数优化**：高频调用时使用精确计数（tiktoken）
2. **流式响应处理**：避免在累积器中做字符串拼接（使用 list + join）
3. **连接池复用**：通过 `client_kwargs` 配置 HTTP 连接池

---

### 9.3 安全建议

1. **凭证管理**：使用 `CredentialBase` 封装 API Key，避免硬编码
2. **输入验证**：`_validate_tool_choice()` 验证工具选择参数
3. **输出过滤**：在中间件中过滤敏感信息
