## 一、核心概念

### 1.1 什么是权限系统？

**权限系统（Permission System）** 拦截 Agent 的每一次工具调用，给出三种决策之一：**允许（ALLOW）** 执行、**拒绝（DENY）** 执行，或者**询问用户（ASK）** 确认。

它把静态配置与动态运行时分析组合起来：

```
┌─────────────────────────────────────────────────────────────┐
│                    权限系统全景                                │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │   Rules      │  │    Mode      │  │ Built-in     │      │
│  │  (规则)      │  │   (模式)     │  │  Checks      │      │
│  │  最高优先级   │  │  全局策略     │  │  (内置检查)   │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
│                                                             │
│  5 种模式：DEFAULT / ACCEPT_EDITS / EXPLORE / BYPASS / DONT_ASK │
│  4 种行为：ALLOW / DENY / ASK / PASSTHROUGH                 │
└─────────────────────────────────────────────────────────────┘
```

**关键理解** 🔴：
- **Rules（规则）**：针对每个 tool 与命令的显式 allow/deny/ask 模式，最高优先级
- **Mode（模式）**：配置阶段设定的全局静态策略，决定不命中任何规则的调用的默认行为
- **Built-in Checks（内置检查）**：由 tool 自身在运行时基于真实输入做的动态分析

---

### 1.2 为什么需要权限系统？

| 需求 | 没有权限系统 | 有权限系统 |
|------|-------------|-----------|
| 安全控制 | 工具随意执行 | 分层权限检查 |
| 用户确认 | 无 | ASK 决策暂停执行 |
| 只读模式 | 无 | EXPLORE 模式自动拒绝修改 |
| 无人值守 | 无法运行 | DONT_ASK 模式安全运行 |
| 沙箱环境 | 无 | BYPASS 模式跳过安全检查 |
| 规则持久化 | 无 | 已接受的规则自动允许 |

**核心矛盾**：
- Agent 需要**自主执行**工具完成任务
- 用户需要**控制**危险操作

**AgentScope 的解法**：三层决策（规则 → 模式 → 内置检查）+ 五种模式适配不同场景

## 二、核心接口

### 2.1 权限模式（PermissionMode）

```python
# src/agentscope/permission/_types.py:18
class PermissionMode(Enum):
    DEFAULT = "default"          # 最安全，推荐默认值
    ACCEPT_EDITS = "accept_edits" # 自动放行工作目录内的文件操作
    EXPLORE = "explore"          # 只读模式
    BYPASS = "bypass"            # 跳过所有安全检查
    DONT_ASK = "dont_ask"        # 所有 ASK 转为 DENY
```

| Mode | 行为 | 适用场景 |
|------|------|---------|
| `DEFAULT` | 所有操作都需要显式规则或用户确认。唯一自动放行路径是 Bash 识别只读命令 | 最安全，推荐默认值 |
| `ACCEPT_EDITS` | 自动放行工作目录内的文件操作；Bash filesystem 命令仅当所有目标路径都在工作目录内才自动放行 | 用户在场的活跃开发 |
| `EXPLORE` | 只读：放行 read-only 工具与只读 Bash 命令；拒绝任何修改 | 代码探索、规划 |
| `BYPASS` | 跳过所有权限检查，除了 deny/ask 规则与工具自身的 DENY | 沙箱环境或完全可信的运行 |
| `DONT_ASK` | 把所有 ASK 转为 DENY；非交互式运行下默认安全 | 无人值守 / 计划任务 |

### 2.4 权限决策（PermissionDecision）

```python
# src/agentscope/permission/_decision.py:10
@dataclass
class PermissionDecision:
    behavior: PermissionBehavior          # 决策行为
    message: str                          # 人类可读消息
    decision_reason: str | None = None    # 决策原因
    updated_input: dict | None = None     # 修改后的输入（如清理后的路径）
    suggested_rules: list[PermissionRule] | None = None  # 建议规则
    bypass_immune: bool = False           # 是否不可被 allow 规则覆盖
```

**bypass_immune 关键理解** 🔴：
- `True`：安全 ASK，即使命中 allow 规则也不能覆盖，用户必须显式确认
- `False`：普通 ASK，allow 规则可以将其转为 ALLOW
- BYPASS 模式按设计跳过所有 safety ASK

## 三、设计原理

### 3.1 策略模式实现

```python
# src/agentscope/permission/_engine.py:76
async def check_permission(self, tool, tool_input):
    """策略模式：根据 mode 分发到不同的检查方法"""
    mode = self.context.mode
    if mode == PermissionMode.DEFAULT:
        return await self._check_default(tool, tool_input)
    if mode == PermissionMode.EXPLORE:
        return await self._check_explore(tool, tool_input)
    if mode == PermissionMode.ACCEPT_EDITS:
        return await self._check_accept_edits(tool, tool_input)
    if mode == PermissionMode.BYPASS:
        return await self._check_bypass(tool, tool_input)
    if mode == PermissionMode.DONT_ASK:
        return await self._check_dont_ask(tool, tool_input)
```

**关键点** 🔴：
- 每个模式有独立的 `_check_<mode>` 方法
- 模式策略自包含，可读性强
- 新增模式只需添加新方法

---

### 3.2 DEFAULT 模式检查流程

```
1. Deny rules → DENY（最高优先级）
2. Ask rules → ASK（带建议规则）
3. tool.check_permissions():
   - ALLOW / DENY → 直接返回
   - Safety ASK (bypass_immune=True) → 返回，allow 规则不能覆盖
   - 非安全 ASK / PASSTHROUGH → 继续
4. Allow rules → ALLOW
5. Default → ASK（带建议规则）
```

```python
# src/agentscope/permission/_engine.py:116
async def _check_default(self, tool, tool_input):
    # step 1: deny rules — 最高优先级
    deny = self._check_deny_rules(tool, tool_input)
    if deny:
        return deny
    
    # step 2: ask rules
    ask = self._check_ask_rules(tool, tool_input)
    if ask:
        ask.suggested_rules = self._generate_suggestions(tool, tool_input)
        return ask
    
    # step 3: tool's own check_permissions
    tool_decision = await tool.check_permissions(tool_input, self.context)
    if tool_decision.behavior in (ALLOW, DENY):
        return tool_decision
    if self._is_safety_ask(tool_decision):
        tool_decision.suggested_rules = self._generate_suggestions(tool, tool_input)
        return tool_decision
    
    # step 4: allow rules
    allow = self._check_allow_rules(tool, tool_input)
    if allow:
        return allow
    
    # step 5: default — ASK the user
    default = PermissionDecision(behavior=ASK, message=f"Permission required for {tool.name}")
    default.suggested_rules = self._generate_suggestions(tool, tool_input)
    return default
```

### 3.3 EXPLORE 模式检查流程

```
1. Deny rules → DENY
2. Ask rules → ASK（带建议规则）
3. tool.check_read_only():
   - True → ALLOW
   - False → DENY
```

> **注**：`tool.check_permissions` 不被调用。EXPLORE 完全由只读判定决断，allow 规则也不能授予写权限。

### 3.4 v2.0.4.post1 增强：统一 per-mode 评估与只读快速路径（#2117）

v2.0.4.post1 对权限引擎做了一次**架构性收敛**：把"只读快速路径"从各模式的重复实现抽成共享 helper `_check_read_only_fast_path()`，并让所有 `_check_<mode>` 方法都调用它。

**为什么这样改（设计动机）**：
- 在 post1 之前，只读快速路径只内联在 `ACCEPT_EDITS` / `EXPLORE` 中，`DEFAULT` 和 `DONT_ASK` 没有，导致同一句只读 Bash 命令（如 `ls`、`grep`）在不同模式下走不同分支——既违反直觉，也埋下"某模式漏判只读 → 误弹 ASK / 误拒"的隐患。
- 各模式逻辑一旦分叉，后续新增模式极易再次漂移。把共享逻辑收口到单一 helper，是用**单一事实源（Single Source of Truth）**换可维护性。

**实现要点**（`src/agentscope/permission/_engine.py`）：
- `check_permission()` 按 `mode` 分发到 `_check_default / _check_explore / _check_accept_edits / _check_bypass / _check_dont_ask`，每个方法**自包含、可读**。
- 6 步评估顺序中（Deny → Ask → **只读快速路径** → tool 自身判定 → Allow → 兜底），第 3 步对**所有模式一致**。
- EXPLORE 的兜底直接 `DENY`；DONT_ASK 把任何会 ASK 的路径经 `_convert_ask_to_deny` 转为 `DENY`（并保留 `suggested_rules` 供前端展示"加哪条规则可解锁"）。

**"批量确认豁免"传播**：
当用户对一类操作确认时，引擎通过 `_generate_suggestions()` 从工具调用提炼出**更宽的建议规则**（如 `Bash` 提取 `npm run:*`、文件操作提取 `src/**`）。这条机制现在在 DEFAULT/ACCEPT_EDITS 中产出、在 DONT_ASK 中保留，使"确认一次、豁免一类"的体验在五种模式下行为一致。

**替代方案与 trade-off**：
- *替代*：完全扁平的 if/else 大函数，按 `mode` 分支。可读但极易重复、难测试。
- *trade-off*：策略模式（每模式一方法）+ 共享 helper，牺牲了少量代码紧凑度，换来模式间逻辑零漂移与单测可隔离。

**⚠️ 面试考点**：
- 权限引擎用了哪种设计模式？答：**策略模式**（每模式一个 `_check_<mode>`）+ **模板方法**（共享 6 步骨架，仅 per-mode 细节不同）。
- 为什么 EXPLORE 不调用 `tool.check_permissions`？答：EXPLORE 的只读保证是**绝对**的，allow 规则也不能授予写权限，故直接跳过工具层判定，安全 ASK（如 `rm -rf /`）被更大的 DENY 吸收。
- `_check_read_only_fast_path` 为什么必须共享？答：避免各模式对"什么是只读"判断不一致（真实 bug 来源）。

### 3.4 ACCEPT_EDITS 模式检查流程

```
1. Deny rules → DENY
2. Ask rules → ASK（带建议规则）
3. tool.check_read_only() → True → ALLOW（快速路径）
4. tool.check_permissions():
   - ALLOW / DENY → 直接返回
   - Safety ASK (bypass_immune=True) → 返回
   - 非安全 ASK / PASSTHROUGH → 继续
5. Allow rules → ALLOW
6. Default → ASK（带建议规则）
```

---

### 3.5 BYPASS 模式检查流程

```
1. Deny rules → DENY
2. Ask rules → ASK（尊重用户显式意图）
3. tool.check_permissions():
   - ALLOW / DENY → 直接返回
   - ASK（包括 bypass_immune safety ASK）→ 跳过，继续
   - PASSTHROUGH → 继续
4. Allow rules → ALLOW
5. Fallback → ALLOW（BYPASS 放行一切）
```

> **注**：BYPASS 按设计跳过所有 safety ASK。`bypass_immune` 字段在 BYPASS 下无效。

---

### 3.6 DONT_ASK 模式检查流程

```
1. Deny rules → DENY
2. Ask rules → DENY（转换，保留建议规则）
3. tool.check_permissions():
   - ALLOW / DENY → 直接返回
   - Safety ASK → DENY（转换，保留建议规则）
   - 非安全 ASK / PASSTHROUGH → 继续
4. Allow rules → ALLOW
5. Default → DENY（用户不可用）
```

> **不变量**：DONT_ASK 模式永远不会返回 ASK。

### 3.7 规则匹配机制

```python
# src/agentscope/permission/_engine.py:634
def _rule_matches(self, tool, rule, input_data):
    """规则匹配：委托给 tool 的 match_rule 方法"""
    if not rule.rule_content:
        return True  # 空 rule_content 匹配所有调用
    return tool.match_rule(rule.rule_content, input_data)
```

**各工具的匹配策略**：

| 工具 | 匹配方式 | 示例 |
|------|---------|------|
| Bash | 命令前缀 + `:*` | `npm run:*` 匹配 `npm run build` |
| Write/Read/Edit | `fnmatch` glob 匹配 | `src/**/*.py` 匹配 `src/main.py` |
| 其他工具 | 工具名级别匹配 | `None` 匹配所有调用 |

  ├── [决策处理]
  │     │  # 根据权限检查结果决定下一步
  │     │
  │     ├── ALLOW → 执行工具
  │     │    # 权限允许，继续执行工具
  │     │
  │     ├── DENY → 返回错误
  │     │    # 权限拒绝，返回错误消息给 Agent
  │     │
  │     └── ASK → 暂停执行，发出 RequireUserConfirmEvent
  │          # 需要用户确认，暂停执行
  │          # 发出事件，等待用户响应
  │
  └── Agent._acting()                          ← 执行工具
       # 权限检查通过后，执行工具
```

## 七、面试题

### 7.1 基础题

#### Q1: 权限系统的核心职责是什么？

**参考答案**：
> 权限系统拦截 Agent 的每一次工具调用，给出 ALLOW/DENY/ASK 三种决策之一。它把静态配置（Rules/Mode）与动态运行时分析（Built-in Checks）组合起来，确保危险操作需要用户确认。

**关键点**：
- 三层决策（Rules → Mode → Built-in Checks）
- 三种行为（ALLOW/DENY/ASK）
- 五种模式适配不同场景

---

#### Q2: 五种权限模式分别适用于什么场景？

**参考答案**：
> - `DEFAULT`：最安全，所有操作都需要显式规则或用户确认
> - `ACCEPT_EDITS`：自动放行工作目录内的文件操作，适合活跃开发
> - `EXPLORE`：只读模式，拒绝任何修改，适合代码探索
> - `BYPASS`：跳过所有安全检查，适合沙箱环境
> - `DONT_ASK`：所有 ASK 转为 DENY，适合无人值守运行

**关键点**：
- 五种模式
- 不同场景
- 安全级别递减

---

#### Q3: 规则匹配的优先级是什么？

**参考答案**：
> Deny rules（最高优先级）→ Ask rules → tool.check_permissions() → Allow rules → Default（ASK）。Deny 规则在任何模式下都始终生效。

**关键点**：
- 固定检查顺序
- Deny 最高优先级
- Default 是 ASK

---

### 7.2 进阶题

#### Q4: bypass_immune 是什么？

**参考答案**：
> `bypass_immune=True` 标记一个 ASK 为安全 ASK，即使命中 allow 规则也不能将其覆盖为 ALLOW。工具对危险操作（如写入 `~/.bashrc`、`rm -rf /`）设置此标记。在 DEFAULT/ACCEPT_EDITS 下被尊重，BYPASS 下被忽略，DONT_ASK 下转为 DENY。

**关键点**：
- 安全 ASK 不可被覆盖
- 各模式处理不同
- 工具自己设置

---

#### Q5: 策略模式在权限系统中如何应用？

**参考答案**：
> `PermissionEngine.check_permission()` 根据 `context.mode` 分发到不同的 `_check_<mode>()` 方法。每个模式有独立的检查流程，自包含可读。新增模式只需添加新方法，符合开闭原则。

**关键点**：
- 策略模式
- 5 个独立方法
- 开闭原则

---

#### Q6: 建议规则是如何工作的？

**参考答案**：
> 当权限系统返回 ASK 时，调用 `tool.generate_suggestions()` 基于本次调用生成建议规则。例如 Bash 工具提取命令前缀（`git commit -m 'xxx'` → `git commit:*`），文件工具提取父目录（`src/main.py` → `src/**`）。用户接受后，规则被持久化到引擎，未来相同调用自动允许。

**关键点**：
- 基于本次调用生成
- 各工具自定义策略
- 接受后持久化

---

#### Q7: DONT_ASK 模式如何保证安全？

**参考答案**：
> DONT_ASK 模式的不变量是"永远不会返回 ASK"。所有 ASK（包括规则 ASK 和安全 ASK）都被 `_convert_ask_to_deny()` 转为 DENY，同时保留建议规则供后续参考。Default 也是 DENY。这样无人值守运行时，未明确允许的操作都被拒绝。

**关键点**：
- 不变量：永不返回 ASK
- ASK → DENY 转换
- 保留建议规则

---

### 7.3 场景题

#### Q8: 如何为沙箱环境配置权限？

**参考答案**：
> 使用 BYPASS 模式跳过所有安全检查，但通过 deny 规则保护关键路径：

```python
PermissionContext(
    mode=PermissionMode.BYPASS,
    deny_rules={
        "Bash": [PermissionRule(tool_name="Bash", rule_content="rm:*", behavior=DENY, ...)],
        "Write": [PermissionRule(tool_name="Write", rule_content="/etc/**", behavior=DENY, ...)],
    },
)
```

**关键点**：
- BYPASS 模式
- deny 规则保护关键路径
- 跳过 safety ASK

---

#### Q9: 如何实现一个自定义工具的权限检查？

**参考答案**：
> 重写 `check_permissions()` 和 `check_read_only()` 方法：

```python
class MyTool(ToolBase):
    async def check_read_only(self, tool_input):
        return tool_input.get("operation") in {"list", "describe"}
    
    async def check_permissions(self, tool_input, context):
        if tool_input.get("target", "").startswith("prod-"):
            return PermissionDecision(behavior=ASK, bypass_immune=True, ...)
        return PermissionDecision(behavior=PASSTHROUGH)
```

**关键点**：
- `check_permissions()` 运行时检查
- `check_read_only()` 只读判定
- `bypass_immune=True` 标记危险操作

#### Q10: 权限系统与 HITL 是如何集成的？

**参考答案**：
> 当权限引擎返回 ASK 决策时，Agent 发出 `RequireUserConfirmEvent` 并暂停执行。前端收到事件后显示确认框，用户确认后发送 `UserConfirmResultEvent`（可附带已接受的规则），Agent 恢复执行。已接受的规则通过 `PermissionEngine.add_rule()` 持久化到引擎。

**关键点**：
- ASK → RequireUserConfirmEvent
- 暂停/恢复机制
- 规则持久化

## 八、面试题（2026 最新版）

> 基于 2026 年大厂真题（字节、阿里、腾讯、OpenAI、Anthropic）和最新技术趋势整理

### 8.1 基础概念题（必问）

#### Q1: RBAC、ABAC、PBAC 的区别是什么？AI Agent 应该用哪种？（阿里、腾讯高频）

**参考答案**：
> **三种权限模型对比**：
>
> | 模型 | 核心思想 | 优点 | 缺点 | 适用场景 |
> |------|---------|------|------|---------|
> | **RBAC**（Role-Based） | 基于角色授权 | 简单、易管理 | 静态、不灵活 | 传统企业系统 |
> | **ABAC**（Attribute-Based） | 基于属性授权（用户、资源、环境） | 灵活、细粒度 | 复杂、性能开销大 | 云原生系统 |
> | **PBAC**（Policy-Based） | 基于策略语言（OPA/Cedar） | 表达力强、可审计 | 学习曲线陡 | 企业级系统 |
>
> **AI Agent 应该用哪种？**
>
> | 场景 | 推荐方案 | 原因 |
> |------|---------|------|
> | 简单 Agent | RBAC | 快速实现，角色固定 |
> | 复杂 Agent | ABAC | 需要根据任务动态授权 |
> | 企业级 Agent | PBAC | 需要策略引擎（OPA） |
>
> **2026 年趋势**：RBAC 做骨架，ABAC 加条件，PBAC 负责落地引擎
>
> **为什么 RBAC 对 AI Agent 不够？**
> - RBAC 假设角色是静态的（如"销售经理"）
> - AI Agent 的任务是动态的（今天分析销售，明天处理合同）
> - Agent 拿着"销售经理"的权限，实际只需要 5% 的数据，剩下 95% 是风险

**追问**：
- ABAC 的属性有哪些？→ 用户属性、资源属性、环境属性（时间、地点）、操作属性
- PBAC 的策略语言有哪些？→ OPA（Rego）、Cedar、Datalog
- 如何评估权限模型的效果？→ 安全性、性能、可维护性

**面试加分点**：
- 提到 RBAC → ABAC → PBAC 的演进路线
- 提到 AI Agent 的动态任务特性
- 提到 OPA（Open Policy Agent）策略引擎

---

#### Q2: 最小权限原则（Least Privilege）在 AI Agent 中如何实现？（字节高频）

**参考答案**：
> **最小权限原则**：Agent 应仅请求当前任务所需的权限，避免在任务范围之外持久化敏感数据
>
> **传统最小权限 vs AI Agent 最小权限**：
>
> | 维度 | 传统系统 | AI Agent |
> |------|---------|---------|
> | **权限授予时机** | 部署时（静态） | 运行时（动态） |
> | **权限范围** | 固定角色 | 任务范围 |
> | **权限生命周期** | 长期有效 | 会话级别 |
> | **权限撤销** | 手动 | 自动过期 |
>
> **实现策略**：
>
> | 策略 | 实现方式 | 效果 |
> |------|---------|------|
> | **任务范围令牌** | OAuth 2.0 + 细粒度 scope | 权限限定于当前任务 |
> | **短期凭证** | JWT + 短 TTL（30s-5min） | 凭证自动过期 |
> | **动态权限** | 运行时评估（ABAC） | 根据任务动态授权 |
> | **权限隔离** | 双层边界（执行边界 + 暴露边界） | 工具和数据独立控制 |
>
> **代码示例**：
> ```python
> # 任务范围令牌
> async def get_task_scoped_token(task: Task, user: User):
>     # 1. 评估任务需要的权限
>     required_scopes = evaluate_task_scopes(task)
>     
>     # 2. 铸造短期令牌（TTL = 30s）
>     token = jwt.encode({
>         "sub": user.id,
>         "scopes": required_scopes,
>         "task_id": task.id,
>         "exp": datetime.utcnow() + timedelta(seconds=30)
>     })
>     
>     return token
>

#### Q3: 权限系统的三层决策是什么？各层的作用是什么？

**参考答案**：
> **三层决策架构**：
> ```
> 1. Rules（规则层）- 最高优先级
>    ├── allow_rules：允许规则
>    ├── deny_rules：拒绝规则
>    └── ask_rules：询问规则
> 
> 2. Mode（模式层）- 全局策略
>    ├── DEFAULT：最安全，所有操作需要确认
>    ├── ACCEPT_EDITS：自动放行工作目录内的文件操作
>    ├── EXPLORE：只读模式
>    ├── BYPASS：跳过所有安全检查
>    └── DONT_ASK：所有 ASK 转为 DENY
> 
> 3. Built-in Checks（内置检查层）- 动态分析
>    ├── tool.check_permissions()：工具自身检查
>    ├── tool.check_read_only()：只读判定
>    └── bypass_immune：安全 ASK 不可被覆盖
> ```
>
> **各层的作用**：
>
> | 层级 | 作用 | 优先级 | 示例 |
> |------|------|--------|------|
> | **Rules** | 显式规则，用户配置 | 最高 | `npm run:*` → ALLOW |
> | **Mode** | 全局策略，配置阶段设定 | 中等 | DEFAULT → ASK |
> | **Built-in** | 动态分析，运行时检查 | 最低 | 危险路径 → ASK |
>
> **决策流程**：
> ```
> 1. Deny rules → DENY（最高优先级）
> 2. Ask rules → ASK（带建议规则）
> 3. tool.check_permissions():
>    - ALLOW / DENY → 直接返回
>    - Safety ASK (bypass_immune=True) → 返回，allow 规则不能覆盖
>    - 非安全 ASK / PASSTHROUGH → 继续
> 4. Allow rules → ALLOW
> 5. Default → ASK（带建议规则）
> ```

**追问**：
- 为什么 deny 规则优先级最高？→ 安全优先，防止误操作
- 为什么 bypass_immune 不可被覆盖？→ 真正的危险操作必须用户确认
- 如何评估三层决策的效果？→ 规则命中率、用户确认次数

**面试加分点**：

> 1. Agent 调用工具

>     # 1. 获取工具
>     tool = agent.toolkit.get_tool(tool_call.name)
>     
>     # 2. 权限检查
>     decision = await agent.permission_engine.check_permission(
>         tool=tool,
>         tool_input=tool_call.arguments
>     )
>

>     if decision.behavior == PermissionBehavior.ALLOW:
>         # 执行工具

>             reply_id=agent.state.reply_id,
>             tool_calls=[tool_call],
>             message=decision.message,

>

>         # ... (HITL 机制)
> ```

#### Q5: 如何实现规则持久化和自动允许？

**参考答案**：
> **规则持久化机制**：
> ```
> 1. 用户确认 ASK 决策
>    └── UserConfirmResultEvent(rules=[accepted_rules])
> 
> 2. 规则写入引擎
>    └── PermissionEngine.add_rule(rule)
>         │
>         ├── 规则分类（allow/deny/ask）
>         ├── 规则存储（dict[str, list[PermissionRule]]）
>         └── 规则持久化（保存到磁盘/数据库）
> 
> 3. 后续调用自动应用
>    └── 相同工具调用 → 匹配规则 → ALLOW
> ```
>
> **代码示例**：
> ```python
> class PermissionEngine:
>     def __init__(self, context: PermissionContext):
>         self.context = context
>         self.allow_rules = context.allow_rules  # dict[str, list[PermissionRule]]
>         self.deny_rules = context.deny_rules
>         self.ask_rules = context.ask_rules
>     
>     def add_rule(self, rule: PermissionRule):
>         """添加规则并持久化"""
>         # 1. 规则分类
>         if rule.behavior == PermissionBehavior.ALLOW:
>             rules_dict = self.allow_rules
>         elif rule.behavior == PermissionBehavior.DENY:
>             rules_dict = self.deny_rules
>         else:
>             rules_dict = self.ask_rules
>         
>         # 2. 规则存储
>         if rule.tool_name not in rules_dict:
>             rules_dict[rule.tool_name] = []
>         rules_dict[rule.tool_name].append(rule)
>         
>         # 3. 规则持久化
>         self._persist_rules()
>     
>     def _persist_rules(self):
>         """持久化规则到磁盘"""
>         rules_data = {
>             "allow_rules": self.allow_rules,
>             "deny_rules": self.deny_rules,
>             "ask_rules": self.ask_rules
>         }
>         with open("permission_rules.json", "w") as f:
>             json.dump(rules_data, f)
> ```

> **建议规则生成**：
> ```python
> # Bash 工具生成建议规则
> def generate_suggestions(self, tool_input: dict):
>     command = tool_input.get("command", "")
>     
>     # 提取命令前缀
>     # "git commit -m 'xxx'" → "git commit:*"
>     parts = command.split()
>     if len(parts) >= 2:
>         prefix = f"{parts[0]} {parts[1]}:*"
>         return [PermissionRule(
>             tool_name="Bash",
>             rule_content=prefix,
>             behavior=PermissionBehavior.ALLOW,
>             source="session"
>         )]
>     
>     return []
> 
> # Write 工具生成建议规则
> def generate_suggestions(self, tool_input: dict):
>     file_path = tool_input.get("file_path", "")
>     
>     # 提取父目录
>     # "src/main.py" → "src/**"
>     parent_dir = os.path.dirname(file_path)
>     if parent_dir:
>         return [PermissionRule(
>             tool_name="Write",
>             rule_content=f"{parent_dir}/**",
>             behavior=PermissionBehavior.ALLOW,
>             source="session"
>         )]
>     
>     return []
> ```

>

> ```python

>     # 2. Ask rules

>         return ask
>     
>     # 3. Tool check
>     tool_decision = await tool.check_permissions(tool_input, self.context)
>     if tool_decision.behavior in (ALLOW, DENY):
>         return tool_decision
>     
>     # 4. Allow rules
>     allow = self._check_allow_rules(tool, tool_input)

>         return allow
>     
>     # 5. Default
>     return PermissionDecision(behavior=ASK)

> ```python
> class PermissionRule(BaseModel):
>     tool_name: str
>     rule_content: str | None
>     behavior: PermissionBehavior
>     source: str
>     created_at: datetime  # 创建时间
>     ttl: int | None = None  # 过期时间（秒）
>     
>     def is_expired(self):
>         if self.ttl is None:
>             return False
>         return datetime.utcnow() > self.created_at + timedelta(seconds=self.ttl)
> 
> # 定期清理过期规则
> async def cleanup_expired_rules(self):
>     for tool_name, rules in self.allow_rules.items():
>         self.allow_rules[tool_name] = [
>             rule for rule in rules if not rule.is_expired()

#### Q8: 如何优化权限系统的性能？（阿里高频）

> class PermissionEngine:
>     def __init__(self, context: PermissionContext):
>         self.context = context

>         # 1. 规则预分类

>         # 5. 缓存结果
>         self.policy_cache[cache_key] = decision
>         return decision
>     
>     def _build_rule_index(self):
>         """建立规则索引"""
>         for tool_name, rules in self.allow_rules.items():

>         for tool_name, rules in self.deny_rules.items():
>             if tool_name not in self.rule_index:
>                 self.rule_index[tool_name] = []
>             self.rule_index[tool_name].extend(rules)
>         
>         for tool_name, rules in self.ask_rules.items():
>             if tool_name not in self.rule_index:
>                 self.rule_index[tool_name] = []
>             self.rule_index[tool_name].extend(rules)

## 九、最佳实践

### 9.1 开发建议

1. **默认使用 DEFAULT 模式**：最安全，推荐默认值
2. **配置 deny 规则保护关键路径**：如 `rm:*`、`/etc/**`
3. **使用建议规则减少确认**：用户接受后自动允许相同调用
4. **沙箱环境用 BYPASS + deny 规则**：跳过安全检查但保留护栏

---

### 9.2 性能优化

1. **规则按工具名分组**：`dict[str, list[PermissionRule]]` 快速查找
2. **只读快速路径**：`check_read_only()` 避免调用 `check_permissions()`
3. **预分类规则**：allow/deny/ask 规则分开存储

---

### 9.3 安全建议

1. **危险路径保护**：不要修改 `dangerous_files` 和 `dangerous_directories`
2. **bypass_immune 谨慎使用**：只对真正的危险操作设置
3. **BYPASS 模式配合 deny 规则**：不要裸用 BYPASS
4. **DONT_ASK 用于无人值守**：所有 ASK 转为 DENY
