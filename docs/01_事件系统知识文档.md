## 一、核心概念

### 1.1 什么是事件系统？

**事件系统**是 AgentScope 中用于**流式传输 Agent 执行状态**的机制。

```
消息 (Msg)  ←→  事件 (Event)
  静态视图        动态视图
  完整快照        流式传输
  持久化存储      实时渲染
```

**关键理解**：
- **消息** = 一次完整的对话回合（如 Agent 的一次回复）
- **事件** = 消息的流式传输单元（如逐字输出的文本）
- **关系**：一个消息由多个事件组成，事件可以重建为消息

---

### 1.2 为什么需要事件系统？

| 需求 | 消息 | 事件 |
|------|------|------|
| 存到数据库，下次继续聊 | ✅ | ❌ |
| 发给 LLM 当上下文 | ✅ | ❌ |
| 前端打字机效果实时显示 |  太慢 | ✅ |
| 断线后恢复进度 |  只能从头 | ✅ 从检查点继续 |
| 人工确认（暂停/恢复） |  | ✅ |

**核心矛盾**：
- 存数据需要**完整**（消息）
- 传数据需要**实时**（事件）

**AgentScope 的解法**：事件可以组装成消息，消息可以拆成事件。

### 2.3 事件分类详解

#### 类别 1：生命周期事件

| 事件 | 触发时机 | 关键字段 |
|------|---------|---------|
| **ReplyStartEvent** | Agent 开始回复 | `session_id`, `reply_id`, `name` |
| **ReplyEndEvent** | Agent 完成回复 | `session_id`, `reply_id`, ⚠️`finished_reason`, ⚠️`error`(main 新增) |
| **ExceedMaxItersEvent** | 达到最大循环次数 | `reply_id`, `name` |

**作用**：标记一次回复的开始和结束

> ⚠️ **main 未发版（#2133）**：`ReplyEndEvent` 新增 `finished_reason: ReplyFinishedReason`（completed/interrupted/exceed_max_iters/error，默认 completed）与 `error: ErrorInfo | None`（仅 ERROR 时填充，含 8 类 `ErrorType` + 脱敏 message）。前端由此可区分"正常结束/中断/迭代耗尽/异常"，错误详情见 [12_接口知识文档](./12_接口知识文档.md) §5。

---

#### 类别 2：模型调用事件

| 事件 | 触发时机 | 关键字段 |
|------|---------|---------|
| **ModelCallStartEvent** | 开始调用 LLM | `reply_id`, `model_name` |
| **ModelCallEndEvent** | LLM 返回完成 | `reply_id`, `input_tokens`, `output_tokens` |

**作用**：记录 LLM 调用的 Token 消耗

---

#### 类别 3：内容块事件（Start/Delta/End 模式）

**文本块**：
| 事件 | 作用 | 关键字段 |
|------|------|---------|
| **TextBlockStartEvent** | 开始输出文本 | `reply_id`, `block_id` |
| **TextBlockDeltaEvent** | 文本增量（逐字） | `reply_id`, `block_id`, `delta` |
| **TextBlockEndEvent** | 文本输出结束 | `reply_id`, `block_id` |

**思考块**：
| 事件 | 作用 | 关键字段 |
|------|------|---------|
| **ThinkingBlockStartEvent** | 开始思考 | `reply_id`, `block_id` |
| **ThinkingBlockDeltaEvent** | 思考增量 | `reply_id`, `block_id`, `delta` |
| **ThinkingBlockEndEvent** | 思考结束 | `reply_id`, `block_id` |

**数据块**（多模态）：
| 事件 | 作用 | 关键字段 |
|------|------|---------|
| **DataBlockStartEvent** | 开始传输数据 | `reply_id`, `block_id`, `media_type` |
| **DataBlockDeltaEvent** | 数据增量（base64） | `reply_id`, `block_id`, `data`, `media_type` |
| **DataBlockEndEvent** | 数据传输结束 | `reply_id`, `block_id` |

**关键点** 🔴：
- 遵循 **Start → Delta → End** 模式
- `block_id` 用于关联同一内容块的事件
- `delta` 字段携带增量数据

---

#### 类别 4：工具调用事件

**工具调用请求**：
| 事件 | 触发时机 | 关键字段 |
|------|---------|---------|
| **ToolCallStartEvent** | 开始调用工具 | `reply_id`, `tool_call_id`, `tool_call_name` |
| **ToolCallDeltaEvent** | 工具参数增量 | `reply_id`, `tool_call_id`, `delta` |
| **ToolCallEndEvent** | 工具调用结束 | `reply_id`, `tool_call_id` |

**工具执行结果**：
| 事件 | 触发时机 | 关键字段 |
|------|---------|---------|
| **ToolResultStartEvent** | 开始接收结果 | `reply_id`, `tool_call_id`, `tool_call_name` |
| **ToolResultTextDeltaEvent** | 文本结果增量 | `reply_id`, `tool_call_id`, `delta` |
| **ToolResultDataDeltaEvent** | 数据结果增量 | `reply_id`, `tool_call_id`, `block_id`, `media_type` |
| **ToolResultEndEvent** | 结果接收完成 | `reply_id`, `tool_call_id`, `state` |

**关键点** 🔴：
- `tool_call_id` 用于关联工具调用和结果
- `state` 字段表示执行状态（success/error/denied/interrupted）

---

#### 类别 5：人工介入事件（HITL）

| 事件 | 触发时机 | 作用 |
|------|---------|------|
| **RequireUserConfirmEvent** | 需要用户确认 | 暂停执行，等待确认 |
| **UserConfirmResultEvent** | 用户已确认 | 恢复执行 |
| **RequireExternalExecutionEvent** | 需要外部执行 | 暂停，等待外部系统 |
| **ExternalExecutionResultEvent** | 外部执行完成 | 恢复执行 |

**关键点** 🔴：
- 这是**控制流**，不仅仅是数据流
- `RequireUserConfirmEvent` 会**暂停** Agent 执行
- `UserConfirmResultEvent` 会**恢复** Agent 执行

---

#### 类别 6：其他事件

| 事件 | 作用 |
|------|------|
| **HintBlockEvent** | 注入隐藏提示（给 LLM 的） |
| **CustomEvent** | 自定义事件（中间件扩展） |

## 三、设计原理

### 3.1 三级 ID 关联机制

```
reply_id      ← 这次回复的唯一标识
  │
  ├── block_id      ← 这个内容块的唯一标识（文本块/思考块/数据块）
  │     │
  │     └── TextBlockStartEvent(reply_id="r1", block_id="b1")
  │     └── TextBlockDeltaEvent(reply_id="r1", block_id="b1", delta="你")
  │     ── TextBlockEndEvent(reply_id="r1", block_id="b1")
  │
  ── tool_call_id  ← 这次工具调用的唯一标识
        │
        ├── ToolCallStartEvent(reply_id="r1", tool_call_id="t1", name="get_weather")
        ├── ToolCallDeltaEvent(reply_id="r1", tool_call_id="t1", delta='{"city":"北京"}')
        └── ToolCallEndEvent(reply_id="r1", tool_call_id="t1")
```

**关键点** 🔴：
- `reply_id`：每次回复开始时生成
- `block_id`：每个内容块开始时生成
- `tool_call_id`：LLM 返回时自带（模型生成的）

---

### 3.2 事件与消息的转换

#### 事件 → 消息（append_event）

```python
msg = AssistantMsg(name="agent", content=[], id=reply_id)

async for event in agent.reply_stream(user_msg):
    msg.append_event(event)  # 每个事件追加到消息

# 循环结束后，msg 就是完整的回复
```

**关键点** 🔴：
- `append_event` 根据 `block_id` / `tool_call_id` 自动归类
- 文本 Delta 事件会拼接到对应文本块
- 工具结果事件会设置工具调用的状态

---

#### 消息 → 事件（重放时）

```python
for event in msg.to_events():
    yield event
```

**关键点** 🔴：
- 消息可以拆分为事件序列
- 用于断点续传时的重放

---

### 3.3 事件产生机制（埋点）

**关键点** 🔴：所有事件都是**预先埋点**的

```python
# src/agentscope/agent/_agent.py:782
async def _reasoning_impl(self, tool_choice):
    # 埋点 1：模型调用开始
    yield ModelCallStartEvent(
        reply_id=self.state.reply_id,
        model_name=self.model.model,
    )
    
    # 调用 LLM
    res = await self._call_model(**kwargs)
    
    # 埋点 2：文本块开始
    if text_blocks:
        yield TextBlockStartEvent(...)
    
    # 埋点 3：文本增量
    yield TextBlockDeltaEvent(delta="...")
    
    # 埋点 4：文本块结束
    yield TextBlockEndEvent(...)
    
    # 埋点 5：模型调用结束
    yield ModelCallEndEvent(
        input_tokens=...,
        output_tokens=...,
    )
```

**关键点** 🔴：
- 使用 `yield` 关键字让函数变成异步生成器
- 每次 `yield` 都会暂停函数，把事件传给调用者
- 调用者处理完后，函数从暂停处继续执行

---

### 3.4 事件传输机制（SSE）

```python
# src/agentscope/app/_router/_session.py:530
@session_router.get("/{session_id}/stream")
async def stream_session_events(session_id, ...):
    async def _sse_generator() -> AsyncGenerator[str, None]:
        # 1. 重放缓冲的事件（断线重连）
        for _entry_id, event in await message_bus.log_read(...):
            yield f"data: {json.dumps(event)}\n\n"
        
        # 2. 订阅实时事件
        queue = asyncio.Queue()
        await message_bus.subscribe(..., queue)
        
        # 3. 实时推送
        while True:
            item = await queue.get()
            yield f"data: {json.dumps(item)}\n\n"
    
    return StreamingResponse(
        _sse_generator(),
        media_type="text/event-stream",
    )
```

**关键点** 🔴：
- 使用 **SSE**（Server-Sent Events）传输
- 支持**断线重连**（重放缓冲事件）
- 每 30 秒发送**心跳**保持连接

## 四、实现原理与流程

### 4.1 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  1. 事件定义层（Pydantic 模型）                              │
│     - EventBase（基类）                                      │
│     - 30+ 种具体事件类                                       │
└─────────────────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 事件产生层（AsyncGenerator + yield）                     │
│     - Agent._reply() → yield 事件                           │
│     - Agent._reasoning() → yield 事件                       │
│     - Agent._execute_tool() → yield 事件                    │
└─────────────────────────────────────────────────────────────┘
         │
         ▼
─────────────────────────────────────────────────────────────┐
│  3. 事件传输层（SSE / StreamingResponse）                    │
│     - FastAPI Router: /{session_id}/stream                  │
│     - MessageBus（Redis Pub/Sub）                           │
└─────────────────────────────────────────────────────────────┘
         │
         ▼
─────────────────────────────────────────────────────────────┐
│  4. 事件消费层（前端 appendEvent）                           │
│     - EventSource 接收 SSE                                  │
│     - msg.appendEvent(event) 重建消息                       │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 事件产生层实现

#### 4.3.1 核心方法：`Agent._reply()`

```python
# src/agentscope/agent/_agent.py:580
async def _reply(self, inputs):
    # 1. 检查输入类型
    if isinstance(inputs, (UserConfirmResultEvent, ExternalExecutionResultEvent)):
        event = inputs
        msgs = None
    else:
        event = None
        msgs = inputs
    
    # 2. 处理事件或消息
    is_awaiting = await self._check_incoming_event(event)
    
    if is_awaiting:
        # 继续之前暂停的事件
        async for evt in self._handle_incoming_event(event):
            yield evt
    else:
        # 新消息处理
        await self._handle_incoming_messages(msgs)
        self.state.reply_id = _generate_id()
        self.state.cur_iter = 0
        
        # 埋点：发送开始事件
        yield ReplyStartEvent(
            session_id=self.state.session_id,
            reply_id=self.state.reply_id,
            name=self.name,
        )
    
    # 3. ReAct 循环
    while self.state.cur_iter < self.react_config.max_iters:
        action, data = self._check_next_action()
        
        if action == "exit" and isinstance(data, Msg):
            yield data
            return
        
        if action == "reasoning":
            await self.compress_context()
            async for evt in self._reasoning():
                if isinstance(evt, Msg):
                    yield ReplyEndEvent(...)
                    yield evt
                    return
                yield evt
        
        if action == "acting":
            for batch in await self._batch_tool_calls():
                async for evt in evt_generator:
                    yield evt
                    if isinstance(evt, (RequireUserConfirmEvent, ...)):
                        return
    
    # 4. 达到最大迭代次数
    yield ExceedMaxItersEvent(...)
    yield ReplyEndEvent(...)
```

**实现要点**：
- 使用 `async def` + `yield` 变成异步生成器
- 每次 `yield` 暂停函数，把事件传给调用者
- 调用者处理完后，函数从暂停处继续执行

#### 4.3.2 推理阶段：`Agent._reasoning_impl()`

```python
# src/agentscope/agent/_agent.py:782
async def _reasoning_impl(self, tool_choice):
    # 埋点 1：模型调用开始
    yield ModelCallStartEvent(
        reply_id=self.state.reply_id,
        model_name=self.model.model,
    )
    
    # 调用 LLM
    res = await self._call_model(**kwargs)
    
    block_ids = {"text": None, "thinking": None, "tools": [], "data": []}
    completed_response = None
    
    # 处理流式响应
    if inspect.isasyncgen(res):
        async for chunk in res:
            if chunk.is_last:
                completed_response = chunk
            else:
                # 将 chunk 转换为事件
                async for evt in self._convert_chat_response_to_event(
                    block_ids, chunk
                ):
                    yield evt
    
    # 发送块结束事件
    if block_ids["text"] is not None:
        yield TextBlockEndEvent(...)
    if block_ids["thinking"] is not None:
        yield ThinkingBlockEndEvent(...)
    
    # 埋点 2：模型调用结束
    yield ModelCallEndEvent(
        reply_id=self.state.reply_id,
        input_tokens=completed_response.usage.input_tokens,
        output_tokens=completed_response.usage.output_tokens,
    )
```

**实现要点**：
- 调用 LLM 后，将响应转换为事件
- 使用 `block_ids` 字典跟踪每个内容块的 ID
- 流式响应逐 chunk 转换为事件

#### 4.3.3 事件转换：`_convert_chat_response_to_event()`

```python
# src/agentscope/agent/_agent.py:2426
async def _convert_chat_response_to_event(self, block_ids, chunk):
    # 1. 分类内容块
    text_blocks = [b for b in chunk.content if isinstance(b, TextBlock)]
    thinking_blocks = [b for b in chunk.content if isinstance(b, ThinkingBlock)]
    tool_call_blocks = [b for b in chunk.content if isinstance(b, ToolCallBlock)]
    
    # 2. 处理文本块
    if text_blocks:
        if not block_ids.get("text"):
            block_ids["text"] = _generate_id()
            yield TextBlockStartEvent(
                reply_id=self.state.reply_id,
                block_id=block_ids["text"],
            )
        
        yield TextBlockDeltaEvent(
            reply_id=self.state.reply_id,
            block_id=block_ids["text"],
            delta="".join([b.text for b in text_blocks]),
        )
    
    # 3. 处理思考块（类似）
    if thinking_blocks:
        if not block_ids.get("thinking"):
            block_ids["thinking"] = _generate_id()
            yield ThinkingBlockStartEvent(...)
        
        yield ThinkingBlockDeltaEvent(...)
    
    # 4. 处理工具调用
    for tool_call in tool_call_blocks:
        if tool_call.id not in block_ids["tools"]:
            block_ids["tools"].append(tool_call.id)
            yield ToolCallStartEvent(
                reply_id=self.state.reply_id,
                tool_call_id=tool_call.id,
                tool_call_name=tool_call.name,
            )
        
        yield ToolCallDeltaEvent(
            reply_id=self.state.reply_id,
            tool_call_id=tool_call.id,
            delta=tool_call.input,
        )
```

**实现要点**：
- 将 LLM 响应的 ContentBlock 转换为事件
- 使用 `block_ids` 跟踪每个块的 ID，确保 Start/Delta/End 正确配对
- 文本/思考/工具调用分别处理

```python
        yield RequireUserConfirmEvent(
            reply_id=self.state.reply_id,
            tool_calls=[tool_call],
        )
        return  # 暂停执行，等待用户输入
    
    if decision.behavior == PermissionBehavior.ALLOW:
        # 埋点：工具结果开始
        yield ToolResultStartEvent(
            reply_id=self.state.reply_id,
            tool_call_id=tool_call.id,
            tool_call_name=tool_call.name,
        )
        
        # 执行工具
        async for chunk in tool_call.execute(**parsed_input):
            # 埋点：工具结果增量
            yield ToolResultTextDeltaEvent(
                reply_id=self.state.reply_id,
                tool_call_id=tool_call.id,
                delta=chunk.text,
            )
        
        # 埋点：工具结果结束
        yield ToolResultEndEvent(
            reply_id=self.state.reply_id,
            tool_call_id=tool_call.id,
            state=state,
        )
```

**实现要点**：
- 权限检查后，根据决策决定下一步
- `ASK` 决策会暂停执行，等待用户确认
- 工具执行结果通过事件流式返回

#### 4.4.1 SSE 路由

```python
# src/agentscope/app/_router/_session.py:530
@session_router.get("/{session_id}/stream")
async def stream_session_events(
    session_id: str,
    agent_id: str = Query(...),
    user_id: str = Depends(get_current_user_id),
    storage: StorageBase = Depends(get_storage),
    message_bus: MessageBus = Depends(get_message_bus),
) -> StreamingResponse:
    
    async def _sse_generator() -> AsyncGenerator[str, None]:
        # 1. 重放缓冲的事件（断线重连）
        for _entry_id, event in await message_bus.log_read(
            MessageBusKeys.session_events(session_id),
            max_count=MessageBusKeys.SESSION_REPLAY_MAX_LEN,
        ):
            yield f"data: {json.dumps(event)}\n\n"
        
        # 2. 订阅实时事件
        queue = asyncio.Queue()
        await message_bus.subscribe(
            MessageBusKeys.session_events(session_id),
            queue,
        )
        
        # 3. 实时推送
        try:
            while True:
                try:
                    item = await asyncio.wait_for(
                        queue.get(),
                        timeout=30,  # 30 秒超时
                    )
                    if item is None:
                        break
                    yield f"data: {json.dumps(item)}\n\n"
                except asyncio.TimeoutError:
                    yield ":\n\n"  # 心跳
        finally:
            await message_bus.unsubscribe(...)
    
    return StreamingResponse(
        _sse_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },
    )
```

**实现要点**：
- 使用 `StreamingResponse` 返回 SSE 流
- 先重放缓冲事件（断线重连）
- 再订阅实时事件
- 每 30 秒发送心跳保持连接

```python
# 伪代码
class MessageBus:
    async def publish(self, channel: str, event: dict):
        """发布事件到 Redis Pub/Sub"""
        await self.redis.publish(channel, json.dumps(event))
        await self.log_write(channel, event)  # 写入日志
    
    async def subscribe(self, channel: str, queue: asyncio.Queue):
        """订阅事件"""
        pubsub = self.redis.pubsub()
        await pubsub.subscribe(channel)
        
        async for message in pubsub.listen():
            event = json.loads(message["data"])
            await queue.put(event)
    
    async def log_read(self, channel: str, max_count: int):
        """读取事件日志（用于重放）"""
        return await self.redis.lrange(channel, 0, max_count)
```

**实现要点**：
- 使用 Redis Pub/Sub 实现事件分发
- 事件同时写入日志（用于重放）
- 支持多订阅者

```typescript
// 前端 SDK
class Msg {
    content: ContentBlock[] = [];
    
    appendEvent(event: AgentEvent) {
        switch (event.type) {
            case EventType.TEXT_BLOCK_START:
                // 创建新的文本块
                this.content.push({
                    type: "text",
                    id: event.block_id,
                    text: ""
                });
                break;
            
            case EventType.TEXT_BLOCK_DELTA:
                // 找到对应的文本块，追加文本
                const block = this.content.find(b => b.id === event.block_id);
                if (block) {
                    block.text += event.delta;
                }
                break;
            
            case EventType.TEXT_BLOCK_END:
                // 标记完成
                break;
            
            case EventType.TOOL_CALL_START:
                // 创建新的工具调用块
                this.content.push({
                    type: "tool_call",
                    id: event.tool_call_id,
                    name: event.tool_call_name,
                    input: ""
                });
                break;
            
            case EventType.TOOL_CALL_DELTA:
                // 找到对应的工具调用块，追加参数
                const toolBlock = this.content.find(b => b.id === event.tool_call_id);
                if (toolBlock) {
                    toolBlock.input += event.delta;
                }
                break;
            
            // ... 其他事件类似
        }
    }
}
```

**实现要点**：
- 根据事件类型和 ID 找到对应的内容块
- Delta 事件追加到对应块
- Start/End 事件标记块的开始和结束

### 4.10 实现原理总结

**事件系统的实现原理**：

1. **定义层**：Pydantic 模型定义 30+ 种事件类型
2. **产生层**：AsyncGenerator + yield 在代码关键位置埋点（精确位置见上表）
3. **传输层**：SSE + Redis Pub/Sub 实现实时推送（重放 + 实时组合）
4. **消费层**：前端 EventSource 接收，appendEvent 重建消息

**核心设计思想**：
- 事件是"流式数据"，通过 `yield` 产生
- 通过 SSE 传输到前端
- 通过 ID 关联归类
- 最终在前端重建为完整的消息
- **洋葱模型**（`execute_chain`）在每个关键阶段提供中间件拦截能力

```python
        if event.type == EventType.REQUIRE_USER_CONFIRM:
            pending_confirm = event
            break
    
    # 用户确认后，继续执行
    confirm_event = UserConfirmResultEvent(
        reply_id=pending_confirm.reply_id,
        confirm_results=[...]
    )
    async for event in agent.reply(inputs=confirm_event):
        yield event
```

#### Q1: 事件和消息的本质区别是什么？为什么需要两套系统？

> - **消息（Message）**：完整的对话回合，**静态视图**，用于持久化存储和发送给 LLM
> - **事件（Event）**：消息的流式传输单元，**动态视图**，用于实时渲染和断点续传

> 3. **持久化 vs 实时**：消息需要持久化，事件可以丢失（重连后重放）

#### Q4: 如何实现 SSE 的断线重连和消息去重？

**参考答案**：
> **断线重连**：
> 1. **客户端**：浏览器自动重连（EventSource API）
> 2. **Last-Event-ID**：客户端发送最后收到的 Event-ID
> 3. **服务端**：从该 ID 后重放事件，然后切换到实时推送
>
> **消息去重**：
> 1. **Event-ID 去重**：客户端维护已收到的 Event-ID 集合
> 2. **幂等处理**：相同 Event-ID 的事件只处理一次
> 3. **滑动窗口**：只保留最近 N 个 Event-ID，避免内存溢出
>
> **网络抖动处理**：
> 1. **指数退避**：重连间隔指数增长（1s → 2s → 4s → 8s）
> 2. **最大重试**：超过最大重试次数后，提示用户刷新
> 3. **心跳检测**：定期发送心跳，检测连接是否存活

**追问**：
- 如果客户端断线期间产生了 1000 个事件，如何处理？→ 批量重放，但限制单次重放数量（如 100 个），剩余事件通过分页获取
- 如何保证重放的事件和实时事件不重复？→ 使用 Event-ID 去重

#### Q5: 如何在前端实现流式 Markdown 解析器？

**参考答案**：
> **核心挑战**：
> 1. **标签截断**：`**bold` 被截断，无法判断是否完整
> 2. **代码块未闭合**：````python\nprint(``` 被截断
> 3. **嵌套结构**：列表嵌套代码块，解析复杂
>
> **解决方案**：
> 1. **缓冲机制**：缓存不完整的标签，等待下一个 chunk
> 2. **状态机**：维护解析状态（普通文本、粗体、代码块等）
> 3. **增量解析**：只解析新增内容，避免全量重解析
> 4. **容错处理**：未闭合标签自动补全（如 `**bold**`）
>
> **实现步骤**：
> ```javascript
> class StreamingMarkdownParser {
>   constructor() {
>     this.buffer = '';
>     this.state = 'normal'; // normal, bold, code, etc.
>   }
>   
>   parse(chunk) {
>     this.buffer += chunk;
>     const result = [];
>     
>     while (this.buffer.length > 0) {
>       const token = this.nextToken();
>       if (!token) break; // 等待更多数据
>       
>       result.push(this.renderToken(token));
>       this.buffer = this.buffer.slice(token.length);
>     }
>     
>     return result.join('');
>   }
>   
>   nextToken() {
>     // 状态机解析
>     if (this.state === 'normal') {
>       if (this.buffer.startsWith('**')) {
>         // 检查是否闭合
>         const endIndex = this.buffer.indexOf('**', 2);
>         if (endIndex === -1) return null; // 等待更多数据
>         return this.buffer.slice(0, endIndex + 2);
>       }
>     }
>     // ... 其他状态
>   }
> }
> ```

**追问**：
- 如何处理代码块中的 Markdown 语法？→ 代码块内不解析 Markdown
- 如何优化性能？→ 使用 Web Worker 异步解析，避免阻塞主线程

#### Q6: 如何设计一个支持"优先级调度"的流式请求队列？

**参考答案**：
> **场景**：用户同时发起多个请求（如翻译 + 代码生成），需要优先处理高优先级任务
>
> **设计方案**：
> 1. **优先级队列**：使用优先队列（如二叉堆）管理请求
> 2. **中断机制**：低优先级请求可以被中断，让出资源
> 3. **恢复机制**：中断的请求可以从中断点恢复
> 4. **公平调度**：避免高优先级请求饿死低优先级请求
>
> **实现步骤**：
> ```python
> import heapq
> from enum import IntEnum
> 
> class Priority(IntEnum):
>     LOW = 3
>     MEDIUM = 2
>     HIGH = 1
>     CRITICAL = 0
> 
> class StreamingRequestQueue:
>     def __init__(self, max_concurrent=3):
>         self.queue = []  # 优先队列
>         self.active = {}  # 活跃请求
>         self.max_concurrent = max_concurrent
>     
>     def submit(self, request, priority=Priority.MEDIUM):
>         heapq.heappush(self.queue, (priority, request.id, request))
>         self.schedule()
>     
>     def schedule(self):
>         while len(self.active) < self.max_concurrent and self.queue:
>             priority, req_id, request = heapq.heappop(self.queue)
>             self.active[req_id] = request
>             request.start()
>     
>     def interrupt(self, req_id):
>         if req_id in self.active:
>             request = self.active.pop(req_id)
>             request.pause()  # 暂停，保存状态
>             # 可以重新加入队列
>             heapq.heappush(self.queue, (request.priority, req_id, request))
> ```

**追问**：
- 如何保存中断点？→ 序列化请求状态（如已生成的 token 数）
- 如何避免饿死？→ 老化机制（Aging）：等待时间越长，优先级越高

**面试加分点**：
- 提到 2026 年字节真题：优先级调度流式请求队列
- 提到 LLM 推理的 KV Cache 复用（中断后恢复）
- 提到成本控制：高优先级请求使用大模型，低优先级使用小模型

#### Q8: 如何设计 Agent 的事件溯源（Event Sourcing）架构？

**参考答案**：
> **核心思想**：Agent 状态 = 不可变事件流（Immutable Event Log）
>
> **架构设计**：
> ```
> 用户输入
>     ↓
> 命令（Command）： CreateUser、SendMessage
>     ↓
> 事件溯源层（Event Sourcing）
>     ↓  持久化事件： UserCreated、MessageSent
> 事件存储（Event Store）
>     ↓
> 状态重建（State Rebuilding）
>     ↓  重放事件，重建 Agent 状态
> Agent 状态（当前状态）
> ```
>
> **关键设计**：
> 1. **事件不可变**：事件一旦写入，不可修改（只能追加新事件）
> 2. **状态重建**：通过重放事件重建状态（而非直接修改状态）
> 3. **快照优化**：定期保存快照（Snapshot），避免全量重放
> 4. **事件版本**：事件结构变化时，使用版本号（v1、v2）
>
> **示例**：
> ```python
> # 事件定义
> @dataclass
> class Event:
>     id: str
>     type: str
>     data: dict
>     timestamp: datetime
>     version: int = 1
> 
> # 事件存储
> class EventStore:
>     def append(self, event: Event):
>         # 追加事件（不可修改）
>         self.db.insert(event)
>     
>     def replay(self, agent_id: str, from_version: int = 0):
>         # 重放事件，重建状态
>         events = self.db.query(agent_id, from_version)
>         state = AgentState()
>         for event in events:
>             state.apply(event)
>         return state
> 
> # Agent 状态
> class AgentState:
>     def apply(self, event: Event):
>         if event.type == 'MessageSent':
>             self.messages.append(event.data['message'])
>         elif event.type == 'ToolCalled':
>             self.tool_calls.append(event.data['tool_call'])
> ```

**追问**：
- 事件溯源和传统 CRUD 的区别？→ CRUD 直接修改状态，Event Sourcing 追加事件
- 如何处理事件结构变化？→ 使用版本号 + 事件升级（Event Upcasting）

**面试加分点**：
- 提到 2026 年趋势：Event-Sourced AI Agents（事件溯源 Agent）
- 提到 CQRS（命令查询职责分离）：写操作追加事件，读操作查询状态
- 提到确定性重放（Deterministic Replay）：相同事件流重建相同状态（用于调试、审计）

### 7.4 生产实战题（区分度最高）

#### Q10: 事件系统在生产环境中的常见坑和解决方案？

**参考答案**：
>
> | 问题 | 原因 | 解决方案 |
> |------|------|---------|
> | **连接泄漏** | 客户端异常断开，服务端未清理 | 心跳检测 + 超时断开（如 5 分钟无事件） |
> | **事件堆积** | 消费者处理慢，事件堆积 | 背压控制（Backpressure）+ 限流 + 扩容 |
> | **乱序问题** | 网络抖动导致事件乱序 | 全局递增 ID + 分区有序 |
> | **重复消费** | 重连时重复推送事件 | Event-ID 去重 + 幂等处理 |
> | **心跳失效** | 心跳超时导致连接断开 | 心跳间隔优化（如 30 秒）+ 指数退避重连 |
> | **内存溢出** | 事件对象未释放 | 弱引用（WeakRef）+ 定期 GC |
> | **事件丢失** | Redis 宕机 | Redis 持久化（AOF）+ 主从复制 |
>
> **真实案例**：
> - **案例 1**：某大厂 Agent 系统，Redis Pub/Sub 丢失事件 → 改用 Redis Stream（持久化）
> - **案例 2**：某大厂 SSE 系统，10 万连接导致 Nginx 崩溃 → 改用 sticky session + 限流

#### Q11: 如何优化事件系统的性能？

**参考答案**：
> **优化方向**：
> 1. **减少事件数量**：
>    - 事件合并（Event Coalescing）：多个小事件合并为一个大事件
>    - 事件过滤（Event Filtering）：只推送用户关心的事件
> 2. **减少事件大小**：
>    - 事件压缩（Event Compression）：使用 gzip 压缩事件
>    - 事件裁剪（Event Trimming）：只保留必要字段
> 3. **减少网络开销**：
>    - 批量推送（Batch Push）：多个事件合并为一个包
>    - 心跳合并（Heartbeat Coalescing）：多个连接的心跳合并
> 4. **减少处理开销**：
>    - 异步处理（Async Processing）：事件处理异步化
>    - 缓存优化（Cache Optimization）：热点事件缓存
>
> **真实数据**：
> - 事件合并：减少 50% 事件数量
> - 事件压缩：减少 70% 网络流量
> - 批量推送：减少 30% 网络开销
> - 异步处理：提升 2x 吞吐量

**追问**：
- 事件合并会不会导致延迟增加？→ 会，需要权衡（如 100ms 合并窗口）
- 如何决定合并窗口？→ 根据业务需求（如实时性要求高的场景，窗口小）

#### Q12: 如何设计一个支持多租户的事件系统？

**参考答案**：
> **核心挑战**：租户隔离（数据隔离、资源隔离、性能隔离）
>
> **设计方案**：
> 1. **数据隔离**：
>    - 租户 ID（Tenant ID）：每个事件携带租户 ID
>    - 分区存储（Partition Storage）：按租户 ID 分区（如 Redis Key = `tenant:{id}:events`）
> 2. **资源隔离**：
>    - 连接限制（Connection Limit）：每个租户限制连接数（如 1000）
>    - 带宽限制（Bandwidth Limit）：每个租户限制带宽（如 10Mbps）
> 3. **性能隔离**：
>    - 优先级队列（Priority Queue）：高优先级租户优先处理
>    - 资源预留（Resource Reservation）：为高优先级租户预留资源
> 4. **计费支持**：
>    - 事件计数（Event Counting）：记录每个租户的事件数
>    - 流量统计（Traffic Statistics）：记录每个租户的流量
>
> **实现示例**：
> ```python
> class MultiTenantEventSystem:
>     def __init__(self):
>         self.tenant_limits = {
>             'free': {'connections': 100, 'bandwidth': '1Mbps'},
>             'pro': {'connections': 1000, 'bandwidth': '10Mbps'},
>             'enterprise': {'connections': 10000, 'bandwidth': '100Mbps'},
>         }
>     
>     def publish(self, tenant_id: str, event: Event):
>         # 检查租户限额
>         if not self.check_limit(tenant_id):
>             raise LimitExceededError()
>         
>         # 发布事件（携带租户 ID）
>         event.tenant_id = tenant_id
>         self.event_store.append(event)
>         
>         # 计费
>         self.billing.record(tenant_id, event)
>     
>     def subscribe(self, tenant_id: str, callback):
>         # 检查连接限额
>         if not self.check_connection_limit(tenant_id):
>             raise ConnectionLimitExceededError()
>         
>         # 订阅事件（只推送该租户的事件）
>         self.event_store.subscribe(
>             filter=lambda e: e.tenant_id == tenant_id,
>             callback=callback
>         )
> ```

**追问**：
- 如何防止租户 A 看到租户 B 的事件？→ 严格的事件过滤（基于租户 ID）
- 如何处理租户突发流量？→ 限流 + 降级（如返回 429 Too Many Requests）

**面试加分点**：
- 提到 2026 年大厂真题：多租户事件系统设计
- 提到 SaaS 架构：多租户是 SaaS 的核心挑战
- 提到计费系统：事件计数 + 流量统计 → 账单生成
