## 一、核心概念

### 1.1 什么是工具模块？

**工具模块**是 AgentScope 中用于**封装、注册、管理和执行工具**的核心模块。

它将 Python 函数、MCP 工具、内置工具统一为一个接口：

```
┌─────────────────────────────────────────────────────────────┐
│                    Toolkit（工具集）                           │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │ FunctionTool │  │   MCPTool    │  │  Builtin     │      │
│  │ (Python函数)  │  │  (MCP协议)   │  │  (内置工具)   │      │
│  └──────────────┘  └──────────────┘  └──────────────      │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  ToolGroup   │  │   Skill      │  │  Permission  │      │
│  │  (工具分组)   │  │  (技能系统)   │  │  (权限控制)   │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

**关键理解** 🔴：
- **统一协议**：所有工具继承 `ToolBase`，对外暴露相同的接口
- **适配器模式**：Python 函数和 MCP 工具通过适配器转换为统一格式
- **分组管理**：工具按组管理，支持动态激活/停用
- **流式执行**：工具执行结果通过 `ToolChunk` 流式返回

---

### 1.2 为什么需要工具模块？

| 需求 | 没有工具模块 | 有工具模块 |
|------|-------------|-----------|
| 工具注册 | 手动管理 | 自动从函数签名提取 Schema |
| 工具执行 | 各自实现 | 统一流式接口 |
| 工具分组 | 无 | 按组激活/停用 |
| 权限控制 | 无 | 内置权限检查 |
| MCP 集成 | 手动适配 | 自动转换 |
| 技能系统 | 无 | 技能目录管理 |

**核心矛盾**：
- 不同来源的工具（Python 函数、MCP、内置）格式各异
- Agent 需要统一的工具调用接口

**AgentScope 的解法**：适配器模式 + 统一协议

class ToolBase(ABC):
    # 核心属性
    name: str                          # 工具名称
    description: str                   # 工具描述
    input_schema: dict                 # 输入 Schema（JSON Schema 格式）

    async def check_read_only(tool_input) -> bool

## 三、设计原理

### 3.1 适配器模式

```python
# src/agentscope/tool/_adapters.py:31
class FunctionTool(ToolBase):
    """适配器：将 Python 函数转换为 ToolBase 协议"""
    
    def __init__(
        self,
        func: Function,
        name: str | None = None,
        description: str | None = None,
        is_concurrency_safe: bool = True,
        is_read_only: bool = False,
        is_state_injected: bool = False,
        middlewares: list[ToolMiddlewareBase] | None = None,
    ):
        self.name = name or func.__name__
        self.description = description or _extract_func_description(func.__doc__)
        self.input_schema = _extract_input_schema(func)  # 从签名自动提取
        self._func = func
    
    async def call(self, **kwargs):
        """调用包装的函数"""
        if inspect.iscoroutinefunction(self._func):
            result = await self._func(**kwargs)
        else:
            result = self._func(**kwargs)
        
        # 统一转换为 ToolChunk
        return self._convert_func_result_to_chunk(result)
```

**关键点** 🔴：
- 自动从函数签名提取 JSON Schema
- 自动从 docstring 提取描述
- 统一转换为 `ToolChunk` 格式

### 3.2 MCP 工具适配

```python
# src/agentscope/tool/_adapters.py:167
class MCPTool(ToolBase):
    """适配器：将 MCP 工具转换为 ToolBase 协议"""
    
    is_mcp: bool = True
    
    def __init__(
        self,
        mcp_name: str,
        tool: mcp.types.Tool,
        client_gen: Callable | None = None,
        session: Any | None = None,
        timeout: float | None = None,
    ):
        # 工具名格式化：mcp__{server}__{tool}
        sanitized_tool = re.sub(r"[^a-zA-Z0-9_-]", "x", tool.name)
        self.name = f"mcp__{mcp_name}__{sanitized_tool}"
        
        # 保留完整的 inputSchema（包括 $defs）
        self.input_schema = dict(tool.inputSchema) if tool.inputSchema else {}
        
        # 从 MCP annotations 提取只读属性
        self.is_read_only = tool.annotations.readOnlyHint if tool.annotations else False
    
    async def call(self, **kwargs):
        """调用 MCP 工具"""
        if self._client_gen:
            # 无状态客户端：创建临时会话
            async with self._client_gen() as cli:
                async with ClientSession(...) as session:
                    result = await session.call_tool(self._tool.name, arguments=kwargs)
        else:
            # 有状态客户端：使用现有会话
            result = await self._session.call_tool(self._tool.name, arguments=kwargs)
        
        # 转换 MCP 结果为 AgentScope 格式
        return ToolChunk(
            content=self._convert_mcp_content_to_blocks(result.content),
            state=ToolResultState.ERROR if result.isError else ToolResultState.RUNNING,
        )
```

**关键点** 🔴：
- 工具名格式：`mcp__{server}__{tool}`
- 支持有状态/无状态 MCP 客户端
- MCP 结果自动转换为 AgentScope Block 格式

### 3.3 v2.0.4.post1 更新：Bash 只读安全 + MCP 依赖锁定

#### 3.3.1 EXPLORE 模式拒绝"会改数据的 find"（#2004）

`Bash.check_read_only()` 用 `BashCommandParser` 逐命令判断只读性。修复前，`find` 被整条列入 `READ_ONLY_COMMANDS`，导致 `find . -name x -delete` 这类**带变更谓词**的命令被误判只读、在 EXPLORE 模式（应全拒绝写）下漏网。

**修复**（`src/agentscope/tool/_builtin/_bash_parser.py`）：
- 抽出 `FIND_MUTATING_PREDICATES = {"-delete","-exec","-execdir","-fls","-fprint","-fprint0","-fprintf","-ok","-okdir"}`。
- `is_read_only_command()` 在命中只读命令后追加 `_is_mutating_find_command()` 检查：用 tree-sitter AST 解析，若 `find` 带上述任一谓词则返回 `False`（非只读）。
- 于是 EXPLORE 的只读快速路径对"改数据的 find"返回非只读 → 兜底 `DENY`；而纯 `find`（只读列举）仍被正确放行。

**设计动机**：`find` 是"读 / 写两态"命令的典型——默认像读，但 `-delete / -exec` 会落盘。朴素关键词白名单无法区分，必须用 AST 看实际谓词。

**⚠️ 面试考点**：为什么不能用字符串 `startswith("find ")` 判断只读？答：会漏掉 `find ... -delete` 的破坏性；AST 级谓词分析才能精确区分读 / 写两态命令。

#### 3.3.2 MCP 依赖版本锁定 `< 2.0.0`（#2091）

`pyproject.toml` 中 MCP 依赖从放开改为 **`"mcp<2.0.0"`**。

**设计动机**：MCP Python SDK **2.0 有 breaking change（尚未适配）**。若放任装到 2.x，MCPTool 的 `ClientSession` / `call_tool` 等调用会因 API 变更而失败。

**替代方案 / trade-off**：
- *替代*：立即适配 MCP SDK 2.0。代价是需重写适配器且要覆盖有 / 无状态两种客户端路径，节奏上跟不上 SDK 发布。
- *trade-off*：锁版本（短期稳定、牺牲"用最新 SDK"）vs 即时适配（追新但引入回归风险）。AgentScope 选**暂时锁定上界**，待适配完成再放开——典型的依赖管理现实取舍。

**⚠️ 面试考点**：依赖上界锁定的作用？答：在尚未适配下游 breaking change 时，用 `<` 上界防止自动装到不兼容版本，保护现有用户。

### 3.3 洋葱模型（工具中间件）

```python
# src/agentscope/tool/_base.py:36
class ToolMiddlewareBase(ABC):
    """工具中间件基类"""
    
    @abstractmethod
    async def on_tool_call(
        self,
        tool: "ToolBase",
        input_kwargs: dict[str, Any],
        next_handler: Callable[..., AsyncGenerator[ToolChunk, None]],
    ) -> AsyncGenerator[ToolChunk, None]:
        """拦截工具调用"""

# src/agentscope/tool/_base.py:209
async def __call__(self, *args, **kwargs):
    """洋葱模型执行工具中间件链"""
    middlewares = getattr(self, "_middlewares", [])
    if not middlewares:
        return await self.call(**kwargs)
    
    async def execute_chain(index=0, **chain_kwargs):
        if index >= len(middlewares):
            # 最内层：执行工具
            return await self.call(**chain_kwargs)
        else:
            mw = middlewares[index]
            async def next_handler(**kw):
                async for chunk in execute_chain(index + 1, **kw):
                    yield chunk
            async for chunk in mw.on_tool_call(
                tool=self,
                input_kwargs=chain_kwargs,
                next_handler=next_handler,
            ):
                yield chunk
    
    return execute_chain(**kwargs)
```

**关键点** 🔴：
- 与 Agent 中间件相同的洋葱模型
- 第一个注册的中间件是最外层
- 统一流式/非流式接口

#### 为什么选择洋葱模型？

**核心问题**：工具执行前后有很多"横切关注点"需要处理（日志、权限、重试、超时、缓存、限流、监控等），但这些逻辑不应该写在工具本身里。

**洋葱模型 vs 线性模型**：

```
线性模型（Pipeline）：
  Middleware1 → Middleware2 → Middleware3 → call()
  只能"拦截"调用，不能"包裹"返回

洋葱模型（Onion）：
  Middleware1 ─┐
    Middleware2 ─┐
      Middleware3 ─┐
        call()    │
      Middleware3 ─┘
    Middleware2 ─┘
  Middleware1 ─┘
  可以"包裹"整个调用过程（pre + post）
```

**洋葱模型的优势**：
- 中间件可以在调用前执行逻辑（如权限检查）
- 中间件可以在调用后执行逻辑（如日志记录）
- 中间件可以修改输入参数（传递给下一层）
- 中间件可以修改输出结果（返回给上一层）
- 中间件可以短路（不调用 next_handler，直接返回）

**设计亮点**：
- **职责分离**：工具只关心业务逻辑，横切关注点由中间件处理
- **可组合**：中间件可以任意组合，灵活配置
- **可复用**：中间件可以在多个工具间复用
- **流式统一**：`next_handler` 始终返回 `AsyncGenerator`，中间件不关心流式/非流式

**缺点**：
- 调试复杂：调用链长，调试时需要理解洋葱模型
- 顺序敏感：中间件注册顺序影响执行顺序，容易出错

> **详细中间件设计原理、实现机制和最佳实践**：参见 [08_中间件知识文档.md](./08_中间件知识文档.md)

### 3.3b ⚠️ main 分支新增（未发版，截至 2026-07-23）

#### PowerShell 内置工具（#2132）

Windows 上 `Bash` 不可用的问题终于有了官方解：新增 `PowerShell` 工具类（`src/agentscope/tool/_builtin/_powershell.py`），`LocalWorkspace.list_tools()` 按平台自动选择 shell：

```python
# workspace/_local_workspace.py（#2132 新增 override）
if os.name == "nt":
    shell: ToolBase = PowerShell(cwd=self.workdir, backend=backend)
else:
    shell = Bash(cwd=self.workdir, backend=backend)
return [shell, Edit(...), Glob(...), Grep(...), Read(...), Write(...)]
```

核心实现要点：

| 要点 | 说明 |
|------|------|
| 可执行探测 | 优先 `pwsh`（PowerShell 7+），回退 `powershell.exe`（Windows 内置 5.1），探测结果缓存 |
| **双层 Base64 编码** | 用户命令 → UTF-16LE base64 内嵌到 wrapper 脚本 → 整体再 base64 经 `-EncodedCommand` 传递。彻底规避引号/特殊字符转义地狱 |
| wrapper 脚本 | 关闭进度条（`$ProgressPreference=SilentlyContinue`，避免 CLIXML 噪音）、强制 UTF-8 输出编码、`ScriptBlock::Create` 还原并执行原命令 |
| 启动参数 | `-NoLogo -NoProfile -NonInteractive`——确定性执行，不受用户 profile 污染 |
| 只读判定 | `is_read_only=False` 恒定——PowerShell 语法复杂（cmdlet 别名、管道、表达式），不做静态只读分析，EXPLORE 模式下一律需审批（对比 Bash 有 `BashCommandParser` 白名单） |
| 超时 | 默认 120s，上限 600s，与 Bash 一致 |

**面试考点**：为什么用 `-EncodedCommand` 而不是 `-Command "..."`？PowerShell 的引号转义规则跨 cmd/pwsh 版本不一致，base64 编码是唯一无歧义的传参方式（这也是各类 RAT 恶意软件爱用它的原因——正常工程也有同样需求）。

#### MCP list_tools 失败降级（本地分支 fix/mcp-list-tools-error-handling）

`Toolkit` 聚合 MCP 工具时（`_toolkit.py:517`），原逻辑单个 MCP `list_tools()` 抛异常会中断整个工具装配、Agent 直接不可用。修复后 try-except 包裹，失败的 MCP 记 warning 并跳过，其余 MCP 与内置工具正常加载：

```

配套测试 `tests/tool/test_toolkit_mcp_error_handling.py`（153 行）。设计取舍：**可用性优先于完整性**——工具缺失时 Agent 仍能应答并告知用户，好过整体 500。

#### main 未发版更新（截至 2026-08-20）

**#2114 Read 工具支持 DataBlock 多模态返回**：`Read` 工具新增 `model_input_types` 参数（声明可返回的模态类型）与 `pages` 参数（PDF 分页读取）。读取二进制/结构化文件（如图片、PDF）时返回 `DataBlock` 而非纯文本，使多模态内容能直接进入模型上下文，无需强制转文本。

**#2316 check_tool_available 区分 inactive 与 missing**：原逻辑把"工具组未激活"和"工具不存在"都当作同一错误。修复后新增 `ToolGroupInactiveError`，`check_tool_available` 能区分两种情况——工具存在但组未激活（提示激活）vs 工具根本不存在（提示不存在），给 Agent 更准确的错误反馈。

**#2366 Bash 按 backend OS 选 shell**：`Bash` 工具选择 shell 时，由"宿主 OS"改为"**backend OS**"（`BackendBase.os_name`）。在远程/容器 backend 场景下，shell 应与执行环境匹配而非本地环境，避免在 Windows 宿主上误用 Linux shell 或反之。

**#2371 解析 PEP 563 惰性注解**：`FunctionTool` 提取工具 schema 时，支持 `from __future__ import annotations` 产生的**字符串化（惰性）类型注解**。修复前这类注解无法被 `inspect.signature` 正确解析，导致 schema 提取失败或类型错误。

**#2302 ResetTools 先验证 kwargs 再更新**：`ResetTools` 元工具在更新激活工具组前，先校验传入的 kwargs 是否合法（工具组是否存在、参数类型是否正确），校验失败则拒绝更新，避免非法参数导致工具组状态被破坏。

### 4.2 工具执行流程

```python
# src/agentscope/tool/_toolkit.py:225
async def call_tool(self, tool_call, state):
    """执行工具，返回流式结果"""
    tool_response = ToolResponse(id=tool_call.id)
    
    # 1. 检查工具是否可用
    available_tools = await self._get_available_tools(
        state.tool_context.activated_groups,
    )
    
    if tool_call.name not in available_tools:
        # 工具未激活或不存在
        yield ToolChunk(content=[...error...], state=ERROR)
        return
    
    # 2. 获取工具实例
    tool_func = available_tools[tool_call.name].tool
    
    # 3. 准备参数
    kwargs = _json_loads_with_repair(tool_call.input)
    
    # 4. 状态注入（如果需要）
    if tool_func.is_state_injected:
        kwargs["_agent_state"] = state
    
    # 5. 执行工具
    try:
        res = await tool_func(**kwargs)
        
        # 6. 处理结果（统一为流式）
        if isinstance(res, ToolChunk):
            yield res
            tool_response.append_chunk(res)
        elif isinstance(res, AsyncGenerator):
            async for chunk in res:
                yield chunk
                tool_response.append_chunk(chunk)
        elif isinstance(res, Generator):
            for chunk in res:
                yield chunk
                tool_response.append_chunk(chunk)
    
    except Exception as e:
        yield ToolChunk(content=[...error...], state=ERROR)
    
    finally:
        # 7. 返回完整结果
        yield tool_response
```

**关键点** 🔴：
- 统一流式接口：`ToolChunk` 流 + 最终 `ToolResponse`
- 状态注入：`is_state_injected=True` 时注入 `AgentState`
- 异常分类处理：MCP 异常、取消异常、开发者异常

#### 4.2.1 v2.0.6 修复：ToolResponse 错误状态优先级（#2178）

**问题**：`ToolResponse.append_chunk()` 合并多个 `ToolChunk` 时，状态更新是"后写覆盖"——若工具先报 `ERROR`，后续又收到 `INTERRUPTED`/`DENIED` chunk，最终状态会被错误地降级为中断/拒绝，**掩盖了真正的错误**。

**修复**：确立不可逆的优先级 `ERROR > INTERRUPTED/DENIED`，`ERROR` 一旦出现即锁定：

```python
# src/agentscope/tool/_response.py:136
if chunk.state == ToolResultState.ERROR:
    self.state = ToolResultState.ERROR
elif (
    self.state != ToolResultState.ERROR
    and chunk.state == ToolResultState.INTERRUPTED
):
    self.state = ToolResultState.INTERRUPTED
elif (
    self.state != ToolResultState.ERROR
    and chunk.state == ToolResultState.DENIED
):
    self.state = ToolResultState.DENIED
```

**关键点** 🔴：
- **优先级语义**：`ERROR` 是终态，一旦出现不可被 `INTERRUPTED`/`DENIED` 覆盖；`INTERRUPTED` 与 `DENIED` 之间仍按到达顺序（后到覆盖）
- **设计动机**：工具结果一旦报错，后续的确认/拒绝操作不应掩盖错误——前端据此可靠区分"工具真出错"与"用户中断/拒绝"
- 面试易错点：状态合并不是简单的"取最后"，而是带优先级的不可逆合并；`ERROR` 是最高优先级终态

**FunctionTool：Python 函数 → ToolBase**

class FunctionTool(ToolBase):
    def __init__(self, func, name=None, description=None, ...):
        self.name = name or func.__name__

class MCPTool(ToolBase):
    def __init__(self, mcp_name, tool, client_gen=None, session=None, ...):
        self.name = f"mcp__{mcp_name}__{tool.name}"  # 格式化名称
        self.description = tool.description
        self.input_schema = dict(tool.inputSchema)    # 直接用 MCP 的 Schema
        self.is_mcp = True
        self._tool = tool
        self._client_gen = client_gen  # 无状态客户端
        self._session = session        # 有状态客户端

    async def call(self, **kwargs):
        # 1. 调用 MCP 工具（支持有状态/无状态两种模式）
        if self._client_gen:
            async with self._client_gen() as cli:
                async with ClientSession(...) as session:
                    result = await session.call_tool(self._tool.name, arguments=kwargs)
        else:
            result = await self._session.call_tool(self._tool.name, arguments=kwargs)
        
        # 2. 转换 MCP 内容为 AgentScope 的 Block 格式
        return ToolChunk(content=self._convert_mcp_content_to_blocks(result.content))
```

**适配逻辑**：

- Schema 直接用 MCP 的 `inputSchema`

#### 4.3.4 洋葱模型：中间件链（`_base.py`）

```python
# src/agentscope/tool/_base.py:175
async def __call__(self, **kwargs):
    middlewares = getattr(self, "_middlewares", [])
    if not middlewares:
        return await self.call(**kwargs)  # 无中间件，直接调用
    
    # 洋葱模型：中间件层层包裹
    async def execute_chain(index=0, **chain_kwargs):
        if index >= len(middlewares):
            # 最内层：执行工具本身
            result = await self.call(**chain_kwargs)
            yield result
        else:
            mw = middlewares[index]
            async def next_handler(**kw):
                async for chunk in execute_chain(index + 1, **kw):
                    yield chunk
            # 当前中间件包裹下一层
            async for chunk in mw.on_tool_call(tool=self, input_kwargs=chain_kwargs, next_handler=next_handler):
                yield chunk
    
    return execute_chain(**kwargs)
```

**设计亮点**：
- 流式/非流式统一：`next_handler` 始终返回 `AsyncGenerator`
- 中间件不需要知道底层工具是流式还是非流式
- 洋葱模型：日志、权限、重试等横切关注点可灵活叠加

#### 4.3.6 设计亮点总结

| 设计点 | 实现方式 | 优势 |
|--------|---------|------|
| **统一协议** | `ToolBase` 抽象基类 | 所有工具来源实现同一接口 |
| **适配器模式** | `FunctionTool` + `MCPTool` | 自动转换，用户无感 |

| **洋葱中间件** | `ToolMiddlewareBase` + `execute_chain` | 横切关注点灵活叠加 |
| **流式统一** | `next_handler` 始终返回 `AsyncGenerator` | 中间件不关心流式/非流式 |
| **分组管理** | `ToolGroup` + `"basic"` 默认组 | 动态激活/停用 |
| **状态注入** | `is_state_injected` + `_agent_state` | 工具可访问 Agent 状态 |
| **安全隔离** | MCP 禁止状态注入 | 外部工具不可访问内部状态 |

#### 4.5.3 Skill vs Tool 的本质区别

| 维度 | Skill | Tool |
|------|-------|------|
| **本质** | 指令/知识 | 可调用函数 |
| **执行者** | LLM 自己执行 | 框架执行 |
| **访问方式** | 通过 SkillViewer 工具读取 | 直接调用 |
| **返回值** | Markdown 指令文本 | 执行结果 |
| **示例** | "代码审查清单" | "search()" 函数 |

#### 4.5.4 各框架 Skill 接入方式对比

| 框架 | Skill 怎么接入 | 特点 |
|------|--------------|------|
| **AgentScope** | 通过 `SkillViewer` 代理工具 | 调用方式统一，都是 `tool_call` |
| **CrewAI** | 直接注入 prompt | 简单直接，不经过工具 |
| **Claude Code** | MCP Prompts 转为 `/command` 斜杠命令 | 不走工具调用 |
| **CodeBuddy** | 直接注入 prompt | 和 MCP 分开管理 |

**AgentScope 的独特之处**：用"代理工具"把 Skill 接入工具体系，保持了调用方式的统一性。

### 4.6 Schema 自动生成

```python
# src/agentscope/tool/_utils.py:68
def _extract_input_schema(tool_func):
    """从函数签名自动提取 JSON Schema"""
    docstring = parse(tool_func.__doc__)
    params_docstring = {_.arg_name: _.description for _ in docstring.params}
    
    fields = {}
    for name, param in inspect.signature(tool_func).parameters.items():
        if name in ["self", "cls"]:
            continue
        
        fields[name] = (
            param.annotation if param.annotation != inspect.Parameter.empty else Any,
            Field(
                description=params_docstring.get(name),
                default=... if param.default is param.empty else param.default,
            ),
        )
    
    # 动态创建 Pydantic 模型
    base_model = create_model("_DynamicClass", **fields)
    return base_model.model_json_schema()
```

**关键点** 🔴：
- 从 `inspect.signature` 提取参数名和类型
- 从 docstring 提取参数描述
- 动态创建 Pydantic 模型生成 JSON Schema

### 6.1 核心设计思想

| 设计点 | 说明 |
|--------|------|
| **统一协议** | 所有工具继承 `ToolBase`，对外暴露相同接口 |

| **流式执行** | `ToolChunk` 流 + `ToolResponse` 统一结果 |
| **工具分组** | 按组管理，支持动态激活/停用 |
| **洋葱模型** | 工具中间件拦截执行 |
| **危险路径保护** | 防止误操作敏感文件和目录 |

#### Q5: MCP 的生产落地难点是什么？如何解决？

**参考答案**：
> **MCP 生产落地的 5 大难点**：
>
> | 难点 | 问题 | 解决方案 |
> |------|------|---------|

>
> **安全性详解**：
> ```
> 传统方式（Function Calling）：
>   应用层持有所有凭证 → 凭证泄露风险高
> 
> MCP 方式：
>   MCP Server 持有凭证 → 凭证隔离
>   最小权限原则 → 只暴露必要能力
>   审计日志 → 完整调用记录
> ```
>
> **稳定性详解**：
> ```python
> # 超时控制
> async def call_tool_with_timeout(tool, timeout=5.0):
>     try:
>         return await asyncio.wait_for(tool.call(), timeout=timeout)
>     except asyncio.TimeoutError:
>         return ToolChunk(content=[TextBlock(text="工具调用超时")])
> 
> # 重试机制
> async def call_tool_with_retry(tool, max_retries=3):
>     for attempt in range(max_retries):
>         try:
>             return await tool.call()
>         except Exception as e:
>             if attempt == max_retries - 1:
>                 raise
>             await asyncio.sleep(2 ** attempt)  # 指数退避
> 
> # 熔断机制
> class CircuitBreaker:
>     def __init__(self, failure_threshold=5):
>         self.failure_count = 0
>         self.state = "CLOSED"  # CLOSED, OPEN, HALF_OPEN
>     
>     async def call(self, tool):
>         if self.state == "OPEN":
>             return ToolChunk(content=[TextBlock(text="熔断中")])
>         
>         try:
>             result = await tool.call()
>             self.failure_count = 0
>             return result
>         except Exception:
>             self.failure_count += 1
>             if self.failure_count >= self.failure_threshold:
>                 self.state = "OPEN"
>             raise
> ```

- 如何评估 MCP Server 的安全性？→ 凭证隔离、权限控制、审计日志
- 如何处理 MCP Server 的兼容性问题？→ 版本管理、向后兼容

### 7.4 高级话题题（区分度最高）

#### Q9: 多工具协调和编排如何实现？（腾讯高频）

**参考答案**：
> **多工具协调的挑战**：
> 1. **工具依赖**：工具 B 依赖工具 A 的结果
> 2. **工具冲突**：多个工具可能产生冲突的结果
> 3. **工具编排**：需要按特定顺序调用工具
> 4. **错误处理**：某个工具失败时的回退策略
>
> **多工具协调模式**：
>
> | 模式 | 说明 | 适用场景 |
> |------|------|---------|
> | **顺序执行** | 按顺序调用工具 | 工具间有依赖关系 |
> | **并行执行** | 同时调用多个工具 | 工具间无依赖关系 |
> | **条件执行** | 根据条件选择工具 | 不同场景用不同工具 |
> | **循环执行** | 重复调用直到满足条件 | 需要迭代优化 |
>
> **工具编排示例**：
> ```python
> # 顺序执行：工具 B 依赖工具 A
> async def sequential_execution():
>     result_a = await tool_a.call(query="北京")
>     result_b = await tool_b.call(data=result_a)
>     return result_b
> 
> # 并行执行：多个工具无依赖
> async def parallel_execution():
>     results = await asyncio.gather(
>         tool_a.call(query="北京"),
>         tool_b.call(query="上海"),
>         tool_c.call(query="广州")
>     )
>     return results
> 
> # 条件执行：根据条件选择工具
> async def conditional_execution(query: str):
>     if "天气" in query:
>         return await weather_tool.call(query=query)
>     elif "新闻" in query:
>         return await news_tool.call(query=query)
>     else:
>         return await search_tool.call(query=query)
> ```
>
> **2026 年工具编排趋势**：
> 1. **Agentic 编排**：LLM 自主决定工具调用顺序
> 2. **图编排**：使用 DAG（有向无环图）描述工具依赖
> 3. **自适应编排**：根据执行结果动态调整编排策略

**追问**：
- 如何处理工具依赖？→ 顺序执行 + 结果传递
- 如何处理工具冲突？→ 优先级规则 + 人工审核
- 如何评估编排效果？→ 任务完成率、执行时间、成本

### 8.1.1 各框架统一封装方案详解

#### LangChain：`BaseTool` 统一抽象

```
统一层次：
  @tool 装饰器 → StructuredTool → BaseTool（最终统一）
  自定义类   → BaseTool
  第三方工具  → 适配为 BaseTool
```

| 维度 | 实现方式 |
|------|---------|
| **统一基类** | `BaseTool`（name + description + args_schema + _run/_arun） |
| **函数适配** | `@tool` 装饰器 → 自动提取 name/description/schema → 转为 `StructuredTool` |
| **Schema 统一** | 所有工具最终生成标准 JSON Schema |
| **执行统一** | 统一调用 `.invoke()` / `.ainvoke()` |
| **MCP 支持** | 后加，插件式接入 |

**特点**：
- 从简到繁 3 种方式（`@tool` → `StructuredTool` → 继承 `BaseTool`）
- 自动从 docstring + type hints 提取 Schema
- 同步/异步统一（`_run` / `_arun`）

---

#### Semantic Kernel：`KernelFunction` + `Plugin` 路由

```
统一层次：
  Native Code（@kernel_function） ─┐
  OpenAPI Specification           ─┼→ KernelPlugin → Kernel
  MCP Server                      ─┘
```

| 维度 | 实现方式 |
|------|---------|
| **统一基类** | `KernelFunction`（语义描述 + 输入/输出 Schema） |
| **原生代码** | `@kernel_function` 装饰器 + docstring |
| **OpenAPI** | 解析 Swagger 文件，动态生成 Plugin |
| **MCP** | 连接 MCP Server，导入为 Plugin |
| **统一注册** | `kernel.add_plugin()` |
| **统一调用** | LLM Function Calling → SK 路由到对应实现 |

**特点**：
- **依赖注入**：Plugin 构造函数可注入数据库连接、HTTP 客户端等
- **跨语言共享**：通过 OpenAPI 规范，其他语言的微服务也能作为 Plugin
- **双向 MCP**：既能消费 MCP Server，也能将自身暴露为 MCP Server
- **语义描述**：强调 Function 必须提供丰富的语义元数据

---

#### CrewAI：`BaseTool` + `@tool` + 生态兼容

```
统一层次：
  @tool 装饰器        ─┐
  继承 BaseTool       ─┼→ CrewAI Tool（统一接口）
  LangChain Tools     ─┤
  CrewAI Toolkit      ─┘
```

| 维度 | 实现方式 |
|------|---------|
| **统一基类** | `BaseTool`（name + description + args_schema + _run） |
| **函数适配** | `@tool` 装饰器 → 自动提取 docstring |
| **输入统一** | Pydantic 强类型校验 |
| **输出统一** | Agent 调用时自动序列化为 JSON；代码调用时返回原生对象 |
| **异步统一** | 框架自动处理事件循环，调用者无需关心 |
| **生态兼容** | 直接兼容 LangChain Tools |
| **缓存/错误** | 统一缓存机制 + 统一错误处理 |

**特点**：
- **双轨制返回**：代码调用返回原生对象，Agent 调用返回 JSON
- **自定义 Agent 视图**：`format_output_for_agent()` 控制 Agent 看到的格式
- **LangChain 兼容**：直接复用 LangChain 生态的数百个工具

### 8.2 为什么大多数 Agent 没有统一封装？

#### 8.2.1 设计哲学：Skill 和 MCP 是"不同层次"的东西

```
Skill = 指令/知识/方法论（告诉 Agent "如何思考"）
  - 静态注入到 prompt
  - 影响 Agent 的思维方式
  - 例如：代码审查清单、写作风格指南

MCP = 工具/能力（让 Agent "采取行动"）
  - 动态调用
  - 提供执行能力
  - 例如：搜索 GitHub、读取数据库

很多框架认为：这是两个不同的概念，不应该混为一谈
```

**CrewAI 的明确区分**：
> "Skills 不是 Tools。Skills 注入指令和上下文，告诉 Agent '如何思考'；Tools 提供可调用函数，让 Agent '采取行动'。"

#### 8.2.2 生命周期和执行方式不同

| 维度 | Skill | MCP |
|------|-------|-----|
| **加载时机** | 会话开始时注入 prompt | 运行时按需调用 |
| **执行方式** | 静态文本，不执行 | 动态调用，有返回值 |
| **状态** | 无状态 | 可能有状态（连接、认证） |
| **错误处理** | 无 | 需要处理超时、网络错误 |

**统一封装的复杂度**：
- 需要处理"静态指令"和"动态调用"的差异
- 需要统一权限模型（Skill 不需要权限，MCP 需要）
- 需要统一流式支持（Skill 不需要，MCP 可能需要）

#### 8.2.3 历史演进：MCP 太新

```
2023 初：只有函数工具
    ↓
2023 中：加了 Skill/Rules 系统（静态指令注入）
    ↓
2024 底：MCP 协议发布
    ↓
2025 初：开始适配 MCP（但架构已定型，只能"插件式"接入）

大多数编程 Agent 的 Skill/Rules 系统在 MCP 出现前就已经定型，
只能把 MCP 作为"外部工具"接入，无法深度整合到核心架构。
```

#### 8.2.4 工程复杂度：统一封装成本高

| 挑战 | 说明 |
|------|------|
| **执行环境差异** | Skill 在 prompt 中，MCP 可能远程执行 |
| **权限模型不同** | Skill 无需权限，MCP 需要 OAuth/Token |
| **错误处理不同** | Skill 无错误，MCP 需要处理超时/网络错误 |
| **流式支持差异** | Skill 不需要，MCP 可能需要 |
| **Schema 来源不同** | Skill 是 Markdown，MCP 是 JSON Schema |

**分开维护的好处**：
- 职责清晰，各管各的
- 工程简单，不需要处理复杂的适配逻辑
- 用户可以独立选择用不用 MCP 或 Skill

#### 8.2.5 用户需求：不是所有人都需要统一

```
场景 A：只需要 MCP（工具调用）
  - 用户想让 Agent 调用 GitHub API
  - 不需要 Skill，只需要 MCP
  - 统一封装反而增加学习成本

场景 B：只需要 Skill（知识注入）
  - 用户想让 Agent 遵循代码审查清单
  - 不需要 MCP，只需要 Skill
  - 统一封装反而增加复杂度

场景 C：两者都需要
  - 用户想让 Agent 遵循审查清单（Skill）+ 调用 GitHub API（MCP）
  - 分开管理更灵活：Skill 注入 prompt，MCP 按需调用
```

---

### 8.3 AgentScope 为什么能统一？

| 优势 | 说明 |
|------|------|
| **设计之初就考虑多来源** | 没有历史包袱，架构从一开始就支持统一 |
| **ToolBase 协议足够抽象** | 能同时容纳"静态指令"和"动态调用" |
| **Skill 也是工具** | AgentScope 的 Skill 包含指令 + 工具 + 资源，不是纯静态 |
| **工程投入大** | 统一封装的复杂度高，AgentScope 愿意投入 |

---

### 8.4 架构选择的权衡

> **不是其他 Agent "不想"统一，而是"没必要"或"做不到"。**
> 
> - **没必要**：Skill 和 MCP 是不同层次的东西，分开管理更清晰、更灵活
> - **做不到**：架构已定型，MCP 太新，无法深度整合
> 
> **AgentScope 的统一封装是一种"超前设计"**，优势是对 Agent 透明、易于扩展，但代价是工程复杂度高。其他框架选择"分开维护"是务实的工程决策。

**未来趋势**：随着 MCP 协议的成熟，可能会有更多框架走向统一，但"分开维护"也可能是长期并存的一种模式。

## 九、最佳实践

### 9.1 开发建议

1. **使用 docstring 描述工具**：Schema 自动生成依赖 docstring
2. **合理设置并发属性**：`is_concurrency_safe` 影响工具执行方式
3. **使用工具分组**：相关工具放在同一组，便于管理
4. **实现权限检查**：自定义工具应实现 `check_permissions()`

---

### 9.2 性能优化

1. **避免重复 Schema 生成**：Schema 在注册时生成一次
2. **合理使用并发**：`is_concurrency_safe=True` 的工具可并发执行
3. **缓存 MCP 连接**：使用有状态 MCP 客户端避免重复连接

---

### 9.3 安全建议

1. **危险路径保护**：不要修改 `dangerous_files` 和 `dangerous_directories`
2. **MCP 工具权限**：MCP 工具默认需要用户确认
3. **状态注入安全**：MCP 工具禁止状态注入

## 十、总结

### 一句话总结

> **工具模块通过 `ToolBase` 协议统一工具接口，通过适配器模式支持 Python 函数和 MCP 工具，通过 `Toolkit` 管理工具分组和技能系统，提供 Schema 自动生成、流式执行、权限控制等企业级能力。**
