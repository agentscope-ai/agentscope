## 一、核心概念

### 1.1 什么是 Agent？

**Agent（智能体）** 是 AgentScope 的**核心抽象**，本质上是一个**无状态的推理-行动循环引擎**。

它将以下能力整合到一个统一接口中：
- 大语言模型（LLM）调用
- 工具执行（Tool Execution）
- 权限系统（Permission System）
- 人机交互（Human-in-the-Loop）
- 上下文管理（Context Management）
- 中间件（Middleware）
- 状态管理（State Management）
- 事件系统（Event System）

**关键理解** 🔴：
- Agent 是**无状态**的——状态保存在 `AgentState` 中，可序列化/持久化
- Agent 是**循环引擎**——通过 ReAct 循环不断推理和行动
- Agent 是**统一接口**——一个类集成所有能力（God Object 模式）

---

### 1.2 Agent 的核心职责

| 职责 | 说明 |
|------|------|
| **接收输入** | 接收消息（Msg）或事件（Event） |
| **推理决策** | 调用 LLM 进行思考和决策 |
| **工具执行** | 调用工具完成任务 |
| **上下文管理** | 管理对话历史、压缩上下文 |
| **权限控制** | 检查工具调用权限 |
| **人机交互** | 暂停等待用户确认 |
| **中间件编排** | 在关键节点运行中间件 |
| **事件产出** | 产出结构化事件流 |

## 二、核心接口

### 2.1 公开 API

```python
class Agent:
    # 核心方法
    async def reply(inputs) -> Msg                    # 运行 ReAct 循环，返回最终消息
    async def reply_stream(inputs) -> AsyncGenerator  # 流式产出事件
    async def observe(msgs) -> None                   # 静默接收消息（不触发推理）
    async def compress_context(config) -> None        # 手动压缩上下文

    # v2.0.4: reply/reply_stream 的 inputs 参数新增支持 UserInterruptEvent
```

**关键区别** 🔴：

| 方法 | 返回值 | 用途 |
|------|--------|------|
| `reply()` | `Msg` | 获取最终结果（阻塞式） |
| `reply_stream()` | `AsyncGenerator[Event]` | 实时渲染（流式） |
| `observe()` | `None` | 添加上下文（不触发推理） |
| `compress_context()` | `None` | 手动压缩（控制上下文长度） |

**⚠️ v2.0.4**：`reply()` 和 `reply_stream()` 的 `inputs` 参数现在接受以下类型：
- `Msg` — 正常用户输入
- `ExternalExecutionResultEvent` — 外部执行结果
- `UserInterruptEvent` — **v2.0.4 新增**：中止 parked 状态的 reply

### 2.2 使用示例

```python
from agentscope.agent import Agent
from agentscope.message import UserMsg

# 创建 Agent
agent = Agent(
    name="assistant",
    system_prompt="你是一个有用的助手",
    model=your_model,
    toolkit=your_toolkit,
)

# 方式 1：阻塞式获取结果
result = await agent.reply(UserMsg("user", "帮我查天气"))
print(result)

# 方式 2：流式获取事件
async for event in agent.reply_stream(UserMsg("user", "帮我查天气")):
    print(event)

# 方式 3：静默观察（不触发推理）
await agent.observe([UserMsg("user", "这是背景信息")])

# 方式 4：手动压缩上下文
await agent.compress_context()
```

## 四、ReAct 循环（核心机制）

### 4.1 什么是 ReAct？

**ReAct** = **Re**asoning（推理）+ **Act**ing（行动）

Agent 在每次 `reply()` 调用时，启动 ReAct 循环：
1. **推理**：LLM 根据当前上下文思考，决定下一步行动
2. **行动**：执行工具调用
3. **观察**：将工具结果反馈给 LLM
4. **循环**：重复直到得出最终回复

---

### 4.2 ReAct 循环流程

```python
# src/agentscope/agent/_agent.py:569
async def _reply_impl(self, inputs):
    # Step 1: 检查输入（新消息 or 继续事件）
    is_awaiting = await self._check_incoming_event(event)
    
    # Step 2: 处理输入
    if is_awaiting:
        # 继续之前暂停的事件（HITL）
        async for evt in self._handle_incoming_event(event):
            yield evt
    else:
        # 新消息处理
        await self._handle_incoming_messages(msgs)
        self.state.reply_id = _generate_id()
        self.state.cur_iter = 0
        
        yield ReplyStartEvent(...)  # 🔴 埋点：回复开始
    
    # Step 3: ReAct 循环
    while self.state.cur_iter < self.react_config.max_iters:
        # 3.1 检查下一步行动
        action, data = self._check_next_action()
        
        if action == "exit":
            yield data
            return
        
        # 3.2 推理阶段
        if action == "reasoning":
            await self.compress_context()  # 压缩上下文
            async for evt in self._reasoning():
                if isinstance(evt, Msg):
                    yield ReplyEndEvent(...)  #  埋点：回复结束
                    yield evt
                    return
                yield evt
        
        # 3.3 行动阶段
        if action == "acting":
            for batch in await self._batch_tool_calls():
                async for evt in evt_generator:
                    yield evt
                    if isinstance(evt, (RequireUserConfirmEvent, ...)):
                        return  # 暂停，等待用户确认
        
        # 3.4 迭代计数
        self.state.cur_iter += 1
    
    # Step 4: 达到最大迭代次数
    yield ExceedMaxItersEvent(...)  #  埋点：超过最大迭代
    yield ReplyEndEvent(...)
```

#### 4.2.1 v2.0.6 修复：reasoning-acting 轮次计数（#2217）

**问题**：旧实现每轮循环末尾无条件 `cur_iter += 1`。当一轮中 Agent 发起了工具调用但**尚未拿到结果**（工具仍在执行/等待确认）时，该轮其实还没"完成"，但计数已提前递增——导致 `max_iters` 被过早耗尽，长工具链任务提前中断。

**修复**：递增前先检查是否还有未完成的工具调用，有则不递增：

```python
# src/agentscope/agent/_agent.py:977
if not self.state.get_unfinished_tool_calls(self.name):
    self.state.cur_iter += 1
```

**关键点** 🔴：
- 新增 `AgentState.get_unfinished_tool_calls(agent_name)`：返回当前 agent 尚未拿到结果的工具调用集合
- **语义**：`cur_iter` 从"循环执行次数"修正为"**完整 reasoning-acting 轮次数**"——只有一轮真正走完（工具结果已回填）才计数
- **影响**：多步工具链（每步都要等工具返回）不再被 `max_iters` 误杀；HITL 等待确认的轮次也不消耗配额
- 面试易错点：`cur_iter` 不是"模型调用次数"，而是"完成的轮次数"；未完成工具调用的轮次不计数

### 4.3 下一步行动决策（_check_next_action）

```python
# src/agentscope/agent/_agent.py:2297
def _check_next_action(self):
    """
    决策逻辑：
    
    |                          | 有待确认工具 | 无待确认工具 |
    | ------------------------ | ------------ | ------------ |
    | 有可执行工具             | 执行工具     | 执行工具     |
    | 无可执行工具             | 退出等待     | 继续推理     |
    """
    last_msg = self._get_last_msg()
    
    # 分类工具调用
    awaiting_tool_calls = []   # 等待确认/外部执行
    executable_tool_calls = [] # 可以立即执行
    
    for tool_call in unfinished_tool_calls:
        if tool_call.state in [PENDING, ALLOWED]:
            executable_tool_calls.append(tool_call)
        elif tool_call.state == ASKING:
            awaiting_tool_calls.append(tool_call)
        elif tool_call.state == SUBMITTED:
            awaiting_tool_calls.append(tool_call)
    
    # 决策
    if executable_tool_calls:
        return "acting", None      # 有可执行工具 → 行动
    if awaiting_tool_calls:
        return "exit", msg         # 有待确认工具 → 退出等待
    return "reasoning", None       # 无工具 → 继续推理
```

**关键点** 🔴：
- 这是一个**状态机**，根据工具调用状态决定下一步
- `PENDING/ALLOWED` → 可执行
- `ASKING/SUBMITTED` → 等待外部输入
- 无工具 → 继续推理

## 五、上下文压缩

### 5.1 为什么需要压缩？

LLM 有上下文窗口限制（如 128K Token）。当对话历史超过限制时：
- 无法发送完整上下文给 LLM
- 需要压缩旧消息，保留关键信息

---

### 5.2 压缩触发机制

```python
# src/agentscope/agent/_agent.py:312
async def _compress_context_impl(self, context_config, instructions):
    cfg = context_config or self.context_config
    
    # 1. 计算当前 Token 数
    estimated_tokens = await self.model.count_tokens(**kwargs)
    
    # 2. 判断是否超过阈值
    threshold = cfg.trigger_ratio * self.model.context_size
    if estimated_tokens < threshold:
        return  # 未超过，跳过压缩
    
    # 3. 分割上下文（要压缩的 vs 要保留的）
    msgs_to_compress, msgs_to_reserve = await self._split_context_for_compression(
        cfg.reserve_ratio * self.model.context_size,
        tools,
    )
    
    # 4. 调用 LLM 生成摘要
    res = await self.model.generate_structured_output(
        messages=messages,
        structured_model=cfg.summary_schema,
    )
    
    # 5. 更新摘要
    self.state.summary = cfg.summary_template.format(**res.content)
    
    # 6. 卸载到磁盘（可选）
    if self.offloader:
        path = await self.offloader.offload_context(...)
        self.state.summary += f"\n<system-reminder>压缩内容已卸载到 '{path}'</system-reminder>"
    
    # 7. 更新上下文
    self.state.context = msgs_to_reserve
```

```

    ▼

## 六、人机交互（HITL）

### 6.1 用户确认流程

```
1. Agent 调用工具
   │
   ▼
2. 权限引擎检查
   │
   ├── ALLOW → 直接执行
   ├── DENY → 拒绝执行
   └── ASK → 暂停，等待确认
         │
         ▼
3. 发出 RequireUserConfirmEvent
   │
   ▼
4. Agent 暂停执行（return）
   │
   ▼
5. 前端显示确认框
   │
   ▼
6. 用户确认/拒绝
   │
   ▼
7. 发送 UserConfirmResultEvent
   │
   ▼
8. Agent 恢复执行（继续 ReAct 循环）
```

---

```
1. Agent 调用外部工具（is_external_tool=True）
   │
   ▼
2. 发出 RequireExternalExecutionEvent
   │
   ▼
3. Agent 暂停执行
   │
   ▼
4. 外部系统执行（前端/第三方 API）
   │
   ▼
5. 发送 ExternalExecutionResultEvent
   │
   ▼
6. Agent 恢复执行
```

```python
# src/agentscope/agent/_agent.py:538
async def execute_chain(index=0, inputs=inputs):
    if index >= len(self._reply_middlewares):
        # 链尾：调用实际实现
        async for item in self._reply_impl(inputs=inputs):
            yield item
    else:
        mw = self._reply_middlewares[index]
        
        async def next_handler(**kwargs):
            async for item in execute_chain(index + 1, **kwargs):
                yield item
        
        # 调用中间件
        async for item in mw.on_reply(
            agent=self,
            input_kwargs={"inputs": inputs},
            next_handler=next_handler,
        ):
            yield item
```

**关键点** 🔴：
- **递归闭包链**实现洋葱模型
- 每个中间件可以**前置处理**（在 `next_handler` 之前）和**后置处理**（在 `next_handler` 之后）
- `is_implemented` 惰性检测：构造时预计算，避免每次循环都检查

**v2.0.6+（#2322）on_reply 吞 ReplyEndEvent 继续循环**：
- 中间件可在 `on_reply` 中**吞掉 `ReplyEndEvent`**（不 yield 给上层），从而让回复循环**继续**而非结束。
- 实现：`_receive_reply_end` 钩子 + `made_progress` 标志。当中间件吞掉 ReplyEndEvent 后，Agent 检查本轮是否"有进展"（`made_progress`）；若吞掉但无进展，则**强制终止**，防止中间件误吞导致死循环。
- 典型用途：中间件在回复结束后注入额外上下文/工具结果，然后让 Agent 再跑一轮（如"先总结再追问"的迭代式回复）。

#### Q4: Agent 训练流程是什么？为什么 SFT 时要 mask 掉 observation tokens？（字节高频）

**参考答案**：
> **三阶段训练流程**：
>
> | 阶段 | 目标 | 数据 | 关键技术 |
> |------|------|------|---------|
> | **CPT**（Continual Pre-Training） | 注入领域知识 | 领域文档、代码 | 继续预训练 |
> | **SFT**（Supervised Fine-Tuning） | 学习工具调用格式 | 工具调用轨迹 | observation mask |
> | **RL**（Reinforcement Learning） | 优化决策策略 | 奖励模型 | PPO/DPO/GRPO |
>
> **为什么 SFT 时要 mask 掉 observation tokens？**
> - observation 是外部环境返回的结果（如搜索结果、API 返回），不是模型生成的
> - 如果对 observation 也算 loss，模型会试图学习预测搜索结果
> - 这件事既不可能（搜索结果不可预测）也没有意义（模型不需要记住搜索结果）
> - 正确做法：只对 `thought` 和 `action` 计算 loss，observation 部分 mask 掉
>
> **实现示例**：
> ```python
> # SFT 数据格式
> {
>     "messages": [
>         {"role": "user", "content": "查天气"},
>         {"role": "assistant", "content": "我需要调用天气 API"},  # thought（计算 loss）
>         {"role": "assistant", "tool_calls": [...]},              # action（计算 loss）
>         {"role": "user", "content": "北京今天晴，26°C"},         # observation（mask 掉）
>         {"role": "assistant", "content": "今天天气晴朗..."},     # 最终回复（计算 loss）
>     ]
> }
> 
> # 训练时 mask
> loss = model(messages, mask_positions=[2])  # 只计算第 3 条消息的 loss
> ```

**追问**：
- RL 阶段的奖励函数如何设计？→ 任务完成率 + 工具调用准确性 + 自我纠正能力
- 如何构建高质量的 SFT 数据？→ 人工标注 + 合成数据（Synthetic Data）+ 动作轨迹（Trajectory）
- CPT 和 SFT 的区别？→ CPT 注入知识（无监督），SFT 学习格式（有监督）

>
> | 层级 | 策略 | 实现方式 |
> |------|------|---------|
> | **第一层** | 重试机制 | 指数退避（1s → 2s → 4s → 8s） |
> | **第二层** | 模型降级 | 主模型失败切换小模型（`fallback_model`） |

> ```python
> try:
>     response = await model(messages, tools)
> except RateLimitError:
>     # 限流：指数退避重试
>     await asyncio.sleep(backoff_time)
>     return await retry()
> except ModelError:
>     # 模型错误：切换降级模型
>     if fallback_model:
>         return await fallback_model(messages, tools)
>     raise
> except TimeoutError:
>     # 超时：人工介入
>     yield RequireUserConfirmEvent(...)
>     return
> except Exception as e:
>     # 其他异常：记录日志，返回兜底消息

> ```python
> # 检测重复的 thought-action 对
> recent_patterns = hash(thought + action for last 3 iterations)
> if recent_patterns in history:
>     # 检测到循环，强制退出
>     yield ExceedMaxItersEvent(...)
>     return Msg("assistant", "我似乎陷入了循环，让我换个思路。")
> ```

#### Q8: 如何优化 Agent 的成本？（面试加分重点）

>
> | 策略 | 实现方式 | 效果 |
> |------|---------|------|

>        elif complexity == "medium":
>            return call_model("claude-sonnet-4-6", query)  # 平衡

>    # 相同或相似查询返回缓存结果

>        return cached
>    result = call_llm(prompt)
>    redis.setex(cache_key, ttl=3600, value=result)
>    ```

>    ```python
>    # 离线任务批量调用（Anthropic Batch API - 50% 成本降低）

## 十二、⚠️ v2.0.4 新增：Agent 中断机制

### 12.1 什么是 Agent 中断？

**Agent 中断**允许在 Agent 处于 **parked 状态**（等待用户确认或外部执行结果）时，通过 `UserInterruptEvent` 中止当前 reply，自动关闭未完成的 tool calls。

```
┌─────────────────────────────────────────────────────────────────┐
│                    Agent 中断生命周期                               │
│                                                                  │
│  1. Agent 执行 tool call → 需要用户确认（HITL）                    │
│     → reply 进入 parked 状态                                     │
│                                                                  │
│  2. 用户发送 UserInterruptEvent(reply_id=xxx)                     │
│     → reply() / reply_stream() 接收中断事件                       │
│                                                                  │
│  3. _reply_impl() 处理中断：                                      │
│     ├── state.has_awaiting_tool_calls() == True                  │
│     │   → 发出 ReplyEndEvent(finished_reason=INTERRUPTED)        │
│     │   → _close_unfinished_tool_calls() 关闭未完成的 tool calls  │
│     │                                                             │
│     └── state.has_awaiting_tool_calls() == False                 │
│         → 静默 no-op（idle session）                              │
│                                                                  │
│  4. _close_unfinished_tool_calls() 对每个未完成的 tool call：      │
│     ├── 发出 ToolResultEndEvent(state=INTERRUPTED)               │
│     ├── 注入中断消息到上下文                                       │
│     └── ToolResultBlock(state=INTERRUPTED)                       │
└─────────────────────────────────────────────────────────────────┘
```

### 12.2 核心实现

**新增事件类型**（`src/agentscope/event/_event.py`）：

```python
class UserInterruptEvent(EventBase):
    """中止 parked 状态的 reply"""
    reply_id: str  # 要中止的 reply ID
```

**新增枚举值**：

```python
class ReplyEndReason(StrEnum):
    COMPLETED = "completed"
    EXCEED_MAX_ITERS = "exceed_max_iters"
    INTERRUPTED = "interrupted"   # ← v2.0.4 新增
```

**中断消息注入**（`src/agentscope/agent/_agent.py`）：

```python
# _close_unfinished_tool_calls() 方法
interruption_message = (
    "<system-reminder>The tool call has been interrupted by "
    "the user.</system-reminder>"
)

# 为每个未完成的 tool call 注入中断消息
yield ToolResultEndEvent(
    reply_id=self.state.reply_id,
    state=ToolResultState.INTERRUPTED,
)
```

### 12.3 配置项

```python
# ReActConfig 新增字段
react_config = ReActConfig(
    interruption_raise_cancelled_error=False,  # 中断后是否抛 CancelledError
    interruption_message="...",                 # 自定义中断消息
)
```

### 12.4 使用示例

```python
from agentscope.event import UserInterruptEvent

# 场景：Agent 正在等待用户确认一个危险操作
# 用户决定取消

# 方式 1：通过 reply() 发送中断
await agent.reply(UserInterruptEvent(reply_id=current_reply_id))

# 方式 2：通过 reply_stream() 发送中断

    if isinstance(event, ReplyEndEvent) and event.finished_reason == "interrupted":
        print("Agent 已被中断")
```

**面试考点** 🔴：
- **为什么需要中断机制？** → HITL 场景中用户可能想取消等待中的操作
- **中断时如何保证 tool call 状态一致性？** → `_close_unfinished_tool_calls()` 为每个未完成的 tool call 注入 `INTERRUPTED` 状态的 ToolResultBlock
- **parked vs running 的区别？** → parked 等待外部输入（HITL/外部执行），running 正在执行推理循环。running 状态需 cancel 底层 task

## 十三、⚠️ main 分支新增（未发版，截至 2026-07-23）

### 13.1 结构化输出工具化（#2150，2026-07-22）

**背景**：v2.0.4 之前结构化输出依赖模型 API 原生的 `response_format`/JSON mode，与 ReAct 循环割裂——模型要么调工具、要么出结构化结果，无法"先推理再产出"。

**新机制**：结构化输出改为**内建工具** `_GenerateStructuredOutput`（`src/agentscope/agent/_structured_output_tool.py`）：

```python
# 调用方式：reply/reply_stream 传入 pydantic 模型类
result = await agent.reply("分析这段代码", structured_schema=MyModel)
# 结果在 AssistantMsg.structured_output（dict）
```

核心设计：

| 要点 | 说明 |
|------|------|
| 工具化 | schema 转为工具的 `input_schema`，模型通过 tool call 提交结构化结果，与 ReAct 循环天然融合 |
| 双路验证 | 进程内用 pydantic `model_validate`（支持自定义 validator）；状态恢复后只剩 JSON schema dict，用 jsonschema `Draft202012Validator` + 默认值回填 |
| 验证失败重试 | 验证失败返回 `ToolResultState.ERROR`，模型看到错误信息后可在下一轮迭代修正 |
| 宽限迭代 | `ReActConfig.structured_output_grace_iters`（默认 5）：达到 `max_iters` 后仍未产出结构化结果时，额外给宽限轮次，并用 `ToolChoice(mode="GenerateStructuredOutput")` 强制调用该工具 |
| 永远放行 | `check_permissions` 恒返回 ALLOW——纯输出转换，无副作用 |
| 状态归属 | schema 存在 `ReplyContext.structured_schema`（`state/_state.py:149`），序列化时类 → JSON schema dict，支持断点恢复 |

**面试考点**：为什么用工具而不用 API 原生 JSON mode？① 跨模型厂商统一（不依赖各家 response_format 差异）；② 与 ReAct 融合，允许"先查资料再输出"；③ 验证失败可自我修正。trade-off：多一轮 tool call 的 token 开销。

### 13.2 运行时状态注入（#2134，2026-07-20）

**问题**：系统提示是静态的，Agent 在长对话中对"当前时间、任务进度、上下文余量"缺乏感知。

**新机制**：`_inject_runtime_state()`（`_agent.py:1009`）在每次 reply 前按需将运行时状态以 `HintBlock` 追加到上下文，配置类为 `InjectionConfig`（`_config.py:142`）：

三个维度独立判定注入时机：
- **时间**：上下文中无时间记录（首次 reply 或压缩后），或距上次注入超过 `time_interval` 小时
- **任务**：存在 pending/in_progress 任务，且上下文中既无任务工具调用也无先前任务注入（如被压缩掉）
- **上下文长度**：reply 首轮迭代时 input tokens 进入压缩阈值的 `context_buffer_ratio`（默认 0.2）缓冲区，让 Agent 预感知即将压缩

关键设计决策（源码注释明确说明）：
1. **注入非临时性**——持久追加到上下文，让 Agent 建立"时间流逝感"
2. **用 HintBlock 而非改系统提示**——保住 prompt caching（系统提示变化会击穿缓存前缀）
3. **只注入会变化的信息**——固定信息应放系统提示
4. 通过 `injection_source` 标识自己的注入，扫描上下文去重；`extra_fields` 支持用户自定义字段搭车注入
5. `emit_hint_event=True` 时发出 `HintBlockEvent`，前端可见

### 13.3 thinking-only 响应循环修复（#2120，2026-07-20）

**Bug**：推理模型（如 DeepSeek R1、Claude extended thinking）可能产出**只含 ThinkingBlock** 的响应。旧逻辑判定"无 tool call ⇒ 最终答案"，导致循环提前结束，用户收到空回复。

**修复**（`_agent.py:1426`）：

```python
has_only_thinking_blocks = bool(completed_response.content) and all(
    isinstance(block, ThinkingBlock)
    for block in completed_response.content

# 结束条件追加 and not has_only_thinking_blocks
```

thinking-only 响应被视为中间推理步骤，循环继续，让模型在下一轮迭代产出文本或工具调用。

> **Agent 是 AgentScope 的核心抽象，通过 ReAct 循环整合 LLM 推理、工具执行、权限控制、人机交互、上下文管理、中间件编排等能力，采用无状态设计支持断点恢复和多租户隔离。v2.0.4 新增 Agent 中断机制，支持在 HITL 场景中优雅中止等待中的操作。**
