# 知识库文件上传与图片处理逻辑（含 URL 上传改造方案）

> 会话日期：2026-08-04
> 目标：梳理 AgentScope 文件上传处理逻辑（特别是图片文件的处理方式），并给出"上传图片 URL 而非图片流、由服务端下载并转 base64、尽可能不动源码"的改造方案。

---

## 一、整体架构概览

AgentScope 的知识库文件上传采用 **"上传即注册 + 异步索引"** 设计，核心参与者如下：

| 层级 | 组件 | 文件路径 | 职责 |
|---|---|---|---|
| 路由层 | `upload_knowledge_document` | `app/_router/_knowledge_base.py:445-505` | FastAPI 端点，接收 multipart 上传 |
| 服务层 | `KnowledgeBaseService.register_document` | `app/_service/_knowledge_base.py:221-304` | 流式写入 blob 存储 + 派发索引任务 |
| 存储层 | `BlobStoreBase` / `LocalBlobStore` | `app/rag/blob_store/_base.py`, `_local.py` | 字节级持久化（本地/S3） |
| 索引层 | `IndexWorker._run_pipeline` | `app/_service/_index_worker.py:310-390` | 后台管线：解析→分块→嵌入→入库 |
| 解析层 | `ParserBase` / `ImageParser` | `rag/_parser/_base.py`, `_image.py` | 按文件类型解析为 Section |
| 数据结构 | `Section` / `Chunk` / `DataBlock` | `rag/_document.py`, `message/_block.py` | 管线中的数据载体 |

---

## 二、文件上传的完整流程（通用）

```
HTTP multipart/form-data
        │
        ▼
[1] Router: upload_knowledge_document
    └─ file: UploadFile, content_type 可覆盖
        │
        ▼
[2] Service: register_document
    ├─ a. 权限校验 (_require_edit)
    ├─ b. 生成 document_id (uuid4.hex)
    ├─ c. blob_store.write_stream(key="kb/{kb_id}/{doc_id}", stream=file.file)
    │     └─ 流式分块写入（1 MiB/块），字节不全驻内存
    ├─ d. 持久化 KnowledgeDocumentRecord (status="pending")
    ├─ e. 失败回滚：删除已写入的 blob
    └─ f. enqueue_index_task(message_bus)  ← 异步派发
        │
        ▼
[3] 立即返回 { document_id, filename, status="pending" }
        │
        ▼  (后台异步)
[4] IndexWorker.process
    ├─ a. CAS 获取处理租约（防多 worker 重复处理）
    ├─ b. 心跳续租（防 sweeper 误回收）
    └─ c. _run_pipeline:
         ├─ ① 判定 media_type
         │    data.content_type or mimetypes.guess_type(filename)
         ├─ ② 路由到 parser (registry[media_type])
         ├─ ③ status → "parsing"
         ├─ ④ _read_blob: 流式读取全量字节（1 MiB/块）
         ├─ ⑤ parser.parse(bytes, filename) → list[Section]
         ├─ ⑥ status → "chunking"
         ├─ ⑦ chunker.chunk(sections) → list[Chunk]
         ├─ ⑧ status → "indexing"
         ├─ ⑨ knowledge.insert_document(chunks)
         └─ ⑩ status → "ready", chunk_count=len(chunks)
```

关键代码位置：
- 路由入口：`app/_router/_knowledge_base.py:451-505`
- 服务层注册：`app/_service/_knowledge_base.py:221-304`
- 管线执行：`app/_service/_index_worker.py:310-390`

## 三、图片文件的特殊处理逻辑

图片走通用流程，但在 **解析阶段** 与文本/PDF 完全不同。

### 3.1 路由判定：如何识别图片

```python
# app/_service/_index_worker.py:330-341
media_type = data.content_type or mimetypes.guess_type(data.filename)[0]
parser = self._parsers_by_media_type.get(media_type)
```

- 优先使用上传时传入的 `content_type`（如 `image/png`）
- 否则用 `mimetypes.guess_type` 根据文件名扩展名推断
- 通过 `media_type → parser` 路由表找到 `ImageParser`

`ImageParser` 声明支持的类型（`rag/_parser/_image.py:30-48`）：

```python
supported_media_types = [
    "image/png", "image/jpeg", "image/gif",
    "image/bmp", "image/webp",
]
# supported_extensions: .bmp .gif .jpeg .jpg .png .webp
```

### 3.2 ImageParser.parse：图片的核心处理

图片 **不做 OCR、不做描述生成**，而是把原始字节原样封装：

```python
# rag/_parser/_image.py:50-92
async def parse(self, file: bytes | str, filename: str) -> list[Section]:
    if isinstance(file, str):
        with open(file, "rb") as fp:
            file = fp.read()

    media_type = _guess_image_media_type(file)    # 嗅探 magic number
    data = base64.b64encode(file).decode("utf-8") # 整图 base64 编码
    return [
        Section(
            content=DataBlock(
                source=Base64Source(media_type=media_type, data=data),
                name=filename,
            ),
            source=filename,
            metadata={"media_type": media_type},
        ),
    ]
```

设计要点（来自 docstring）：**图片即 Section，原样透传给多模态嵌入模型**，绕过传统文本处理路径。

### 3.3 MIME 类型嗅探：靠 magic number 而非扩展名

`_guess_image_media_type`（`rag/_parser/_utils.py:20-47`）通过文件头魔数判定真实类型：

```python
signatures = {
    b"\x89PNG\r\n\x1a\n": "image/png",
    b"\xff\xd8":           "image/jpeg",
    b"GIF87a":             "image/gif",
    b"GIF89a":             "image/gif",
    b"BM":                 "image/bmp",
}
# WebP: RIFF@0 + WEBP@8
# 兜底: image/jpeg
```

最终 `Section` 里的 `media_type` 用的是这里嗅探的结果，而非上传声明的 `content_type`。

### 3.4 数据结构：DataBlock + Base64Source

图片字节被包装进两个 Pydantic 模型（`message/_block.py:56-98`）：

```python
class Base64Source(BaseModel):
    type: Literal["base64"] = "base64"
    data: str          # base64 编码的图片字节
    media_type: str    # 如 "image/png"

class DataBlock(BaseModel):
    type: Literal["data"] = "data"
    id: str
    source: Base64Source | URLSource   # 图片走 Base64Source
    name: str | None                   # 原始文件名
```

`Section.content` 是 `TextBlock | DataBlock` 联合类型（`rag/_document.py:48`），图片对应 `DataBlock`，文本对应 `TextBlock`。

### 3.5 后续阶段：分块与嵌入

- **分块（chunking）**：`ChunkerBase` 对 `DataBlock` 类型的 Section 透传不切分（`rag/_document.py:80-82`），整张图作为一个 Chunk。
- **嵌入（indexing）**：Chunk 流向 `KnowledgeBase.insert_document`，最终交给 **多模态嵌入模型**（如 DashScope 的 `qwen3-vl-embedding`、`multimodal-embedding-v1`，见 `src/agentscope/embedding/_dashscope/_models/*.yaml`）生成向量写入向量库。

## 四、图片 vs 文本类文件的处理对比

| 维度 | 图片（ImageParser） | PDF/Word/文本 |
|---|---|---|
| 解析输出 | 1 个 Section，content 为 `DataBlock` | N 个 Section，content 为 `TextBlock` |
| 内容提取 | 无（原样 base64） | 提取文本/表格/页结构 |
| MIME 判定 | magic number 嗅探 | 上传声明 / 扩展名推断 |
| 分块行为 | 透传不切 | 按 token/结构切分 |
| 嵌入模型 | 多模态嵌入模型 | 纯文本嵌入模型 |
| OCR | 无 | 无（纯文本提取） |

## 五、关键设计理念

1. **流式上传**：`write_stream` 按 1 MiB 分块写入 blob，大图也不全驻内存（`blob_store/_local.py:81-107`）。
2. **异步索引**：上传只注册 + 入队，解析/嵌入在后台 `IndexWorker` 完成，前端轮询状态。
3. **租约机制**：CAS 租约 + 心跳续租，保证多 worker 部署下同一文档只被处理一次（`_index_worker.py:215-290`）。
4. **图片原样透传**：`ImageParser` 不做内容理解，把"理解图片"的职责完全下放给多模态嵌入模型 —— 关注点分离。
5. **类型双重保障**：上传时用声明/扩展名做路由，解析时用 magic number 嗅探真实类型。

## 六、改造方案：新增 `/documents/by-url` 端点（只加不改源码）

### 6.1 需求与结论

- **需求**：上传的不是图片流，而是图片 URL；需服务端下载并转 base64，且尽可能不动源码。
- **约束**（用户确认）：新增独立 API 端点 + 图片来源公网可直接 GET + 注入方式子类化扩展。
- **关键澄清**：**子类化 `ImageParser` 其实不必要**。因为 `ImageParser.parse(file: bytes | str)` 本就接受 bytes，URL 下载后传 bytes 即可，parser 层零改动。子类化反而会把"网络下载"这一入口层职责塞进解析层，破坏原有分层。

### 6.2 改动清单

**只动一个文件**：`src/agentscope/app/_router/_knowledge_base.py`

1. **头部 import 补充**：加 `io`、`httpx`、`Body`、`HTTPException`、`AnyHttpUrl`、`BaseModel`
2. **文件末尾追加**：路由 `POST /{kb_id}/documents/by-url` + 请求模型 `UploadDocumentByUrlRequest`

**未动**：`ImageParser`、`KnowledgeBaseService`、`IndexWorker`、blob store、chunker、嵌入模型。

### 6.3 工作流程

```
客户端 POST /{kb_id}/documents/by-url  { "url": "https://.../cat.png" }
        │
        ▼
[路由层] upload_knowledge_document_by_url
   ├─ httpx.AsyncClient.stream("GET", url)  ← 流式下载，硬上限 20 MiB
   ├─ 边下载边写入 bytearray（内存可控）
   ├─ 从 URL path 推断 filename，从响应头取 content-type
   └─ io.BytesIO(bytes(buffer))  ← 包装成同步 IO[bytes]
        │
        ▼
[服务层] service.register_document(...)   ← 完全复用，未改动
   ├─ blob_store.write_stream  → 写入 blob
   ├─ 持久化 KnowledgeDocumentRecord (status=pending)
   └─ enqueue_index_task  → 异步派发
        │
        ▼
[索引层] IndexWorker._run_pipeline        ← 完全复用
   ├─ media_type 路由到 ImageParser
   ├─ _read_blob 读回字节
   ├─ ImageParser.parse(bytes) → base64 → DataBlock
   ├─ chunker 透传 DataBlock
   └─ 多模态嵌入模型 → 向量库
```

### 6.4 核心代码

```python
# 常量
_MAX_URL_DOWNLOAD_BYTES = 20 * 1024 * 1024  # 20 MiB 下载硬上限
_DOWNLOAD_TIMEOUT = 30.0                     # 秒


class UploadDocumentByUrlRequest(BaseModel):
    url: AnyHttpUrl          # 公网可直接 GET
    filename: str | None = None
    content_type: str | None = None


@knowledge_base_router.post(
    "/{knowledge_base_id}/documents/by-url",
    response_model=UploadKnowledgeDocumentResponse,
    status_code=status.HTTP_201_CREATED,
)
async def upload_knowledge_document_by_url(
    body: UploadDocumentByUrlRequest = Body(...),
    knowledge_base_id: str = Path(...),
    user_id: str = Depends(get_current_user_id),
    service: "KnowledgeBaseService" = Depends(get_knowledge_base_service),
) -> UploadKnowledgeDocumentResponse:
    url_str = str(body.url)

    # filename：显式指定 > URL path 末段 > uploaded_file
    if body.filename:
        filename = body.filename
    else:
        parsed = urlparse(url_str)
        tail = parsed.path.rsplit("/", 1)[-1]
        filename = tail if tail else "uploaded_file"

    buffer = bytearray()
    downloaded = 0
    try:
        async with httpx.AsyncClient(timeout=_DOWNLOAD_TIMEOUT,
                                     follow_redirects=True) as client:
            async with client.stream("GET", url_str) as resp:
                if resp.status_code >= 400:
                    raise HTTPException(
                        status_code=status.HTTP_502_BAD_GATEWAY,
                        detail=f"Remote URL returned {resp.status_code} ...")
                remote_content_type = resp.headers.get("content-type")
                async for chunk in resp.aiter_bytes():
                    downloaded += len(chunk)
                    if downloaded > _MAX_URL_DOWNLOAD_BYTES:
                        raise HTTPException(
                            status_code=status.HTTP_413_REQUEST_ENTITY_TOO_LARGE,
                            detail="Remote file exceeds the download cap.")
                    buffer.extend(chunk)
    except httpx.RequestError as exc:
        raise HTTPException(
            status_code=status.HTTP_502_BAD_GATEWAY,
            detail=f"Failed to fetch {url_str}: {exc}") from exc

    content_type = body.content_type or remote_content_type

    record = await service.register_document(
        user_id=user_id,
        knowledge_base_id=knowledge_base_id,
        filename=filename,
        stream=io.BytesIO(bytes(buffer)),
        size=len(buffer),
        content_type=content_type,
    )
    return UploadKnowledgeDocumentResponse(
        document_id=record.id,
        filename=record.data.filename,
        status=record.status,
    )
```

### 6.5 使用示例

```bash
curl -X POST http://localhost:8000/api/knowledge-bases/{kb_id}/documents/by-url \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/cat.png", "filename": "cat.png", "content_type": "image/png"}'
```

返回与原 `/documents` 端点完全一致：
```json
{ "document_id": "...", "filename": "cat.png", "status": "pending" }
```

### 6.6 关键设计点

| 设计点 | 说明 |
|---|---|
| **流式下载 + 硬上限** | `aiter_bytes()` 分块接收，`_MAX_URL_DOWNLOAD_BYTES=20MiB` 防超大文件打爆内存 |
| **超时控制** | `_DOWNLOAD_TIMEOUT=30s`，避免 hang 死 |
| **跟随重定向** | `follow_redirects=True`，兼容短链/CDN 跳转 |
| **错误转 502** | 远程 4xx/5xx 或网络异常统一转 `502 Bad Gateway`，不泄露内部异常 |
| **filename 推断** | 显式指定 > URL path 末段 > `uploaded_file` |
| **content_type 来源** | 显式指定 > 远程响应头 `Content-Type` > worker 兜底 `mimetypes.guess_type` |
| **通用性** | 该端点不仅支持图片，PDF/Word 的 URL 也可走，因下游按 media_type 分发 |

### 6.7 其他备选方案（未采用）

- **调用方预处理**：在 AgentScope 之外下载 URL→临时文件→调原 multipart 接口。最轻量、零源码改动，但需要客户端/调用方多一次处理。
- **子类化 `KnowledgeBaseService`**：加 `register_document_by_url` 方法，把 URL 下载职责放进服务层。适用于需要鉴权 header / referer 等特殊下载场景。
